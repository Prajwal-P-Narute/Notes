Q1 Triage How do you triage flaky and slow tests? ⌄
🗣 Say this in the interview "I look for patterns first — not fixes. I check CI artifacts like logs, traces, and video, then cross-reference with recent changes. I prioritise by failure rate again user impact, and fix root causes: smart waits, isolated test data, stable infra."
How to think about it
Check CI artifacts: logs, screenshots, traces, video — find where it breaks
Look for patterns: specific browser? time of day? environment only?
Recent changes: cross-reference failures with last few commits
Prioritise: failure rate × user impact = urgency
Fix root causes: hardcoded waits → smart waits, shared data → isolated data, environment drift → stable infra
💡 Key phrase to use "I triage by pattern, not symptom" — this shows systematic thinking.
Q2 Performance How do you prove slowness improvements? ⌄
🗣 Say this in the interview "Before touching anything I capture baseline timings from CI. Then I optimise — more parallelism, less setup/teardown, replace slow dependencies. After that I compare before and after. Numbers prove it, not opinions."
Steps
Step 1 — Baseline first: record current CI run times before any change
Step 2 — Optimise: increase parallelism, cut setup/teardown, replace slow APIs/DBs
Step 3 — Measure again: compare both numbers side by side
Step 4 — Report: "reduced suite from 18 min to 7 min" — concrete wins
💡 Key phrase to use "Numbers, not feelings, prove the win."
Q3 Strategy When do you choose API over UI testing? ⌄
🗣 Say this in the interview "API for fast business logic coverage — I use it heavily. UI only for critical user journeys and integrations where browser interaction itself matters. I aim for a healthy test pyramid, not a top-heavy UI suite, then I choose API over UI Testing."
Simple rule
Use API when: testing business rules, validations, data logic — fast and stable
Use UI when: critical user journeys, form flows, cross-browser rendering matters
Test Pyramid: many unit + API tests at the base, few UI tests at the top
💡 Key phrase to use "Test pyramid, not test ice-cream cone." — this phrase signals architectural maturity.
Q4 Migration When to migrate Selenium to Playwright? ⌄
🗣 Say this in the interview "I migrate flows with chronic flakiness or slow runs — Playwright's auto-waiting and modern API fix those. Stable, low-value Selenium tests stay until migration cost is justified. Always incremental, never big-bang."
Decision guide
Migrate when: flaky due to timing, slow due to waits, needs parallel runs — Playwright wins here
Keep Selenium when: test is stable, low business value, migration cost > benefit
Strategy: incremental migration, not rewriting everything at once
Playwright benefits: auto-waiting, async API, built-in parallelism, better debugging
💡 Key phrase to use "I think in cost-benefit, not technology trends."
Q5 Data How do you isolate test data in LambdaTest? ⌄
🗣 Say this in the interview "I use unique IDs per test run, per-test accounts, idempotent setup scripts, and cleanup hooks after each test. Shared mutable data is the root cause of most data-related flakiness — I eliminate it."
Techniques
Unique IDs: generate per test run — no two tests share the same data record
Per-test accounts: each test owns its user/account, not a shared one
Idempotent setup: setup can run multiple times without side effects
Cleanup hooks: always run after-test cleanup, even on failure
Never: share mutable state between parallel tests
Q6 SQL How to get the second highest salary with ties? ⌄
🗣 Say this in the interview "Use DENSE_RANK() ordered by salary descending, then filter where rank equals 2. DENSE_RANK handles ties correctly — LIMIT/OFFSET breaks when multiple people share the top salary."
Why DENSE_RANK and not others?
DENSE_RANK: ties get the same rank, next rank is consecutive — correct result ✓
RANK: ties skip numbers (1,1,3) — would miss data
LIMIT 1 OFFSET 1: breaks if two people tie for #1 — wrong result ✗
solution.sql
SELECT salary FROM ( SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees ) ranked WHERE rnk = 2;
Q7 Release How do you decide on release with red automation? ⌄
🗣 Say this in the interview "Hard block on high-severity, user-impacting failures — no exceptions. For known flaky tests, I quarantine them with a tagged owner and a fix-by date. I never silently ignore red — every decision is explicit and documented."
Decision framework
Red = high severity + user impact: BLOCK the release, no exceptions
Red = known flaky test: quarantine it — tag, assign owner, set fix-by date, then release
Never: silently ignore red or merge without a documented decision
Always: make the go/no-go call visible in the release doc or ticket
💡 Key phrase to use "Every red test has an owner and a fix-by date before we ship."
Q8 AI How should AI be used in testing? ⌄
🗣 Say this in the interview "AI is a suggestion engine, not a decision maker. I use it to speed up test generation and find coverage gaps, but every AI-written test goes through code review, deterministic assertion checks, and security scans. The human owns the quality bar."
How to use AI in QA
Good uses: test case suggestions, coverage gap analysis, data generation, boilerplate
Not a replacement for: human judgement on what matters to test
Every AI test must pass: code review + deterministic assertions + security scan before merge
Risk: AI is non-deterministic — never let it write assertions that check AI output vs AI output
💡 Key phrase to use "AI accelerates; the engineer decides." — shows you're in control.
Q9 Playwright What is the architecture of a Playwright framework? ⌄
🗣 Say this in the interview "Playwright runs on a client-server model — your test code is the client, and Playwright spins up a browser server per worker over a WebSocket connection using the Chrome DevTools Protocol. Each worker gets its own isolated browser context, so tests run in parallel without sharing state. On top of that I layer a Page Object Model, centralised fixtures for setup and teardown, and a config file that controls environments, parallelism, and retries."
Layer by layer
Protocol layer — CDP / WebSocket: Playwright communicates with Chromium, Firefox, and WebKit over the Chrome DevTools Protocol via a persistent WebSocket connection — no HTTP round-trips per action, so commands are fast and synchronised
Browser → Context → Page: one Browser process can hold multiple BrowserContexts (each is a fresh incognito-like session with its own cookies, storage, and network state), and each Context can have multiple Pages — this is how parallel tests stay fully isolated
Test runner — @playwright/test: built-in runner handles worker spawning, sharding, retries, fixtures, and reporters; no need for a separate Jest/Mocha layer
Fixture system: fixtures replace beforeEach/afterEach hooks — they're composable, scoped (test/worker/project), and automatically torn down; use them for auth state, API clients, and test data setup
Page Object Model on top: POM wraps page interactions into reusable classes — keeps tests readable and insulates them from UI changes; combined with fixtures, setup code stays out of test bodies
💡 Key phrase to use "Browser context is the isolation unit — one per test, zero shared state, full parallelism."
Q10 Framework What is the difference between an Automation Framework and an Automation Architect? ⌄
🗣 Say this in the interview "An Automation Framework is the technical foundation — the set of tools, libraries, and coding standards we use to build and run automated tests. In my case that's Playwright with a Page Object Model, Allure reporting, and CI/CD integration. An Automation Architect is the person who makes those strategic decisions — which tool to adopt, how to structure the framework, what coding standards to enforce, and how to scale automation across teams. Simply put: the Architect designs and owns the Framework."
Key distinctions
Framework = deliverable: a technical artifact — folder structure, reusable utilities, reporters, CI hooks. Examples: Selenium, Playwright, pytest, Robot Framework
Architect = decision-maker: a senior role that evaluates tools, defines standards, governs quality, and mentors the QA team
Framework types: Data-Driven, Keyword-Driven, Hybrid, BDD (Cucumber), Page Object Model — the Architect chooses the right pattern for the project
Scope difference: Framework is project-level; Architect operates at organisation or team level
My role: I build and maintain the Playwright framework — the Architect defined the overall strategy behind it
💡 Key phrase to use "One is a deliverable, the other is the decision-maker behind it."
Q11 Playwright How did you structure your Playwright framework? ⌄
🗣 Say this in the interview "I followed the Page Object Model — each page has its own class with locators and actions, so tests stay readable and are insulated from UI changes. Test data lives in separate files, environment config goes in .env files, and tests run in parallel using Playwright's built-in worker model. Reports are generated with Allure or the HTML reporter, and the whole suite is triggered through a CI/CD pipeline on every pull request."
Structure layer by layer
Page Object Model: each page (e.g. LoginPage, DashboardPage) is a class with locators and action methods — tests call methods, never raw selectors. Changes to the UI require updating only one class
Test data separation: JSON or TypeScript data files hold test inputs — tests import data rather than hardcoding values, making them easy to maintain and data-driven
.env + playwright.config.ts: environment URLs, credentials, and browser settings live in config — switching between staging and production is a one-line change
Parallel execution: Playwright workers run tests concurrently across multiple browsers (Chromium, Firefox, WebKit) — each worker gets its own BrowserContext so there is zero shared state
Reporting & CI/CD: Allure or HTML reporter generates visual reports on each run; tests are triggered via GitHub Actions / Jenkins on every PR, with failures blocking the merge
💡 Key phrase to use "I work on the framework — Playwright with POM. The Architect decides why and how it's built."
Q12 CI/CD How do you integrate automation into your CI/CD pipeline? ⌄
🗣 Say this in the interview "We run smoke tests tagged for quick feedback on every commit, so developers get a signal within minutes. Full regression runs either nightly or on a manual trigger so we don't slow down the pipeline on every push. Reports, screenshots, videos, and logs are all published as CI artifacts — so any failure is immediately traceable without having to re-run anything locally."
Pipeline strategy
Smoke on every commit: a fast, tagged subset of critical tests runs on each push — gives developers rapid feedback without blocking the build for minutes
Full regression = nightly or manual: the complete suite is expensive; scheduling it nightly or triggering it on demand keeps CI pipelines lean and cost-effective
Test tagging: tests are tagged (@smoke, @regression, @critical) so the pipeline can selectively run the right suite at the right stage
Artifacts for traceability: reports, screenshots, videos, and logs are published to the CI run — failures are debuggable without needing to reproduce locally
Gate on failure: smoke failures block the merge; regression failures raise alerts but are reviewed before the next release window
💡 Key phrase to use "Fast feedback on every commit, full confidence before every release."
Q13 Cloud When do you run tests locally vs on LambdaTest? ⌄
🗣 Say this in the interview "Local execution is for fast development feedback — when I'm writing or debugging a test, I don't want cloud overhead. LambdaTest comes in for cross-browser validation and parallel execution on high-priority scenarios, where I need real browser diversity at scale. We keep the cloud suite lean and optimised so we balance execution time against infrastructure cost."
Decision guide
Local = fast iteration: writing new tests, debugging failures, quick sanity checks — no cloud latency or cost, instant feedback loop
LambdaTest = scale & coverage: cross-browser (Chrome, Firefox, Safari, Edge) and cross-OS runs that would be impossible to replicate on a single dev machine
Optimised cloud suite: not the full regression — a curated set of high-priority, cross-browser-sensitive scenarios so cloud minutes are spent where they matter most
Cost vs confidence: running everything in the cloud is expensive; tagging tests by priority and browser sensitivity keeps costs predictable
Parallel execution: LambdaTest lets multiple tests run simultaneously across browsers — what takes 30 min locally can run in 5 min in parallel on the cloud grid
💡 Key phrase to use "Local for speed, cloud for coverage — I know when each one earns its cost."
Q14 AI How do you use AI in your day-to-day QA work? ⌄
🗣 Say this in the interview "I use AI as a productivity layer — it helps me generate test ideas quickly, spot flaky patterns across runs, cluster related failures, and suggest locators when the DOM gets messy. But every AI-generated change goes through a manual code review before it's merged, because AI suggestions can be plausible but subtly wrong. The reliability bar stays human-owned."
Where AI fits in QA
Test idea generation: AI can quickly suggest edge cases, boundary values, and negative scenarios that are easy to overlook — good for expanding coverage faster
Flaky pattern detection: AI can analyse CI history and surface tests that fail intermittently, grouping them by error signature or time-of-day patterns
Failure clustering: instead of reading 50 individual failure logs, AI can group them by root cause — speeds up triage significantly
Locator suggestions: AI can propose stable selectors (data-testid, ARIA roles) when the DOM is complex — but they must be verified against the actual application
Always reviewed before merge: AI output is a first draft, not a final answer — manual review catches subtle logic errors, incorrect assertions, and security issues
💡 Key phrase to use "AI writes the draft; I own the quality."
Q15 Security How do you handle secrets in your test automation setup? ⌄
🗣 Say this in the interview "We store secrets in environment variables and .env files that are never committed to Git — the repo holds no credentials, only placeholders. In CI, credentials are injected securely through the pipeline or CLI, and we use them to generate short-lived Kerberos tokens at runtime for API and database authentication. We also ensure secrets are masked in all log output so they are never accidentally exposed."
Secret management strategy
Environment variables + .env files: credentials live outside the codebase in environment variables or .env files; the repo only contains placeholder keys, never real values — a .gitignore entry enforces this
CI secret injection: pipelines (GitHub Actions, GitLab CI, Jenkins) have a dedicated secrets store; credentials are passed to the runner as masked environment variables, so they never appear in pipeline YAML or logs
Short-lived Kerberos tokens: instead of long-lived passwords, we use stored credentials to generate Kerberos tokens dynamically at runtime — tokens expire quickly, limiting the blast radius if one is ever leaked
Log masking: CI pipelines are configured to mask any variable flagged as a secret, so even if a test accidentally prints a token, it shows as *** in the log output
Common mistake — hardcoding for convenience: developers sometimes hardcode a working credential during local debugging and forget to remove it before committing; a pre-commit hook or secret-scanning tool (e.g. git-secrets, truffleHog) catches this before it reaches the remote
💡 Key phrase to use "Credentials are injected, never committed — and tokens are short-lived by design."
