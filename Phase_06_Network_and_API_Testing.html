🌐 HTTP Fundamentals

HTTP Methods — Quick Reference

HTTP Methods
MethodPurposeHas Body?Idempotent?Use Case
GETFetch resource❌ No✅ YesRetrieve user list, search
POSTCreate resource✅ Yes❌ NoCreate user, login, submit form
PUTReplace resource (full)✅ Yes✅ YesUpdate entire user record

📨 HTTP Request → Response Flow

🧑 Client sends: Method + URL + Headers + (Body)
↓
🌐 Server processes request
↓
✅ Response: Status Code + Headers + Body

📋 Headers

  • Content-Type: format of body (application/json)
  • Authorization: Bearer token / API key
  • Accept: expected response format
  • X-Custom-Header: app-specific data
  • Cache-Control: caching directives

🍪 Cookies

  • Sent in Cookie header by client
  • Set via Set-Cookie in response
  • Used for: sessions, auth tokens, preferences
  • Attributes: HttpOnly, Secure, SameSite
  • Playwright auto-manages cookies in context

🔢 HTTP Status Codes

HTTP Status Codes
RangeCategoryCommon Codes
1xxInformational100 Continue, 101 Switching Protocols
2xxSuccess ✅200 OK, 201 Created, 204 No Content
3xxRedirection301 Moved Permanently, 302 Found, 304 Not Modified
4xxClient Error ❌400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable
5xxServer Error 🔥500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable
💡 Tip: In Playwright, response.status() gives the code. Always assert status before parsing body — a 500 with JSON body can mislead you into thinking the call succeeded!
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “What are the main HTTP methods, and how do you use them in API testing?”

HTTP methods describe the action a client wants to perform on a resource.

GET is used to retrieve data, while POST commonly creates a new resource.

PUT usually replaces the full resource, while PATCH updates only selected fields.

DELETE is used to remove a resource when the API supports that operation.

In API tests, I check that the response status and body match the method's expected behavior.

For example, I usually expect a successful create to return a suitable status such as 201.

So, in short, I validate both the method's purpose and the response, so API tests check real behavior rather than status codes alone.

🔄 Also asked as: "Explain REST methods" / "What's the difference between PUT and PATCH?"

🧪 Playwright API Testing

Topic 23 — APIRequestContext

🔌 API Testing in Playwright

What is request?

The built-in APIRequestContext fixture in Playwright that lets you make HTTP calls directly — no browser needed. Shares cookies/auth state with the browser context.

Why use it?

  • Faster than UI — no rendering
  • Set up test data via API before UI test
  • Tear down after test
  • Validate API contracts independently

⚙️ Setup: APIRequestContext

// Method 1: Use 'request' fixture (auto-provided by Playwright) import { test, expect } from '@playwright/test'; test('API test using request fixture', async ({ request }) => { const response = await request.get('https://api.example.com/users'); await expect(response).toBeOK(); // status 200-299 }); // Method 2: Standalone context (useful outside test fixtures) const context = await playwright.request.newContext({ baseURL: 'https://api.example.com', extraHTTPHeaders: { 'Authorization': 'Bearer TOKEN' } });

📥 GET Request

const response = await request.get('/users/1'); expect(response.status()).toBe(200); const body = await response.json(); // parse JSON body expect(body.name).toBe('John');

📤 POST Request

const response = await request.post('/users', { data: { name: 'Jane', email: 'jane@test.com' }, // auto JSON-serialized headers: { 'Content-Type': 'application/json' } }); expect(response.status()).toBe(201); // 201 = Created

🔄 PUT (Full Update)

const res = await request.put( '/users/1', { data: { name: 'Updated', email: 'u@t.com' } }); expect(res.status()).toBe(200);

🩹 PATCH (Partial Update)

const res = await request.patch( '/users/1', { data: { email: 'new@t.com' } // only email changes }); expect(res.status()).toBe(200);

🗑️ DELETE Request

const res = await request.delete('/users/1'); expect(res.status()).toBe(204); // 204 = No Content (deleted, no body returned)
⚠️ Gotcha: request.delete() — don't call it .delete() in older JS — it's a reserved word in some transpilers. Playwright handles it safely but be aware in raw fetch.

🔎 Request Details & Response Validation

Topic 23 Continued

📬 Request Configuration Deep Dive

📋 Request Headers

const response = await request.get('/secure/data', { headers: { 'Authorization': `Bearer ${token}`, // auth 'Accept': 'application/json', // expected format 'X-Request-ID': 'test-123', // tracing/custom header 'Accept-Language': 'en-US' // locale } });

🔍 Query Parameters

// Option 1: Pass as params object (Playwright auto-encodes) const res = await request.get('/users', { params: { page: 2, limit: 10, role: 'admin' } // → /users?page=2&limit=10&role=admin }); // Option 2: Inline in URL (manual) const res2 = await request.get('/users?page=2&limit=10');

📦 Request Body Formats

// JSON body (most common for REST APIs) await request.post('/login', { data: { username: 'admin', password: 'pass' } // data → auto Content-Type: application/json }); // Form data (URL-encoded) await request.post('/upload', { form: { username: 'admin', token: 'abc' } // form → Content-Type: application/x-www-form-urlencoded }); // Multipart form (file upload) await request.post('/file', { multipart: { file: fs.createReadStream('./test.pdf'), name: 'report' } });

✅ Response Validation

const res = await request.get('/users/1'); // ── Status ────────────────────────── expect(res.status()).toBe(200); await expect(res).toBeOK(); // checks 200-299 range // ── Body ──────────────────────────── const body = await res.json(); // parse JSON const text = await res.text(); // raw string const buffer = await res.body(); // Buffer (binary) // ── Field Assertions ──────────────── expect(body.id).toBe(1); expect(body.name).toBe('John'); expect(body.email).toMatch(/^.+@.+\..+$/); // ── Headers ───────────────────────── expect(res.headers()['content-type']).toContain('application/json');
📝 Note: data: key auto-sets Content-Type: application/json. Using form: sets application/x-www-form-urlencoded. Using multipart: sets multipart/form-data. Pick the right key — don't mix them!
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “How do you make API requests directly in Playwright tests?”

Playwright's request fixture lets me send API requests directly without opening a browser page.

The reason this matters is I can validate backend behavior and prepare data quickly before UI tests run.

For authentication, I pass the required headers, and I use params for query-string values.

For request bodies, I send JSON data with the data option when the endpoint expects a body.

After the request, I assert the status code and read the response with response.json().

I use this approach to create test data through an API when the UI setup would be slower.

So, in short, I use direct API requests for fast setup and focused checks, keeping UI tests about user-visible behavior.

🕸️ Network Interception

Topic 24 — page.route()

🚦 Network Interception with page.route()

🔷 What is it? page.route() intercepts network requests matching a URL pattern before they reach the server. You can then inspect, modify, mock, block, or let them continue.

📐 Syntax

// page.route(urlPattern, handlerFn) await page.route('**/api/users', async (route, request) => { // 'route' → controls what happens to the request // 'request' → lets you inspect the original request await route.continue(); // default: just let it pass through });

🔀 What Can You Do With a Route?

📋 Route Actions — Code Examples

// ✅ CONTINUE — pass through (optionally modify request headers) await route.continue({ headers: { ...request.headers(), 'X-Test': 'true' } }); // ❌ ABORT — block the request entirely await route.abort(); // default error type: 'failed' await route.abort('blockedbyclient'); // or: 'connectionrefused' // 🎭 FULFILL — return a mock response (no network call) await route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify({ id: 1, name: 'Mocked User' }) }); // ✏️ FETCH + MODIFY — hit real server, then modify the response const realResponse = await route.fetch(); const json = await realResponse.json(); json.name = 'Modified Name'; // modify field await route.fulfill({ json }); // send modified response to browser

🚫 Block Specific Request Types

// Block all image/font requests → speeds up tests! await page.route('**/*', route => { const type = route.request().resourceType(); ['image', 'font', 'stylesheet'].includes(type) ? route.abort() : route.continue(); });
📌 Pattern Matching
'**/api/**' → any URL containing /api/
'https://exact.com/path' → exact URL
Can also use a RegExp: /.*\.json$/

🎭 API Mocking & Stubbing

Topic 25 — Mock / Stub / Simulate

🧩 API Mocking in Playwright

🔷 API Mocking = intercepting network calls and returning fake (controlled) responses. Test the frontend without a real backend. Also called stubbing.

1️⃣ Mock a Backend Response (Static)

// Return fake data without hitting the real API await page.route('**/api/products', async route => { await route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify([ { id: 1, name: 'Widget A', price: 9.99 }, { id: 2, name: 'Widget B', price: 19.99 } ]) }); }); await page.goto('/shop'); // page loads with mocked product data

2️⃣ Simulate API Errors

// Test how UI handles server errors await page.route('**/api/login', async route => { await route.fulfill({ status: 401, // Unauthorized contentType: 'application/json', body: JSON.stringify({ message: 'Invalid credentials' }) }); }); // → test that "Invalid credentials" error message appears in UI // Simulate network failure (no internet) await page.route('**/api/**', route => route.abort('failed')); // → test offline/error state in the UI

3️⃣ Simulate Slow APIs (Loading States)

// Add artificial delay to test loading spinners, skeleton screens await page.route('**/api/data', async route => { await new Promise(resolve => setTimeout(resolve, 3000)); // 3s delay await route.fulfill({ status: 200, body: JSON.stringify({ data: 'slow response' }) }); }); // ✅ Playwright test waits automatically — no flakiness from timeout

📊 Stub vs Mock vs Intercept — Comparison

Stub vs Mock vs Intercept
ConceptWhat it doesBackend hits?Use when...
StubReturns fixed fake response❌ NoBackend not ready / unstable
MockReturns dynamic fake response + can assert call was made❌ NoTest-specific data needed
InterceptCaptures real call, optionally modifies✅ YesReal data + modification needed
AbortBlocks request completely❌ NoTest error states / offline
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “What is API mocking in Playwright, and when would you use it?”

API mocking means intercepting a network request and returning a controlled response instead of calling the real backend.

The reason I use it is it lets me test UI behavior without depending on backend availability or changing data.

In Playwright, I intercept requests with page.route() and provide a response with route.fulfill().

For example, I can return a 401 response to check how the UI handles an expired session.

I can also mock empty data, specific records, or an error response for edge cases.

I keep in mind that mocks test frontend behavior, so important backend behavior still needs real API coverage.

So, in short, I mock only the network behavior needed for a scenario, making UI tests repeatable without hiding backend defects.

🔄 Also asked as: "How do you test frontend without backend?" / "How do you simulate errors in Playwright?"
💡 Pro tip: Use page.unroute('**/api/users') to remove a route handler after a specific test. Or use page.routeFromHAR('recorded.har') to replay a full network session!

⚠️ Common Mistakes & Gotchas ALWAYS READ
  • ⚠️ Forgetting to await route.fulfill() or route.continue() — request stays hanging forever
  • ⚠️ Using data: key but setting Content-Type: text/plain — Content-Type wins, server gets confused
  • ⚠️ Asserting status === 200 on a POST create request — it should be 201, not 200
  • ⚠️ Calling await res.json() on a 204 No Content response — throws because body is empty
  • ⚠️ page.route() registers the handler but doesn't fire until a matching request is actually made — always navigate/trigger after setting the route
  • ⚠️ Mocking '**/api/**' too broadly — blocks requests you didn't intend to mock, causing silent test failures
  • ⚠️ Confusing route.fetch() (hit real server) with route.fulfill() (skip server) — easy to mix up
  • ⚠️ PUT vs PATCH trap: sending a PATCH with only one field is fine; sending a PUT with only one field deletes all other fields

🧠 Memory Tricks & Last-Minute Tips
🧠 CRUD ↔ HTTP Method Mapping
Create → POST  |  Read → GET  |  Update → PUT/PATCH  |  Delete → DELETE
Mnemonic: "Create Really Useful Data"
🧠 Status Code Groups: "I See Maybe Some Silly"
1xx = Informational  |  2xx = Success  |  3xx = Move  |  4xx = Client Fail  |  5xx = Server Fail
🧠 Route Action: "Can A Footballer Fly?"
Continue  |  Abort  |  Fulfill  |  Fetch+modify — the 4 things you can do with a route
  • Always set up page.route() before navigating to the page — routes must be registered first
  • Use request fixture for API setup/teardown in test.beforeEach — don't create users via UI when API is faster
  • If asserting JSON body, always check status first — a 500 can return valid JSON that fools your assertions
  • To unregister a route: page.unroute('**/api/users') — prevents interference between tests
  • Record HAR files in dev tools and replay with page.routeFromHAR('file.har') — instant mocking without writing handlers
