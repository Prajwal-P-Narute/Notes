01

What is Playwright?

Playwright is an open-source automation framework by Microsoft for web automation, UI testing, API testing, and cross-browser testing — all in a single library.

Browsers
  • Chromium (Chrome / Edge)
  • Firefox
  • WebKit (Safari engine)
Languages
  • JavaScript / TypeScript
  • Python
  • Java & .NET
02

Why Playwright?

  • Fast execution & auto-waiting — eliminates flaky tests
  • Supports multiple tabs, windows & mobile emulation
  • Built-in parallel execution across browsers
  • Screenshots, videos, and traces out of the box
  • Full API testing support via request fixture
  • Network interception and mocking built-in
  • CI/CD friendly with HTML, JSON, JUnit reports
  • Auth state reuse — login once, share across tests

Custom Fixtures

NEW

Custom fixtures extend Playwright's built-in fixtures. Use them to inject page objects, shared state, or pre-configured contexts into every test automatically.

// fixtures/index.js
const { test: base } = require('@playwright/test');
const LoginPage        = require('../pages/LoginPage');
const DashboardPage    = require('../pages/DashboardPage');

const test = base.extend({
    // Auto-instantiate LoginPage for every test
    loginPage: async ({ page }, use) => {
        await use(new LoginPage(page));
    },

    // Already-logged-in page
    loggedInPage: async ({ page }, use) => {
        await page.goto('/login');
        await page.fill('#user', 'admin');
        await page.fill('#pass', 'admin123');
        await page.click('#login');
        await use(page); // test receives logged-in page
    }
});

module.exports = { test };
// tests/dashboard.spec.js — use custom fixture
const { test } = require('../fixtures');

test('Check dashboard', async ({ loggedInPage }) => {
    await loggedInPage.goto('/dashboard');
    // already logged in — no need to repeat login steps
});
Custom fixtures are the cleanest way to share setup logic across hundreds of tests without repeating code.

Locators

// By CSS
page.locator('#username')
page.locator('.login-btn')

// By XPath
page.locator('//button[text()="Login"]')

// By Text
page.getByText('Submit')
page.getByText('Submit', { exact: true })

// ★ Recommended — Role Based (accessibility-aligned)
page.getByRole('button', { name: 'Login' })
page.getByRole('textbox', { name: 'Username' })
page.getByRole('link', { name: 'Home' })

// By Placeholder
page.getByPlaceholder('Enter username')

// By Label
page.getByLabel('Email address')

// By data-testid (recommended for test-specific attrs)
page.getByTestId('submit-btn')
// HTML: <button data-testid="submit-btn">Submit</button>

// By title attribute
page.getByTitle('Delete item')
Priority: getByRole → getByLabel → getByPlaceholder → getByTestId → locator(css) → XPath (last resort)

Locator Chaining & Filtering

NEW

Locators can be chained and filtered to precisely target elements within a group — essential for tables, lists, and repeating components.

// .nth() — pick by index (0-based)
const firstRow = page.locator('tr').nth(0);
const lastBtn  = page.locator('button').last();
const firstBtn = page.locator('button').first();

// .filter() — narrow by text or nested locator
const adminRow = page
    .locator('tr')
    .filter({ hasText: 'admin' });

// Filter by nested locator
const activeCard = page
    .locator('.card')
    .filter({ has: page.locator('.badge-active') });

// Chain locators — scope to a parent
const form     = page.locator('#login-form');
const username = form.locator('#username');
await username.fill('admin');

// Count matching elements
const count = await page.locator('li').count();

// Loop over all matched elements
const items = page.locator('.product-name');
for (let i = 0; i < await items.count(); i++) {
    console.log(await items.nth(i).textContent());
}

Soft Assertions

NEW

Normal assertions stop the test on first failure. Soft assertions collect all failures and report them together at the end — useful when you want to validate multiple things in one test run.

const { test, expect } = require('@playwright/test');

test('Soft assertion example', async ({ page }) => {
    await page.goto('https://example.com');

    // These do NOT stop the test on failure
    await expect.soft(page).toHaveTitle('Example Domain');
    await expect.soft(page.locator('h1')).toHaveText('Example Domain');
    await expect.soft(page.locator('p')).toBeVisible();

    // Hard assertion — fails immediately if above soft ones failed
    expect(test.info().errors).toHaveLength(0);
});
Use soft assertions for UI validation forms where you want to see ALL broken fields, not just the first one.

Auto Waiting

Playwright automatically waits before performing any action. No explicit waits are needed in most cases.

Playwright waits for… Before action
Element to be visible click, fill, hover…
Element to be enabled click, type…
Element to be stable (no animation) click
Page navigation / network idle goto()
DOM to stabilize all actions
10b

Advanced Waits

NEW 
// Wait for element to appear (visible)
await page.waitForSelector('.toast-message');
await page.waitForSelector('#modal', { state: 'visible' });
await page.waitForSelector('#loader', { state: 'hidden' });

// Wait for URL to change
await page.waitForURL('**/dashboard');
await page.waitForURL(/login/);

// Wait for page load state
await page.waitForLoadState('networkidle'); // no network activity
await page.waitForLoadState('domcontentloaded');
await page.waitForLoadState('load');

// Wait for a specific API response
const responsePromise = page.waitForResponse('**/api/users');
await page.click('#load-users');
const response = await responsePromise;
console.log(await response.json());

// Wait for locator to be visible
await expect(page.locator('.result')).toBeVisible({ timeout: 10000 });
Prefer waitForURL, waitForSelector, and assertion-based waits over waitForTimeout.

        await page.click('#submit');
        await expect(page.locator('.error')).toBeVisible();

});

Hooks

    }
});

Page Object Model (POM)

pages/LoginPage.js
class LoginPage {
    constructor(page) {
        this.page    = page;
        this.url     = '/login';
        this.username = page.locator('#username');
        this.password = page.locator('#password');
        this.loginBtn = page.getByRole('button',{ name:'Login' });
        this.errorMsg = page.locator('.error-msg');
    }

    async navigate() {
        await this.page.goto(this.url);
    }

    async login(user, pass) {
        await this.username.fill(user);
        await this.password.fill(pass);
        await this.loginBtn.click();
    }

    async getErrorText() {
        return this.errorMsg.textContent();
    }
}

module.exports = { LoginPage };
tests/login.spec.js
const { test, expect } = require('@playwright/test');
const { LoginPage } = require('../pages/LoginPage');

test.describe('Login Tests', () => {

    test('Valid login', async ({ page }) => {
        const loginPage = new LoginPage(page);
        await loginPage.navigate();
        await loginPage.login('admin', 'admin123');
        await expect(page).toHaveURL(/dashboard/);
    });

    test('Invalid login', async ({ page }) => {
        const loginPage = new LoginPage(page);
        await loginPage.navigate();
        await loginPage.login('x', 'y');
        await expect(page.locator('.error'))
            .toBeVisible();
    });
});

Storage State / Auth Reuse

NEW

Instead of logging in before every test, save the browser's cookies & localStorage after one login and reuse it. This is the fastest way to handle authentication in large test suites.

// Step 1: Create auth/setup.js — run once before suite
const { chromium } = require('@playwright/test');

async function globalSetup() {
    const browser = await chromium.launch();
    const page    = await browser.newPage();
    await page.goto('https://example.com/login');
    await page.fill('#user', 'admin');
    await page.fill('#pass', 'admin123');
    await page.click('#submit');

    // Save cookies + localStorage to file
    await page.context().storageState({ path: 'auth.json' });
    await browser.close();
}
module.exports = globalSetup;
// Step 2: Reference in playwright.config.js
const config = {
    globalSetup: require.resolve('./auth/setup'),
    use: {
        storageState: 'auth.json'  // applied to ALL tests
    }
};
// Step 3: Tests now start already logged in — no login code needed
test('Dashboard loads', async ({ page }) => {
    await page.goto('/dashboard'); // already authenticated
    await expect(page.locator('h1')).toHaveText('Dashboard');
});
Using storageState can reduce test run time by 30–60% in suites with many tests that require login.

API Testing

const { test, expect } = require('@playwright/test');

test.describe('Users API', () => {

    test('GET — fetch user', async ({ request }) => {
        const res = await request.get('https://reqres.in/api/users/2');
        expect(res.status()).toBe(200);
        const body = await res.json();
        expect(body.data.id).toBe(2);
    });

    test('POST — create user', async ({ request }) => {
        const res = await request.post('https://reqres.in/api/users', {
            data: { name: 'Pratik', job: 'QA Engineer' }
        });
        expect(res.status()).toBe(201);
        const body = await res.json();
        expect(body.name).toBe('Pratik');
    });

    test('PUT — update user', async ({ request }) => {
        const res = await request.put('https://reqres.in/api/users/2', {
            data: { name: 'Updated', job: 'Lead QA' }
        });
        expect(res.status()).toBe(200);
    });

    test('PATCH — partial update', async ({ request }) => {
        const res = await request.patch('https://reqres.in/api/users/2', {
            data: { job: 'Senior QA' }
        });
        expect(res.status()).toBe(200);
    });

    test('DELETE — remove user', async ({ request }) => {
        const res = await request.delete('https://reqres.in/api/users/2');
        expect(res.status()).toBe(204);
    });

    test('With Auth headers', async ({ request }) => {
        const res = await request.get('/api/secure', {
            headers: {
                'Authorization': `Bearer ${process.env.TOKEN}`,
                'Content-Type': 'application/json'
            }
        });
        expect(res.ok()).toBeTruthy();
    });
});

Network Interception & Mocking

// Mock an API response
await page.route('**/api/users', async route => {
    await route.fulfill({
        status: 200,
        contentType: 'application/json',
        body: JSON.stringify([{ id: 1, name: 'Mock User' }])
    });
});

// Block all image requests (speed up tests)
await page.route('**/*.{png,jpg,jpeg,gif,svg}', route => route.abort());

// Modify a request before it goes out
await page.route('**/api/login', async route => {
    const request = route.request();
    await route.continue({
        headers: { ...request.headers(), 'X-Custom': 'test' }
    });
});

// Simulate network error
await page.route('**/api/data', route => route.abort('failed'));

// Remove a route after use
await page.unroute('**/api/users');

CI/CD & GitHub Actions

NEW

Playwright runs in headless mode by default — perfect for CI. Below is a complete GitHub Actions workflow.

# .github/workflows/playwright.yml
name: Playwright Tests

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  playwright:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test
        env:
          BASE_URL: 'https://staging.myapp.com'
          USERNAME: ${{ secrets.TEST_USERNAME }}
          PASSWORD: ${{ secrets.TEST_PASSWORD }}

      - name: Upload HTML Report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30

What is Playwright and how is it different from Selenium?
Playwright is a Microsoft automation framework that communicates directly with browsers via browser-native protocols (CDP for Chromium, custom for Firefox/WebKit) — unlike Selenium which uses WebDriver. This gives Playwright auto-waiting, faster execution, built-in network interception, and multi-tab support without extra libraries.
Feature Selenium Playwright
Waits Manual explicit waits Auto-wait built in
Speed Slower (WebDriver) Faster (direct protocol)
Network mocking External tools needed Built in
Multi-tab Complex workarounds Native support
API testing Not supported Built in
Trace/Video External tools Built in
What is a Browser Context in Playwright?
A browser context is an isolated browser session — like a separate incognito window. Each context has its own cookies, localStorage, and session. Multiple contexts can run in the same browser instance simultaneously. Used for multi-user testing, parallel login sessions, and independent state management.
What is the difference between page.click() and locator.click()?
page.click(selector) is the old API — a shorthand that finds the element and clicks it. page.locator(selector).click() is the modern approach — it creates a reusable Locator object with lazy evaluation. Locators are recommended because they support chaining, filtering, assertions, and auto-retry out of the box.
What is Auto-Waiting in Playwright?
Before performing any action (click, fill, hover…), Playwright automatically waits for the element to be visible, enabled, stable (no animation), and attached to the DOM. This eliminates the need for explicit waitForTimeout() calls in most cases and makes tests more reliable.
What are Soft Assertions? When would you use them?
expect.soft() assertions don't stop the test when they fail — they collect all failures and report them together at the end. Use them when you want to validate multiple UI elements (e.g., an entire form or a dashboard) in a single test run and see all failures at once, rather than stopping at the first one.
What is the Page Object Model (POM) and why is it used?
POM is a design pattern where each web page is represented as a class. The class contains the page's locators as properties and actions as methods. Benefits: avoids duplicate code, makes tests readable, isolates changes (if a selector changes, update only the Page class), and improves maintainability at scale.
How do you handle authentication in large test suites?
Use storageState — log in once in a globalSetup function, save the browser's cookies and localStorage to a JSON file (auth.json), and configure Playwright to apply it to all tests via use: { storageState: 'auth.json' }. This avoids repeating login in every test and dramatically speeds up suite execution.
What are Custom Fixtures and why are they useful?
Custom fixtures extend Playwright's built-in fixtures using test.extend(). They allow you to inject pre-configured objects (page objects, logged-in pages, test data) into any test automatically. This removes boilerplate setup code from test files and keeps tests focused on behavior, not setup.
What is Network Interception / Mocking?
page.route() intercepts outgoing network requests. You can: (1) mock — return a fake response with route.fulfill(), (2) modify — change headers before forwarding with route.continue(), or (3) abort — simulate network errors with route.abort(). Useful for testing error states, offline scenarios, and isolating the UI from backend.
What is the Trace Viewer?
The Playwright Trace Viewer is a GUI debugging tool that records every step of a test: DOM snapshots, screenshots, network calls, console logs, and action timeline. Enable it with trace: 'on-first-retry' in config. View it with npx playwright show-trace trace.zip. Invaluable for debugging CI failures.
What is the difference between waitForSelector and waitForURL?
waitForSelector() waits until a specific DOM element appears (or disappears). waitForURL() waits until the page navigates to a matching URL pattern. Use waitForURL after clicking a link/button that triggers navigation, and waitForSelector when waiting for dynamic content (modals, toasts, results) to appear.
How do you run tests in parallel in Playwright?
Set workers: N in config (or --workers=N CLI flag). By default, each spec file runs in a separate worker. Set fullyParallel: true to also parallelize tests within a file. Use storageState so each worker doesn't need to log in separately. Ensure tests don't share mutable state between workers.
What is the difference between fill() and type()?
fill() clears the input field first, then sets the value in one operation (fastest). type() simulates actual keystrokes character by character — useful when testing autocomplete, input masks, or event listeners that fire on each keypress. Prefer fill() for speed; use type() when keystroke events matter.
How do you handle dynamic elements or elements that load after an AJAX call?
Playwright's auto-wait handles most cases automatically. For explicit control: use expect(locator).toBeVisible() (assertion-based wait), waitForSelector('.result'), or waitForResponse('**/api/data') to wait for the network call that populates the element. Never use waitForTimeout() for this.
How do you integrate Playwright with CI/CD?
Playwright works headlessly out of the box. For GitHub Actions: checkout → setup Node → npm ci → npx playwright install --with-deps → npx playwright test → upload the playwright-report/ folder as an artifact. Store credentials in GitHub Secrets and reference via environment variables. Set retries: 2 in config to handle transient CI failures.
