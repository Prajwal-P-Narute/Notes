📄 Page Object Model + Custom Fixtures

🗂️ Page Object Model (POM)

  • POM = design pattern where each web page = one class that holds its locators + actions.
  • Tests never touch raw locators — they call methods on the page class.
  • When UI changes, update one class — not every test.
// pages/LoginPage.ts import { Page, Locator } from '@playwright/test'; export class LoginPage { private readonly page: Page; private readonly emailInput: Locator; private readonly passwordInput: Locator; private readonly loginBtn: Locator; constructor(page: Page) { this.page = page; this.emailInput = page.locator('#email'); this.passwordInput = page.locator('#password'); this.loginBtn = page.locator('button[type="submit"]'); } async login(email: string, pwd: string) { await this.emailInput.fill(email); await this.passwordInput.fill(pwd); await this.loginBtn.click(); } }

🔧 Custom Fixtures

  • Fixtures = reusable test setup/teardown logic — injected into tests automatically.
  • Built on Playwright's test.extend() API.
  • Replace repetitive beforeEach blocks — DRY principle at its best.
// fixtures/index.ts import { test as base } from '@playwright/test'; import { LoginPage } from './pages/LoginPage'; type Fixtures = { loginPage: LoginPage }; export const test = base.extend<Fixtures>({ loginPage: async ({ page }, use) => { const lp = new LoginPage(page); await use(lp); // inject into test }, });
📌 POM Benefits: Maintainability, Readability, No Duplication, Single Source of Truth for locators.
📌 Fixture Benefits: Auto setup/teardown, Type-safe injection, Scoped to test/file/project.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you structure an enterprise Playwright framework using POM and fixtures?

I use the Page Object Model to keep page locators and page-specific actions inside dedicated classes.

That means tests call readable methods instead of repeating selectors and UI steps everywhere.

For example, a LoginPage can expose a login method while keeping its email, password, and submit locators private.

I also use custom fixtures to create and inject reusable page objects or shared setup into tests.

This helps because setup and teardown stay consistent without repeating beforeEach logic in every test file.

When the UI changes, I update the relevant page object and keep most test scenarios untouched.

So, in short, POM organizes responsibilities, while fixtures manage reusable dependencies and lifecycle in a maintainable framework.

🔄 Also asked as: "How do you avoid duplicated locators and setup?" "How do POM and fixtures work together?"

🌐 API Automation + Test Data Management

🌐 API Automation in Playwright

  • Playwright's request fixture lets you make HTTP calls directly in tests.
  • Use API calls to set up test state faster than UI (create users, seed data, clean up).
  • Combine: API setup → UI test → API teardown = blazing fast + reliable.
// API call in Playwright test import { test, expect } from '@playwright/test'; test('create order via API then verify in UI', async ({ page, request }) => { // API: create order (fast!) const resp = await request.post('/api/orders', { data: { productId: 42, qty: 1 } }); expect(resp.status()).toBe(201); const { orderId } = await resp.json(); // UI: verify it appears await page.goto(`/orders/${orderId}`); await expect(page.locator('.order-status')) .toHaveText('Confirmed'); });

⚡ Parallel Execution

  • Playwright runs tests in parallel by default — each worker = isolated browser context.
  • Set workers in config → how many tests run simultaneously.
  • fullyParallel: true = individual tests (not just files) run in parallel.
  • Tests must be independent — parallel tests that share state WILL fail.
// playwright.config.ts — parallel config export default { fullyParallel: true, // tests inside file run parallel workers: process.env.CI ? 2 : 4, // fewer on CI (resource-limited) retries: process.env.CI ? 2 : 0, // retry flaky tests on CI only };
⚠️ Gotcha: If tests share a DB record (same user ID, same order), parallel runs will corrupt each other's data. Always use unique per-test data!

🔍 Playwright Trace Viewer

  • Trace = time-travel debugging — recorded zip of every action + DOM snapshot + network request.
  • Open with: npx playwright show-trace trace.zip
  • Shows: before/after DOM, console logs, network, screenshots per step.
  • Best debugging tool in Playwright — use 'on-first-retry' in CI so you only pay cost when a test actually flakes.
📌 CI Best Practice: screenshot & video = 'retain-on-failure' + trace = 'on-first-retry'. Don't record everything — storage cost explodes.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you investigate a Playwright test failure in CI?

I start with the error message and test report, then inspect the screenshot, video, or trace captured for the failure.

The Trace Viewer lets me review actions alongside DOM snapshots, network activity, and page state.

That matters because a screenshot shows one moment, while a trace helps reconstruct the sequence that led to failure.

In CI, I commonly keep screenshots and videos on failure and capture traces on the first retry.

Then I check whether the issue comes from an application defect, timing, test data, or environment differences.

After fixing it, I rerun the focused test and then the relevant suite to check for regressions.

So, in short, I use reports and trace evidence to identify the root cause instead of blindly increasing timeouts or retries.

🌿 Git + ⚙️ Jenkins / GitHub Actions

🌿 Git in a Test Framework

  • All test code lives in a Git repository — tracked, versioned, reviewed.
  • Use feature branches: one branch per feature/test suite addition.
  • PRs trigger automated test runs via CI pipeline.
  • Never commit .env files — use .gitignore + secrets management.
# .gitignore — what NOT to commit node_modules/ playwright-report/ test-results/ playwright/.auth/ # auth state files (contain tokens!) .env *.zip # trace files

⚙️ GitHub Actions — CI Pipeline

  • Trigger tests on: push to main, pull request, scheduled cron.
  • Each run: checkout → install → install browsers → run tests → upload artifacts.
# .github/workflows/playwright.yml name: Playwright Tests on: push: { branches: [main] } pull_request: { branches: [main] } jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: '20' } - run: npm ci - run: npx playwright install --with-deps - run: npx playwright test env: USER_EMAIL: ${{ secrets.USER_EMAIL }} USER_PASS: ${{ secrets.USER_PASS }} - uses: actions/upload-artifact@v4 if: always() with: name: playwright-report path: playwright-report/
📌 if: always() on the upload step = reports uploaded even when tests fail! ✅

⚙️ Jenkins Pipeline (Groovy)

// Jenkinsfile — declarative pipeline pipeline { agent any stages { stage('Install') { steps { sh 'npm ci' } } stage('Browsers') { steps { sh 'npx playwright install --with-deps' } } stage('Test') { steps { sh 'npx playwright test' } } } post { always { publishHTML(target: [reportDir: 'playwright-report']) } } }

🐳 Docker + ☁️ Cloud Execution

🐳 Docker — Why Use It?

  • "Works on my machine" problem → SOLVED. Docker gives every environment the same OS, Node version, and browser version.
  • Playwright has official Docker images with all browsers pre-installed.
  • CI agents run tests inside the container = zero browser install issues.
# Dockerfile — containerize your test suite FROM mcr.microsoft.com/playwright:v1.44.0-jammy WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . CMD ["npx", "playwright", "test"]
# docker-compose.yml — run with env vars version: '3.8' services: playwright: build: . environment: - USER_EMAIL=${USER_EMAIL} - USER_PASS=${USER_PASS} volumes: - ./playwright-report:/app/playwright-report
# Run tests in container docker compose up --build --exit-code-from playwright

🧱 SOLID Principles in Test Frameworks

🧱 SOLID — Applied to Automation

PrincipleStands ForIn Test Framework
S Single Responsibility Each page class handles ONE page. Each helper does ONE thing.
O Open/Closed Add new page objects without modifying existing ones. Extend, don't edit.
L Liskov Substitution A subclass page object must work wherever the parent is used.
I Interface Segregation Don't force a page class to implement methods it doesn't need.
D Dependency Inversion Depend on abstractions (interfaces) not concrete classes. Inject dependencies via fixtures.

🏗️ Framework Design Principles

🔁 Reusability

  • Login once → reuse via storageState
  • Page objects reused across all tests
  • Fixtures shared across suites

🛠️ Maintainability

  • Change locator in ONE place (POM)
  • Config centralized in playwright.config.ts
  • Test data in one /fixtures/ folder

🔒 Abstraction

  • Tests call loginPage.login() — not raw locators
  • API calls wrapped in service classes
  • Hides complexity from test authors

✂️ Separation of Concerns

  • Tests → test logic only
  • Page Objects → UI interactions
  • Fixtures → setup/teardown
  • Helpers → shared utilities

⚙️ Configuration Management

  • All config in playwright.config.ts
  • Env-specific via .env.staging, .env.prod
  • Secrets via CI/CD environment variables

📝 Logging

  • Log test actions for debugging
  • Use console.log or a logger like winston
  • Attach logs to Allure reports
⚠️ Exception Handling: Never let a helper function throw silently. Wrap API calls and file reads in try/catch. Custom error messages help debugging: throw new Error(`Login failed for ${email}`)
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you apply SOLID and design principles to a Playwright framework?

I apply SOLID principles to keep the framework understandable as the number of tests and contributors grows.

The key example is Single Responsibility, where each class or module should have one clear reason to change.

For instance, LoginPage handles login-related UI behavior rather than placing orders or owning unrelated test data.

I also prefer injecting page objects through fixtures instead of repeatedly constructing dependencies inside every test.

This improves reuse and testability while keeping test scenarios focused on business behavior.

I avoid oversized page objects, duplicated helpers, and abstractions that hide rather than simplify the test flow.

So, in short, good framework design separates responsibilities and dependencies so changes stay local, tests stay readable, and maintenance scales.

TIER 3 ⚠️ Common Mistakes & Gotchas ALWAYS READ

  • ⚠️ Shared test data in parallel tests → race conditions and random failures. Always use unique data per test.
  • ⚠️ Committing .env or auth JSON files to Git → security breach. Always .gitignore them.
  • ⚠️ Setting workers: 8 on CI → OOM kills. CI machines have fewer cores/RAM — use 2-4 max.
  • ⚠️ Not adding if: always() to upload-artifact step → reports disappear when tests fail. Miss the bug.
  • ⚠️ Hardcoding URLs/credentials in page objects → breaks across environments. Always use process.env.BASE_URL.
  • ⚠️ Putting all locators/logic IN the test file → defeats POM entirely. Locators belong in the Page class.
  • ⚠️ Using trace: 'on' always in CI → 10x storage cost. Use 'on-first-retry'.
