9. Browser Concepts

🧩 The object hierarchy every automation script is built on

📌 The three core objects

Browser → BrowserContext → Page. Each level is a container for the one below it — understanding this hierarchy explains almost everything about isolation and speed in automation.

  • Browser (one Chromium/Firefox/WebKit process)
    • BrowserContext #1 — isolated "profile"
      • Page (tab) 1
      • Page (tab) 2
    • BrowserContext #2 — separate cookies/storage
      • Page (tab) 1

Definitions

  • Browser — the actual launched browser process (chromium, firefox, webkit). Expensive to start, so it's usually launched once per test run.
  • BrowserContext — an isolated session inside a browser: its own cookies, storage, cache — like a fresh incognito profile. Cheap to create.
  • Page — a single tab inside a context. Most actions (click, goto) happen on a Page object.
  • Multiple contexts — spin up several contexts from one browser to simulate different logged-in users at the same time, fully isolated from each other.
  • Multiple pages — several tabs inside the same context; they share cookies/storage since they're in the same context.
  • Persistent context — a context tied to a real user-data directory on disk, so cookies/history/extensions survive between runs (like a normal Chrome profile, not incognito).
  • Incognito-like isolation — the default behaviour of a plain browser.newContext(): nothing is saved to disk, every context starts squeaky clean.
💡 Best practice: Launch one Browser, then create a new BrowserContext per test — this gives full isolation between tests without paying the cost of relaunching the browser itself.
📌 Browser = the engine.
Context = the profile.
Page = the tab.
🎤 🗣️ How I'd say it in an interview
❓ Interviewer asks: “What are Browser, BrowserContext, and Page in Playwright?”

Browser, BrowserContext, and Page are the three main objects in Playwright.

The Browser is the actual browser that runs our tests.

A BrowserContext is a separate session with its own cookies and storage.

A Page is one browser tab inside a context.

This matters because separate contexts keep users and tests isolated.

In my framework, I reuse the browser and create a new context for each test.

So, in short, I use separate contexts to keep tests independent without restarting the browser every time.

🔄 Also asked as: "How does Playwright keep tests isolated from each other?" · "Why not open a new browser for every test?"
Follow-up Qs: "What is the difference between a context and a page?" → "Contexts isolate sessions; pages are tabs inside a session." · "Can one context have multiple pages?" → "Yes, and those pages share the context storage."

10. Page Navigation

🧭 Moving the browser between URLs, reliably

📌 Navigation methods

Core navigation calls
MethodWhat it does
goto(url)Navigates to a URL and waits for load
goBack()Browser "back" button equivalent
goForward()Browser "forward" button equivalent
reload()Refreshes the current page
// Playwright — basic navigation await page.goto('https://example.com', { timeout: 30000 }); await page.goBack(); await page.goForward(); await page.reload({ waitUntil: 'networkidle' });

URL validation

After navigating, assert the browser actually landed where expected — don't just trust goto() resolved. Compare against page.url() or use a built-in URL assertion.

// assert the URL after navigation await expect(page).toHaveURL(/dashboard/);

Navigation timeout

Every navigation call has a default timeout (usually 30s) — if the page hasn't fired its load event by then, the call throws. Override per-call with a timeout option, or globally in config.

⚠️ Warning: A navigation timeout almost always means the app was slower than expected, a redirect loop happened, or a network call hung — don't just bump the timeout blindly, investigate first.
🎤 🗣️ How I'd say it in an interview
❓ Interviewer asks: “How do you navigate between pages and verify navigation in Playwright?”

I use goto() to open a URL and goBack(), goForward(), or reload() to navigate.

The important point is navigation waits for the selected page-load event or until it times out.

For example, I use page.goto() to open the application page.

After navigation, I check the URL with toHaveURL() to confirm I reached the right page.

If a page is slow, I set a suitable navigation timeout instead of adding a fixed sleep.

I do this because a URL check can catch an unexpected redirect or error page.

So, in short, I verify both navigation and the final URL so the test confirms the correct page opened.

🔄 Also asked as: "How does Playwright know a page finished loading?" · "What happens if navigation takes too long?"
Follow-up Qs: "How do you verify navigation?" → "I use `expect(page).toHaveURL(...)`." · "Should you always use `networkidle`?" → "No, I choose the wait condition that fits the application."

// common action patterns await page.locator('#submit').click(); await page.locator('#menu').click({ button: 'right' }); await page.locator('#src').dragTo(page.locator('#drop')); await page.locator('#search').fill('playwright'); await page.locator('#search').press('Enter');
💡 fill() vs type(): Use fill() for speed (sets the value directly) — use pressSequentially() ("type") only when the app has JS listeners that react to each individual keystroke (autocomplete, live validation).
⚠️ Warning: Elements must pass actionability checks (visible, enabled, stable, not obscured) before click()/fill() run — a hidden or animating element will cause the call to wait, then time out.
🎤 🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is the difference between `fill()` and `pressSequentially()` in Playwright?”

`fill()` is used to set the input value in one action.

I use it by default because it is simple and fast for most text fields.

`pressSequentially()` is used to type the text one character at a time.

I use it when the page needs real key presses, such as live search suggestions.

The key difference is fill() sets the value, while pressSequentially() sends key events.

I choose the method based on how the application responds to the input.

So, in short, I use fill() for normal inputs and sequential typing only when the UI needs key-by-key events.

🔄 Also asked as: "When is `fill()` not enough?" · "How do you simulate real typing?"
Follow-up Qs: "Which method is faster?" → "Usually `fill()`." · "When might sequential typing be needed?" → "For interfaces that react to individual key presses."

12. Form Handling

📝 Every input type, and the right way to drive it

Form control cheat sheet
ControlTypical call
Text boxlocator.fill('value')
Checkboxlocator.check() / .uncheck()
Radio buttonlocator.check() on the specific option
Dropdown (native)locator.selectOption('value')
Multi-selectselectOption(['a','b'])
File uploadlocator.setInputFiles('path')
Date pickerfill() if text input; else click calendar cells
Auto-completepressSequentially() + wait for suggestion, then click it
Search boxfill() + press('Enter')
// form handling patterns await page.locator('#agree').check(); await page.locator('#country').selectOption('IN'); await page.locator('#skills').selectOption(['js', 'ts']); await page.locator('#resume').setInputFiles('resume.pdf');

Date pickers & autocomplete — the tricky ones

Custom date pickers are usually not real <input> fields — you often can't just fill() them; you may need to click through calendar navigation and day cells. Autocomplete boxes need a real keystroke sequence to trigger the suggestion list, then an explicit click on the matching suggestion.

💡 Tip: For custom dropdowns built from <div>s (not native <select>), selectOption() won't work — click to open it, then click the visible option text.
⚠️ Warning: setInputFiles() works even on a hidden file input — no need to make it visible first, which is a common beginner trap.
🎤 🗣️ How I'd say it in an interview
❓ Interviewer asks: “How do you handle different form controls in Playwright?”

I choose the method based on the type of form control.

For checkboxes, I use check() or uncheck().

For native dropdowns, I use selectOption().

For file uploads, I use setInputFiles().

For custom controls, I interact with the visible options, such as clicking a date in a calendar.

I do this because custom widgets may not behave like normal HTML inputs.

So, in short, I use the Playwright method that matches the control instead of forcing every control through fill().

🔄 Also asked as: "How would you automate a date picker?" · "Why does `fill()` not work for every control?"
Follow-up Qs: "How do you upload a file?" → "I use `setInputFiles()`." · "How do you select a native dropdown option?" → "I use `selectOption()`."

⚠️ 4. Common Mistakes & Gotchas
  • ⚠️ Reusing one BrowserContext across tests — leaks cookies/login state between them.
  • ⚠️ Assuming goto() means the page is fully interactive — actionability is checked separately per action.
  • ⚠️ Using fill() on a custom autocomplete and wondering why no suggestions appear — it never fires real keystrokes.
  • ⚠️ Trying selectOption() on a div-based fake dropdown — it only works on native <select>.
  • ⚠️ Making a hidden file input visible before uploading — unnecessary, setInputFiles() works on hidden inputs.
  • ⚠️ Blindly increasing navigation timeout instead of investigating the real slow cause.
