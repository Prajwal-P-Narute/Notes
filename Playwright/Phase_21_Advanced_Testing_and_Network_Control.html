⚡ Phase 21 — Advanced Playwright Topics

After the fundamentals, these are the "pro-level" skills interviewers use to separate juniors from seniors: testing components in isolation, thinking about accessibility, controlling the network layer, handling multiple logged-in users at once, testing real-time apps, and debugging flaky CI failures.

72 · Component Testing

Component testing = mounting a single UI component (React/Vue/Svelte) in a real browser and testing it alone — not the whole app, no backend, no routing.

  • Component isolation — the component runs with mocked/controlled props and dependencies, so a failing test always points to that one component, not some unrelated page.
  • UI component validation — assert rendered output, event handlers, and prop-driven states (loading / error / empty) directly, faster than a full E2E page load.
  • Uses @playwright/experimental-ct-react / -vue / -svelte packages — a small dev-server mounts just the component.
📌 Why it matters: Component tests run much faster than full E2E and catch UI bugs earlier — but they don't replace E2E, since they never test real integration/navigation.
// mounting and testing a component in isolation import { test, expect } from '@playwright/experimental-ct-react'; import Button from './Button'; test('button click fires handler', async ({ mount }) => { const component = await mount(<Button label="Save" />); await component.click(); await expect(component).toHaveText('Saved!'); });

73 · Accessibility Locators

Playwright encourages locating elements the way a screen-reader user would — this makes tests resilient to CSS/class changes and improves app accessibility as a side effect.

  • ARIA roles — every interactive element has an implicit or explicit role (button, link, textbox, checkbox...). Locate with getByRole().
  • Accessible names — the visible/label text (or aria-label) exposed to assistive tech; used as the second argument to getByRole('button', { name: ... }).
  • Accessibility-first locator strategy — prefer role + name over CSS selectors or XPath, because it's stable and doubles as an a11y smoke check.
// role-based locator — resilient & accessibility-aware await page.getByRole('button', { name: 'Submit' }).click();

🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you use network interception in Playwright?

I use page.route() to intercept matching network requests and control how the browser receives responses.

This helps me test loading, error, and edge states without depending on a live or unreliable backend.

For example, I can use route.fulfill() to return a controlled 500 response and verify the error message.

When I need the real request to proceed, I use route.continue(), optionally changing headers or request data.

I keep it targeted by matching the relevant URL or request method and allowing unrelated requests to continue.

That makes tests more deterministic and lets me reproduce scenarios that are difficult to trigger on demand.

So, in short, page.route() gives me controlled network behavior so I can verify UI outcomes reliably without unnecessary external dependencies.

🔄 Also asked as: "How would you test an API failure in the UI?" "How do you mock a third-party service?"
Follow-up Qs:
  • What is the difference between `route.fulfill()` and `route.continue()`?
  • How would you simulate a slow response or timeout?
  • How do you ensure unrelated requests are not blocked?

74 · Advanced Network Control

Playwright can sit between the browser and the network — intercepting, inspecting, and rewriting every request/response with page.route().

Browser sends request
→
page.route() intercepts
→
condition? modify? mock?
→
route.fulfill() / continue()
  • Conditional interception — only intercept requests matching a URL pattern, method, or resource type; let everything else pass through.
  • Request modification — change headers, method, or POST body before it's sent (route.continue({...})).
  • Response modification — replace status, headers or body entirely (route.fulfill({...})) without ever hitting the real server.
  • Network simulation — force slow responses, timeouts, or offline states to test loading/error UI.
  • API dependency replacement — swap a flaky/3rd-party API for a fixed mock response so tests stay deterministic.
// mock an API response so the test never depends on a real backend await page.route('**/api/users', async route => { await route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify([{ id: 1, name: 'Mock User' }]), }); }); // only intercept a specific method, pass everything else through await page.route('**/api/orders', route => route.request().method() === 'POST' ? route.fulfill({ status: 500 }) : route.continue() );
⚠️ Remember: route.fulfill() ends the request — the real network call never fires. route.continue() lets it through, optionally modified.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you test a workflow involving multiple logged-in users?

I create a separate browser context for each user so every actor has independent cookies and storage.

For example, an admin, a regular user, and a manager can each use their own context and page.

This matters because sharing a context can leak authentication state and make one user's actions affect another session.

To save time, I can load role-specific storageState files instead of repeating the login flow.

Then I coordinate the pages according to the business workflow, such as creating a request and approving it.

I also clean up contexts and test data so the scenario does not leave state behind for later tests.

So, in short, separate contexts model separate users faithfully and keep multi-user tests isolated, repeatable, and easier to debug.

🔄 Also asked as: "How do you test admin and user interactions in one test?" "How do you prevent session leakage between users?"
Follow-up Qs:
  • What is the difference between a browser and a browser context?
  • How can you reuse authentication with `storageState`?
  • How would you clean up multiple contexts after a test?

75 · Multi-User Scenarios

Many real flows need more than one logged-in user at once — e.g. an admin creates a user, that user logs in, a manager approves something. Playwright's browser contexts make this easy: each context is an isolated "browser profile" (own cookies/storage).

// three independent, isolated authenticated sessions const adminCtx = await browser.newContext({ storageState: 'admin.json' }); const userCtx = await browser.newContext(); const managerCtx = await browser.newContext({ storageState: 'manager.json' }); const adminPage = await adminCtx.newPage(); const userPage = await userCtx.newPage();
💡 Each newContext() = a brand new "incognito" profile. Save/reuse login with storageState so you don't repeat the login flow per test.

76 · WebSocket Testing

For real-time apps (chat, live dashboards), Playwright can observe and even intercept the WebSocket layer, not just HTTP.

  • WebSocket connection — listen for a new socket via the page.on('websocket', ...) event.
  • WebSocket interception — inspect frames sent/received (ws.on('framesent' / 'framereceived')) to assert on real-time messages.
  • Real-time applications — useful for chat apps, stock tickers, collaborative editors — anywhere state updates push from server to client.
// observe websocket frames for a real-time feature page.on('websocket', ws => { console.log(`WS opened: ${ws.url()}`); ws.on('framereceived', event => console.log('received:', event.payload)); });

77 · Advanced Debugging

The hardest bugs are the ones that only show up in CI, not on your machine. These tools close that gap.

  • Trace analysis — record a full trace (DOM snapshots, network, console, screenshots per action) with trace: 'on' / retain-on-failure, then replay it visually with npx playwright show-trace.
  • Network debugging — inspect every request/response Playwright made, including timing and headers, straight from the trace viewer or page.on('request'/'response') listeners.
  • Console debugging — capture in-page console.log/errors via page.on('console', ...) to catch JS errors invisible in the terminal.
  • Browser logs — pageerror, crash and dialog events surface issues the app itself doesn't report cleanly.
  • CI-only failures — usually timing/race conditions, missing fonts, headless-vs-headed rendering diffs, or env/secrets differences; traces + video + screenshots-on-failure are the main weapons.
// enable full tracing + capture console errors await context.tracing.start({ screenshots: true, snapshots: true }); page.on('console', msg => { if (msg.type() === 'error') console.log('Page error:', msg.text()); }); // ...run the test... await context.tracing.stop({ path: 'trace.zip' });
// replay a trace visually npx playwright show-trace trace.zip
📌 CI-only failures checklist: fixed viewport size? disabled animations? enough retries? correct timezone/locale set? headless flag matching local repro?
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you debug a Playwright test that fails only in CI?

I start with the test report and captured evidence rather than guessing or immediately increasing timeouts.

I enable tracing and preserve screenshots or videos on failure to reconstruct what happened.

With Trace Viewer, I inspect action timing, DOM snapshots, network activity, and screenshots step by step.

I also capture browser console errors and page errors that may not appear clearly in the terminal.

Then I compare local and CI settings such as viewport, timezone, browser mode, fonts, environment variables, and test data.

After identifying the root cause, I fix the synchronization or environment issue and rerun the focused test and suite.

So, in short, I use trace evidence and controlled comparisons to diagnose CI-only failures instead of hiding them with arbitrary waits.

🔄 Also asked as: "Tell me about a flaky test you investigated." "What evidence do you collect when a pipeline test fails?"
Follow-up Qs:
  • What information does a Playwright trace contain?
  • Which trace and video settings are useful in CI?
  • How do you distinguish a timing issue from a product defect?

⚠️ Common Mistakes & Gotchas TIER 3ALWAYS READ

  • ⚠️ Forgetting route.continue() for non-matching requests — everything gets blocked if you only handle the matched case.
  • ⚠️ Sharing one context across "different users" — cookies leak between them; always use separate newContext() calls.
  • ⚠️ Using CSS class selectors instead of roles — brittle the moment a designer renames a class.
  • ⚠️ Not enabling retain-on-failure tracing in CI — you get a failure with zero evidence to debug from.
  • ⚠️ Assuming a WebSocket bug is an HTTP bug — check page.on('websocket') frames, not just network requests.
  • ⚠️ Treating component tests as a replacement for E2E — they never test real navigation/integration.

🧠 Memory Tricks & Last-Minute Tips TIER 3

🧠 fulfill = FAKE it (short-circuits, fake response). continue = CARRY on (real request continues).
🧠 Think of a browser context like a separate incognito window per actor — Admin, User, Manager each get their own.
🧠 "Trace" = a black box flight recorder for your test — always keep it on for CI.
