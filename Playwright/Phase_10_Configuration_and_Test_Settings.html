⚙️ Playwright Configuration

Phase 10 · playwright.config.tsPage 1

📌 What is playwright.config.ts?

It's the single source of truth for how your whole test suite behaves — where tests live, how long they wait, what browser/device to use, retries, reporting, etc.

Playwright reads this file automatically when you run npx playwright test — no need to import it anywhere.

🗂️ testDir

Tells Playwright where your spec files live — e.g. ./tests. Playwright scans this folder (and subfolders) for files matching the test pattern.

⏱️ timeout

Max time (ms) a single test is allowed to run before Playwright marks it as failed (timed out). Default is 30000ms (30s).

Don't confuse with actionTimeout or navigationTimeout — those limit individual actions/navigations inside a test, not the whole test.

✅ expect

Configures the default assertion timeout — how long expect(locator).toBeVisible() style assertions will keep retrying before failing. Default 5000ms.

// playwright.config.ts — top-level settings import { defineConfig } from '@playwright/test'; export default defineConfig({ testDir: './tests', timeout: 30000, expect: { timeout: 5000 }, });
💡 Tip: Keep timeout generous for flaky UI flows, but keep expect.timeout tighter — it should catch a real failure fast, not mask it.
⚙️
🗣️ How I'd say it in an interview
❓ Interviewer asks:What is playwright.config.ts, and what do you configure in it?

In simple terms, it is the central configuration file that controls how the Playwright test suite runs.

It matters because I can manage test locations, timeouts, browser settings, retries, and reports in one place.

For example, I use testDir to locate tests and timeout to set the maximum duration for a test.

I also configure expect.timeout separately because it controls how long an assertion retries.

In practice, I keep shared settings in the main config and override them only when a project needs different behavior.

So, in short, a clear config makes test execution consistent, maintainable, and easier to debug.

⚙️ The use{} Block

Phase 10 · playwright.config.tsPage 2

The use object holds default options applied to every test (unless a project overrides them). Think of it as the "global settings" bucket.

🌐 baseURL

Sets a root URL so tests can call page.goto('/login') instead of the full domain every time. Great for switching environments (see Page 4).

🔐 storageState

Lets you reuse a saved login session (cookies + localStorage) across tests, so you don't log in from scratch every run — huge speed win.

🔍 trace

Records a timeline of actions, DOM snapshots, network & console logs for a test — viewable in Trace Viewer for debugging failures.

trace option values
ValueMeaning
'on'Always record
'off'Never record
'retain-on-failure'Keep only for failed tests
'on-first-retry'Record only on the first retry attempt

🎥 video   📸 screenshot

video: records a screen recording of the test run — same value options as trace. screenshot: captures a still image, usually set to 'only-on-failure' to save disk space in CI.

// use{} block — shared defaults for every test export default defineConfig({ use: { baseURL: 'https://staging.myapp.com', storageState: 'auth/state.json', trace: 'retain-on-failure', video: 'retain-on-failure', screenshot: 'only-on-failure', }, });
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:What is the use{} block in Playwright, and how do you use baseURL?

The use block stores default browser and test options that apply to tests unless a project overrides them.

For baseURL, I set the root application URL so tests can navigate with relative paths such as page.goto('/login').

This helps because the same tests can target QA or staging without hardcoding a full URL in every test.

I also configure storageState to reuse a saved session and trace to help investigate failures.

For debugging, I often retain traces and videos on failure and screenshots only when a test fails.

So, in short, the use block centralizes reusable defaults and makes test runs easier to switch and troubleshoot.

🔄 Also asked as: "How do you avoid hardcoding URLs in your tests?" / "Which options do you commonly configure inside use?"
Follow-up Qs: Can baseURL be overridden per project? What does storageState preserve? When would you use Trace Viewer?

⚙️ Projects · Workers · Retries · Reporter

Phase 10 · playwright.config.tsPage 3

🧩 projects

Lets you run the same test suite across multiple browsers/devices/configs in one command — each project can have its own use overrides.

👷 workers

Number of parallel worker processes Playwright spins up to run test files simultaneously. More workers = faster suite, but more CPU/RAM.

🔁 retries

How many times a failed test is automatically re-run before being marked as truly failed — useful for taming flaky tests, especially in CI.

📊 reporter

Controls the output format of test results — e.g. 'list' for console, 'html' for a browsable report, 'json'/'junit' for CI integrations. You can use several at once.

// projects, workers, retries, reporter import { devices } from '@playwright/test'; export default defineConfig({ workers: 4, retries: process.env.CI ? 2 : 0, reporter: [['list'], ['html', { open: 'never' }]], projects: [ { name: 'chromium', use: { ...devices['Desktop Chrome'] } }, { name: 'firefox',  use: { ...devices['Desktop Firefox'] } }, { name: 'mobile',   use: { ...devices['iPhone 13'] } }, ], });
projects vs workers — don't mix these up
OptionControlsAnalogy
projectsWHAT to run against (browser/device/config)Different "lanes" of the same race
workersHOW MANY run at the same timeNumber of runners racing at once
📌 Real CI trick: set retries conditionally on process.env.CI — 0 locally (fail fast while debugging), 2 in CI (absorb network flakiness).
🧩
🗣️ How I'd say it in an interview
❓ Interviewer asks:What is the difference between projects, workers, retries, and reporters?

Projects define which browser, device, or configuration a test suite should run against.

Workers control how many worker processes run tests in parallel, depending on available CPU and memory.

Retries determine how many times Playwright reruns a failed test before reporting its final result.

Reporters control how test results are presented, such as in the terminal, an HTML report, JSON, or JUnit output.

In CI, I may enable retries conditionally and choose a worker count that suits the runner's resources.

So, in short, projects decide the test target, workers decide concurrency, retries handle reruns, and reporters present results.

🔄 Also asked as: "How do you configure cross-browser execution and parallel testing?" / "How do projects differ from workers?"
Follow-up Qs: Why might you use fewer workers in CI? Should retries replace investigating flaky tests? Can you configure multiple reporters?

🔑 Environment Variables & .env

Environment variables keep secrets (URLs, tokens, credentials) out of source code, and let the same test suite point at different environments without editing files.

A .env file stores these as key=value pairs locally; a package like dotenv loads them into process.env at runtime. Never commit .env to git — add it to .gitignore.

// .env.qa BASE_URL=https://qa.myapp.com API_KEY=qa-secret-123 // playwright.config.ts — reading env vars import 'dotenv/config'; export default defineConfig({ use: { baseURL: process.env.BASE_URL, }, });
Set ENV var → ENV=staging npx playwright test
↓
Config loads .env.staging via dotenv
↓
baseURL / API_KEY populated from that file
↓
Same test code runs unchanged against Staging

🗃️ Configuration Management — Best Practice

  • Keep one config file, drive differences via env vars — avoid duplicate config files per environment.
  • Store secrets in CI secret managers (GitHub Actions secrets, etc.), not in committed .env files.
  • Use naming convention .env.qa, .env.staging and load the right one based on an ENV variable.
🌍
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you manage environment configuration and secrets in Playwright?

My approach is to keep environment-specific URLs and credentials out of test code.

I use environment variables and, for local development, environment files loaded through a package such as dotenv.

For example, a BASE_URL variable can point the same test suite at QA or staging.

To protect secrets, I add local environment files to .gitignore and use CI secret storage for pipeline credentials.

Before running tests, I verify that the selected environment and required variables are set correctly.

So, in short, one configurable suite with safely managed environment values is easier to maintain and safer to run.

⚠️ Common Mistakes & Gotchas ALWAYS READ

  • ⚠️ Confusing timeout (whole test) with expect timeout (single assertion) — leads to wrong debugging.
  • ⚠️ Committing .env files with real secrets to git.
  • ⚠️ Setting workers too high on limited CI machines → flaky, resource-starved runs.
  • ⚠️ Forgetting retries masks real bugs if set too high — always investigate why a test needed a retry.
  • ⚠️ Not scoping storageState per role/environment → tests silently run as the wrong user.

🧠 Memory Tricks & Last-Minute Tips TIER 3

🧠 "T-U-P-W-R-R" → TestDir, Use, Projects, Workers, Retries, Reporter — the six pillars of config, in the order you'd usually configure them.
🧠 Think of use{} as the "default settings" and projects[] as "exceptions per browser" — projects always win over use.
  • Double-check .gitignore includes .env before every push.
  • Confirm baseURL matches the environment you intend to hit — a wrong URL silently tests the wrong env.
  • In CI, verify retries and workers are tuned for the runner's actual CPU/RAM.
  • Keep trace/video set to "retain-on-failure" in CI to save storage costs.
