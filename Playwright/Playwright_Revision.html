PHASE 01

Playwright Fundamentals

4 interview cards, copied from this phase file in source order.

PHASE 01 · QUESTION 01
❓ Interviewer asks: “What is Playwright, and why would you use it?”

Playwright is Microsoft's open-source browser automation tool, built for modern web testing.

The problem it solves is flaky, slow tests on dynamic web apps.

What makes it stand out is direct browser communication, with no HTTP middleman, so tests run faster.

It auto-waits for elements to be ready, so I never need sleep() calls.

I can test on Chrome, Firefox, and Safari with the same code.

Compared to Selenium, it's less flaky on dynamic pages and has network mocking built in.

So, in short, I choose Playwright for fast, reliable, cross-browser tests with less maintenance, which saves the whole team time.

🔄 Also asked as: "Why would you choose Playwright over Selenium?" · "What's your experience with browser automation tools?"
PHASE 01 · QUESTION 02
❓ Interviewer asks: “What is a BrowserContext in Playwright, and why does it matter?”

A BrowserContext is an isolated session inside a browser, like an incognito window.

It has its own cookies, local storage, and session state.

In Playwright, every test gets its own BrowserContext by default.

What that means is tests can't accidentally share login state or cached data.

So I never have to clear cookies manually between tests.

The way I remember it is Browser is the app, Context is the profile, and Page is a tab.

So, in short, built-in context isolation keeps every test independent, which makes the suite reliable and safe to run in parallel.

🔄 Also asked as: "How does Playwright ensure test isolation?" · "Difference between Browser, Context, and Page?"
PHASE 01 · QUESTION 03
❓ Interviewer asks: “What is playwright.config.ts , and what do you configure in it?”

The config file is playwright.config.ts , the central control panel for the whole test suite.

It decides the base URL, retries, workers, reporters, and which browsers run.

I set baseURL so tests use relative paths instead of hardcoded URLs.

On CI, I set retries: 2 to absorb network flakiness.

I fill the projects array so tests run on Chromium, Firefox, and WebKit.

That gives me cross-browser coverage without duplicating any code.

So, in short, one config file controls everything, so I can change environments and browsers without touching a single test.

🔄 Also asked as: "How do you configure Playwright?" · "How do you run tests on multiple browsers?"
PHASE 01 · QUESTION 04
❓ Interviewer asks: “What lifecycle hooks does Playwright provide, and when do you use each?”

Playwright has four lifecycle hooks: beforeEach , afterEach , beforeAll , and afterAll .

They handle setup and teardown, so tests stay clean and independent.

Before every test, I use beforeEach to navigate to the right page.

After every test, I use afterEach to capture a screenshot on failure.

For heavy setup, I use beforeAll , which runs once for the whole group.

For final cleanup, I use afterAll to release those resources.

So, in short, I keep repeated steps in hooks and heavy setup in beforeAll , so the suite stays fast, clean, and easy to maintain.

Locators & Selectors

PHASE 02 · QUESTION 01
❓ Interviewer asks: “What is a Locator in Playwright, and how is it different from a Selenium WebElement?”

A Playwright locator is a lazy recipe for finding elements on a page.

The problem it solves is stale elements and manual waits that older tools forced on us.

What that means is it does not touch the DOM when I create it, only when I act.

Before every action, it auto-waits until the element is visible, stable, and enabled.

Because it re-queries each time, it never goes stale like a Selenium WebElement .

In strict mode, if my locator matches more than one element, it throws an error.

So, in short, a locator finds elements when needed and handles waiting automatically, making tests more reliable without manual sleeps.

PHASE 02 · QUESTION 02
❓ Interviewer asks: “Which built-in locators does Playwright have, and which one do you prefer?”

Playwright has seven built-in locators that mirror how real users see a page.

The reason this matters is Because they usually work even when the HTML or CSS changes.

My first choice is getByRole , because it uses the ARIA role and accessible name.

For forms, I use getByLabel , and getByPlaceholder only when no label exists.

For text, images, and tooltips, I use getByText , getByAltText , and getByTitle .

When nothing semantic exists, I ask developers to add data-testid and use getByTestId .

So, in short, I prefer user-friendly locators because they make tests more stable and easier to maintain.

PHASE 02 · QUESTION 03
❓ Interviewer asks: “CSS vs XPath in Playwright: when do you use which?”

CSS selectors are my fallback when built-in locators can't pick out an element.

The reason is they are short, readable, and slightly faster than XPath.

I use XPath only when I must move up to a parent, which CSS can't do cleanly.

The problem with both is they depend on HTML structure, so refactors break them.

To avoid that, I stick with getByRole and getByLabel wherever I can.

I do this because user-facing locators describe intent, not the DOM layout.

So, in short, I prefer user-facing locators because they are more reliable and easier to maintain.

PHASE 02 · QUESTION 04
❓ Interviewer asks: “What is strict mode, and how do you handle multiple matching elements?”

Strict mode means Playwright throws an error if an action's locator matches more than one element.

The problem it prevents is silently clicking the wrong element.

To fix a strict mode error, I make the locator more specific, instead of adding .first() blindly.

For tables and lists, I use locator('tr').filter({hasText:'John'}) and scope another locator inside it.

When I really need one of many, I use nth() , which is zero-indexed.

To check many elements, I use toHaveCount() and allTextContents() .

So, in short, strict mode helps me avoid interacting with the wrong element.

A dynamic locator problem is when IDs, classes, or text change dynamically and break my locators.

For example, generated IDs like #comp-7x9kq4 may change between renders.

First, I avoid hardcoding dynamic IDs or class names.

Instead, I use getByRole() , getByLabel() , or stable data-testid attributes.

For partial matches, I use filter({ hasText: 'Order' }) or regular expressions like /Order #\d+/ .

I also ask developers to add stable test IDs when needed.

So, in short, I use stable locators to make my tests reliable and easy to maintain.

Browser, BrowserContext, and Page are the three main objects in Playwright.

The Browser is the actual browser that runs our tests.

A BrowserContext is a separate session with its own cookies and storage.

A Page is one browser tab inside a context.

This matters because separate contexts keep users and tests isolated.

I use goto() to open a URL and goBack() , goForward() , or reload() to navigate.

The important point is navigation waits for the selected page-load event or until it times out.

For example, I use page.goto() to open the application page.

After navigation, I check the URL with toHaveURL() to confirm I reached the right page.

If a page is slow, I set a suitable navigation timeout instead of adding a fixed sleep.

I do this because a URL check can catch an unexpected redirect or error page.

So, in short, I verify both navigation and the final URL so the test confirms the correct page opened.

❓ Interviewer asks: “What is the difference between `fill()` and `pressSequentially()` in Playwright?”

`fill()` is used to set the input value in one action.

I use it by default because it is simple and fast for most text fields.

`pressSequentially()` is used to type the text one character at a time.

I use it when the page needs real key presses, such as live search suggestions.

The key difference is fill() sets the value, while pressSequentially() sends key events.

I choose the method based on how the application responds to the input.

So, in short, I use fill() for normal inputs and sequential typing only when the UI needs key-by-key events.

Auto-Waiting & Assertions

3 interview cards, copied from this phase file in source order.

PHASE 04 · QUESTION 01
❓ Interviewer asks: “What is auto-waiting in Playwright, and how does it help?”

Auto-waiting means Playwright checks that an element is ready before performing an action.

For a click, it checks that the element is visible, stable, enabled, and able to receive events.

If the element is not ready, Playwright keeps retrying until it is ready or the timeout is reached.

This helps because the test does not act too early while the page is updating.

I usually rely on auto-waiting instead of adding fixed waits.

If it still fails, I investigate why the element never became ready.

So, in short, I rely on auto-waiting and fix the real cause of delays to keep tests reliable.

Follow-up Qs: "What happens when the timeout is reached?" → "Playwright throws a timeout error." · "Does auto-waiting apply to assertions?" → "Web-first assertions retry too."
PHASE 04 · QUESTION 02
❓ Interviewer asks: “What are web-first assertions in Playwright?”

Web-first assertions are checks that automatically retry until the expected result appears or times out.

For example, I use toBeVisible() to check visibility and toHaveText() to check text.

They are useful because page content may take time to update.

Instead of checking once, Playwright keeps checking the condition for the assertion timeout.

In my tests, I use expect() assertions to verify the page state.

I avoid fixed waits because the assertion can continue as soon as the expected condition is met.

So, in short, I use web-first assertions to verify the result reliably without adding unnecessary manual waits.

Follow-up Qs: "What is the default expect timeout?" → "Five seconds by default." · "What does `toHaveText()` check?" → "It checks that the locator has the expected text."
PHASE 04 · QUESTION 03
❓ Interviewer asks: “When do you use explicit waits in Playwright?”

I use explicit waits when I need to wait for something beyond a normal element action.

For example, I may wait for a URL change after login or a specific API response.

For URL changes, I use waitForURL() when the navigation is part of the flow.

For API calls, I use waitForResponse() when the test depends on that response.

I avoid fixed waits like waitForTimeout() because they can slow tests down.

Before adding a wait, I check whether Playwright already handles the timing automatically.

So, in short, I use explicit waits only for specific events that auto-waiting cannot cover.

Follow-up Qs: "Why is `waitForTimeout()` discouraged?" → "It waits for a fixed time even if the page is ready earlier." · "When do you use `waitForResponse()`?" → "When the test depends on a particular network response."

PHASE 05 · QUESTION 01
❓ Interviewer asks: “How do you handle JavaScript alerts and confirmation dialogs in Playwright?”

A JavaScript dialog is a browser popup such as an alert, confirm, or prompt, not a normal page element.

The problem is a locator cannot click or type into a browser dialog like it does with HTML.

Playwright lets me listen for the dialog event before the dialog is handled.

To handle it, I register a handler with page.on('dialog', ...) and call accept or dismiss.

For example, I accept a confirmation when the test should continue with a delete action.

I also remember that an unhandled dialog is automatically dismissed when no dialog listener is present.

So, in short, I handle dialogs explicitly so the test follows the intended user flow and never relies on accidental browser behavior.

❓ Interviewer asks: “How do you interact with elements inside an iframe in Playwright?”

An iframe is a separate document embedded inside the main page, so its elements are in their own frame.

The problem is a normal page locator does not automatically target elements inside that frame.

In Playwright, I use page.frameLocator() to locate the iframe and then find its child element.

For example, I chain a locator for the card number field after selecting the payment iframe.

For nested frames, I chain another frameLocator() for each frame level.

I prefer this because it keeps the frame targeting readable without manually switching back and forth.

So, in short, I target the correct frame first, which makes iframe tests clearer and less likely to interact with the wrong page.

❓ Interviewer asks: “How do you handle a new tab or popup opened by a click in Playwright?”

A new tab is a separate Playwright Page object within the same browser context.

The problem is the new page can open before the test starts waiting for it.

To avoid that, I wait for the page event and perform the click together with Promise.all() .

After the click, I use the returned page object to locate and interact with elements in the new tab.

For example, I use this pattern when a sign-in flow opens a separate OAuth window.

If needed, I bring the relevant page to the front or close the popup after assertions.

So, in short, I wait for the popup before triggering it, so the test reliably captures the correct page every time.

❓ Interviewer asks: “How does Playwright handle elements inside the Shadow DOM?”

The Shadow DOM is a component feature that keeps its internal markup separate from the surrounding page.

The reason this matters is ordinary selectors can be harder to use when elements live inside web components.

By default, Playwright can locate elements inside open shadow roots with its normal locator engine.

For example, I use a role or CSS locator for a control inside an open shadow root.

I also check whether the component uses a closed shadow root, which normal automation cannot pierce.

When a locator fails, I inspect the component and confirm whether the issue is the shadow root or the locator itself.

So, in short, I use Playwright's built-in Shadow DOM support first and verify component boundaries before adding brittle workarounds.

PHASE 06 · QUESTION 01
❓ Interviewer asks: “What are the main HTTP methods, and how do you use them in API testing?”

HTTP methods describe the action a client wants to perform on a resource.

GET is used to retrieve data, while POST commonly creates a new resource.

PUT usually replaces the full resource, while PATCH updates only selected fields.

DELETE is used to remove a resource when the API supports that operation.

In API tests, I check that the response status and body match the method's expected behavior.

For example, I usually expect a successful create to return a suitable status such as 201.

So, in short, I validate both the method's purpose and the response, so API tests check real behavior rather than status codes alone.

PHASE 06 · QUESTION 02
❓ Interviewer asks: “How do you make API requests directly in Playwright tests?”

Playwright's request fixture lets me send API requests directly without opening a browser page.

The reason this matters is I can validate backend behavior and prepare data quickly before UI tests run.

For authentication, I pass the required headers, and I use params for query-string values.

For request bodies, I send JSON data with the data option when the endpoint expects a body.

After the request, I assert the status code and read the response with response.json() .

I use this approach to create test data through an API when the UI setup would be slower.

So, in short, I use direct API requests for fast setup and focused checks, keeping UI tests about user-visible behavior.

PHASE 06 · QUESTION 03
❓ Interviewer asks: “What is API mocking in Playwright, and when would you use it?”

API mocking means intercepting a network request and returning a controlled response instead of calling the real backend.

The reason I use it is it lets me test UI behavior without depending on backend availability or changing data.

In Playwright, I intercept requests with page.route() and provide a response with route.fulfill() .

For example, I can return a 401 response to check how the UI handles an expired session.

I can also mock empty data, specific records, or an error response for edge cases.

I keep in mind that mocks test frontend behavior, so important backend behavior still needs real API coverage.

So, in short, I mock only the network behavior needed for a scenario, making UI tests repeatable without hiding backend defects.

Authentication & Session Management

PHASE 07 · QUESTION 01
❓ Interviewer asks: “How do you automate login and avoid logging in through the UI before every test?”

Login automation means using a test to sign in through the same steps a user would follow.

The problem is repeating the full login flow before every test makes a large suite slower and more fragile.

What I do is run a dedicated login step and save the authenticated browser state.

In Playwright, I reuse that saved state with storageState for tests that need the same user session.

I still keep separate login tests to verify that the sign-in flow itself works correctly.

I also make sure the saved state is refreshed when credentials or session tokens expire.

So, in short, I test login directly and reuse valid sessions elsewhere, improving speed without sacrificing coverage of authentication.

🔄 Also asked as: "How would you handle a test suite where 500 tests all need a logged-in user?"
PHASE 07 · QUESTION 02
❓ Interviewer asks: “What is storageState in Playwright, and why do you use it?”

The <code>storageState</code> option loads a saved snapshot of browser authentication state, including cookies and local storage.

The reason I use it is tests can start logged in instead of repeating the same UI login steps.

To create it, I sign in once and save the context state to a JSON file.

In my test setup, I provide that file as the storage state for tests using that account.

For multiple roles, I keep separate state files so each test uses the correct user's permissions.

I also protect these files because they can contain session information that grants access to an account.

So, in short, I reuse secure, role-specific session snapshots to make tests faster while keeping authentication setup controlled.

🔄 Also asked as: "How do you speed up a suite where every test needs a logged-in user?"
PHASE 07 · QUESTION 03
❓ Interviewer asks: “What is the difference between cookies and local storage?”

Cookies and local storage both store browser-side data, but they behave differently when an application makes requests.

Cookies are often sent automatically with matching HTTP requests, depending on their domain and security settings.

Local storage is kept in the browser and is not automatically attached to HTTP requests.

For example, I check whether an application uses cookies or a client-side token when investigating session behavior.

When I use <code>storageState</code>, I remember that Playwright can capture cookies and supported local-storage data.

I also consider security flags and token handling instead of assuming every app stores authentication the same way.

So, in short, I choose tests based on how the application really manages sessions, rather than treating cookies and local storage as interchangeable.

PHASE 08 · QUESTION 01
❓ Interviewer asks: “What is the Page Object Model, and how does it make an automation framework easier to maintain?”

POM is a design pattern where I keep each page's locators and actions inside a dedicated class.

The problem is UI changes can break many tests when locators are copied across test files.

With POM, I define locators once and expose reusable methods such as login() .

For example, my test calls loginPage.login(user, pass) without knowing the underlying locator details.

When the UI changes, I update the relevant page class instead of editing every test.

I also keep business methods focused on user actions and avoid oversized page classes.

So, in short, I use POM to separate test intent from UI details, making changes safer and the suite easier to maintain.

🔄 Also asked as: “How do you keep your test suite maintainable?” · “How do you manage UI changes that break tests?”
PHASE 08 · QUESTION 02
❓ Interviewer asks: “What is data-driven testing, and how would you implement it in Playwright?”

Data-driven testing is running the same test logic with multiple input sets instead of duplicating test scripts.

The reason this matters is one flow may need valid, invalid, boundary, and other input combinations.

Common data sources are JSON , CSV , and Excel, chosen according to the team's needs.

For data, I keep inputs outside the test logic so cases are easier to review and update.

In Playwright, I can loop through the data and define a separate test for each case.

I also check expected outcomes for each row and keep environment-specific data separate when needed.

So, in short, I separate test data from test logic to reduce duplication and make coverage easier to extend reliably.

❓ Interviewer asks: “❓ Interviewer asks: What is the difference between launch(), connect(), and connectOverCDP()?”

launch() starts a new local browser process controlled by Playwright.

connect() attaches to a remote Playwright browser server through a WebSocket using the Playwright protocol.

connectOverCDP() attaches to an existing Chromium-based browser through the Chrome DevTools Protocol.

I also manage cleanup carefully, because closing a remote cloud session can end the billed session, while CDP attachment behavior differs.

So, in short, launch starts locally, connect attaches through the Playwright protocol, and connectOverCDP attaches to Chromium through CDP.

❓ Interviewer asks: “❓ Interviewer asks: How do workers, projects, shards, and cloud concurrency differ?”

I also keep tests independent so parallel execution does not introduce shared-state or test-data collisions.

So, in short, workers parallelize on a runner, projects vary configurations, shards distribute work across machines, and concurrency limits remote sessions.

PHASE 21 · QUESTION 01
❓ Interviewer asks: “❓ Interviewer asks: How do you use network interception in Playwright?”

I use page.route() to intercept matching network requests and control how the browser receives responses.

This helps me test loading, error, and edge states without depending on a live or unreliable backend.

For example, I can use route.fulfill() to return a controlled 500 response and verify the error message.

I keep it targeted by matching the relevant URL or request method and allowing unrelated requests to continue.

That makes tests more deterministic and lets me reproduce scenarios that are difficult to trigger on demand.

So, in short, page.route() gives me controlled network behavior so I can verify UI outcomes reliably without unnecessary external dependencies.
