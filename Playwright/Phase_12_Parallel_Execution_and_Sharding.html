🎭 Playwright — Parallel Execution

Phase 12 · Workers & Parallel Tests

📌 What is Parallel Testing?

Parallel testing means running multiple test files at the same time, using several worker processes, so the whole suite finishes in a fraction of the time.

Playwright's test runner (@playwright/test) is built for this from the ground up — parallelism is on by default across test files.

Test Suite
→
Split into files
→
Assigned to Workers
→
Run in parallel
→
Results merged

👷 Workers

A Worker is an isolated OS process that runs test files. Each worker owns its own browser instance and its own memory — nothing is shared between workers.

  • By default, each test file is handed to one worker (a file itself doesn't auto-split across workers).
  • Local machine → uses roughly half the CPU cores by default. On CI → often set explicitly (CI runners are smaller).
  • More workers = more parallel files running = faster suite, up to the point your machine/CI runner runs out of CPU or memory.
// playwright.config.ts import { defineConfig } from '@playwright/test'; export default defineConfig({ workers: process.env.CI ? 2 : undefined, // undefined = auto (50% of cores) fullyParallel: true, });
💡 Tip: Run npx playwright test --workers=4 to override the config from the CLI — handy for quick local tuning without editing files.
⚠️ Note: Setting workers: 1 disables parallelism entirely. Great for debugging a flaky, order-dependent failure — bad for everyday runs (much slower).

⚡ Parallel Tests (within a file)

By default, tests inside the same file run one after another in the same worker. To make tests within a file also run in parallel (across extra workers), turn on fullyParallel.

// force one describe block to run its tests in parallel test.describe.configure({ mode: 'parallel' }); test('adds item to cart', async ({ page }) => { /* ... */ }); test('applies coupon', async ({ page }) => { /* ... */ });
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: How does Playwright run tests in parallel, and what are workers?

At a high level, parallel testing runs independent tests at the same time to reduce the overall suite duration.

In Playwright, worker processes execute test files, and each worker has its own browser instance and memory.

By default, parallelism is enabled across files, while tests within a file normally run sequentially.

When tuning workers, I consider CPU, memory, application capacity, and the limits of the CI runner.

For example, I might use fewer workers in CI than locally to keep execution stable.

If needed, I can override the worker count with the --workers command-line option.

So, in short, I choose worker settings to balance execution speed, resource usage, and test reliability.

🎭 Serial Tests & Isolation

Phase 12 · Test Isolation · Worker-level Fixtures

🔗 Serial Tests

Serial mode forces a group of tests to run in order, inside the same worker — if one test fails, the rest of that group is skipped.

  • Use only when steps truly depend on each other (e.g. a multi-page checkout flow that builds on state left by the previous step).
  • Serial tests cannot be spread across workers, so they don't benefit from parallelism.
test.describe.serial('checkout flow', () => { test('add product', async ({ page }) => { /* ... */ }); test('go to cart', async ({ page }) => { /* ... */ }); test('pay', async ({ page }) => { /* ... */ }); });
⚠️ Warning: Serial blocks make your suite slower and hide independent failures — prefer independent tests wherever possible; reach for serial only as a last resort.

🧪 Test Isolation

Every test gets a brand-new browser context — its own cookies, storage, and cache — like opening a fresh incognito window per test.

Test 1
→

(fresh cookies)
Test 2
→
Context B
(fresh cookies)

Because contexts never leak into each other, test order stops mattering — which is exactly what safe parallel execution requires.

🏭 Worker-level Fixtures

A fixture scoped to 'worker' is created once per worker and then reused by every test that worker runs — instead of being rebuilt per test.

  • test-scope fixture — new instance for every single test (default)
    • e.g. a fresh page
  • worker-scope fixture — one instance shared by all tests in that worker
    • e.g. an auth token, a DB connection pool
export const test = base.extend({ apiToken: [async ({}, use) => { const token = await loginOnce(); await use(token); }, { scope: 'worker' }], });
💡 Tip: Worker fixtures are perfect for expensive, read-only setup (login once, seed reference data) — never store mutable per-test data in one, or tests in that worker will interfere with each other.

🎭 Shared State & Race Conditions

Phase 12 · Parallel Testing (continued)

🚫 Avoiding Shared State

Shared state is any data — files, DB rows, global variables — that more than one test touches. In parallel runs, that's dangerous: two tests can collide mid-write.

Best practices

  • Generate unique test data per test (random emails, IDs) instead of reusing one fixed record.
  • Give each worker its own DB schema / table prefix when the suite hits a real database.
  • Never write to a shared fixed filename — use a path derived from the worker or test.
  • Never rely on tests running in a particular order to "prepare" state for a later test.
⚠️ Warning: Don't store data in a plain module-level JS variable expecting it to persist correctly — each worker is a separate OS process with its own memory, so that variable is not actually shared the way you'd think.

🏁 Race Conditions

A race condition happens when two tests (or two workers) touch the same resource at the same time, and the outcome depends on timing — a classic source of flaky, hard-to-reproduce failures.

  • Two tests writing to the same database row at once.
  • Two tests uploading a file to the exact same fixed filename.
  • A global counter incremented from multiple workers without any locking.
// safe: build a unique id from worker index + timestamp test('create user', async ({ page }, testInfo) => { const email = `user_${testInfo.workerIndex}_${Date.now()}@test.com`; await registerUser(page, email); });
💡 Tip: Use testInfo.workerIndex and testInfo.parallelIndex to build guaranteed-unique identifiers safely, instead of hand-rolled random numbers that could theoretically collide.
Do two tests touch the SAME resource?

Yes → give each its own copy/ID   |   No → safe to parallelize

🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you prevent race conditions in parallel tests?

A race condition, happens when tests access the same resource concurrently and the result depends on timing.

For example, two tests might update the same database row or upload to the same filename.

To prevent this, I generate unique test data such as a separate email address or record ID per test.

When using workers, I can include testInfo.workerIndex or testInfo.parallelIndex in identifiers.

I also avoid, relying on execution order or mutable data shared between tests.

For expensive setup, I reserve worker-scoped fixtures for resources that can safely be reused within that worker.

So, in short, reliable parallel tests isolate mutable state and give each test ownership of its data.

🎭 Sharding & Distributed Runs

Phase 12 · Sharding · Large Regression Suites

🧩 Test Sharding

Sharding splits the ENTIRE test suite across multiple MACHINES — not just processes on one machine — so huge suites finish in minutes instead of hours.

Workers vs. Shards
AspectWorkersShards
ScopeProcesses on one machineRuns across multiple machines
Configured viaworkers in config / CLI--shard=i/n CLI flag
Typical useEveryday local & CI parallelismVery large suites, CI job matrix
ReportingSingle reportNeeds merging (e.g. blob reports)
// machine 1 npx playwright test --shard=1/4 // machine 2 npx playwright test --shard=2/4 // ...and so on, up to 4/4 — each machine owns one slice of the suite

🌐 Distributed Execution (CI matrix)

CI systems commonly run each shard as its own job, using a matrix strategy — every job gets a different shard index automatically.

# GitHub Actions — simplified strategy: matrix: shardIndex: [1, 2, 3, 4] shardTotal: [4] steps: - run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}

Afterward, blob reports from every shard are merged back into one HTML report:

npx playwright merge-reports --reporter=html ./all-blob-reports

📈 Large Regression Suites

  • Reach for sharding once a suite has hundreds-to-thousands of tests and a single CI runner can't finish it inside your time budget.
  • Sharding and workers combine: each shard-machine also runs its own set of workers internally — that's parallelism on two levels.
  • More shards = faster wall-clock time, but more CI runner cost — it's a speed-vs-cost tradeoff, not a free lunch.
📌 Mnemonic:
Workers split work within a machine.
Shards split work across machines.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: What is test sharding, and how is it different from workers?

Sharding, divides the full test suite into separate portions that can run on different machines or CI jobs.

Workers, by contrast, split execution into processes on a single machine.

I use workers, for routine parallel execution when one runner has enough capacity.

I consider sharding, when a large regression suite cannot finish within the available CI time budget.

In CI, each matrix job can run a different shard using the --shard option.

Each shard can also, use its own workers, combining machine-level and process-level parallelism.

After execution, I merge the shard reports so the team can review one consolidated result.

So, in short, workers scale within a machine, while sharding distributes the suite across machines.

⚠️ Common Mistakes & Gotchas

  • ⚠️ Assuming a module-level JS variable is shared across workers — it isn't, each worker is a separate process.
  • ⚠️ Overusing describe.serial "just to be safe," quietly killing your parallelism.
  • ⚠️ Two tests writing to the same fixed filename or DB row — a textbook race condition.
  • ⚠️ Forgetting that workers: 1 is meant for debugging only, and leaving it that way in CI.
  • ⚠️ Putting mutable data inside a worker-scoped fixture, so tests in that worker corrupt each other's state.
  • ⚠️ Confusing workers (one machine) with shards (many machines) — they solve different scaling problems.
  • ⚠️ Forgetting to merge shard reports, ending up with 4 separate incomplete reports instead of one.

🧠 Memory Tricks & Last-Minute Tips

🧠 "Workers split inside a machine, Shards split across machines."
🧠 Serial = a train (one track, in order). Parallel = many lanes on a highway.
🧠 Test isolation = "a new incognito window" for every single test.
  • Double-check fullyParallel is actually set if you expect within-file parallelism.
  • Before blaming Playwright for a flaky test, check for shared data/race conditions first.
  • Know the one-line difference: --workers vs --shard — interviewers love this contrast.
  • Remember shards need a report-merge step — mention it, it shows real CI experience.
