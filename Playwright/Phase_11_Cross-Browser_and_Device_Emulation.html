📌 36. Browser Projects — Big Picture

Playwright can run the same test suite against multiple browser engines by defining projects in playwright.config.ts. Each project = one engine + one configuration.

The three real rendering engines Playwright drives are: Chromium (Chrome/Edge), Firefox, and WebKit (Safari). This gives real cross-browser coverage — not just one browser pretending to be another.

One Test File
→
Chromium Project
→
Firefox Project
→
WebKit Project

Same spec runs 3× — once per engine — in parallel by default.

🔧 Defining projects in config

// playwright.config.ts — register 3 browser engines as projects

import { defineConfig, devices } from '@playwright/test'; export default defineConfig({ projects: [ { name: 'chromium', use: { ...devices['Desktop Chrome'] } }, { name: 'firefox', use: { ...devices['Desktop Firefox'] } }, { name: 'webkit', use: { ...devices['Desktop Safari'] } }, ], });

Run only one project: npx playwright test --project=webkit. Run all: just npx playwright test (all projects execute, usually in parallel workers).

🧩 Meet the 3 Engines

Playwright's three browser engines compared
EngineReal browser it maps toNotes
ChromiumGoogle Chrome, Microsoft EdgeFastest, most stable, best debugging tools
FirefoxMozilla Firefox (Gecko)Different JS engine (SpiderMonkey) — catches Chromium-only bugs
WebKitApple SafariClosest thing to testing Safari on Linux/Windows CI

📱 Mobile Browser Projects

Playwright ships built-in devices presets that combine an engine + viewport + touch + user-agent, so a "mobile browser project" is really Chromium/WebKit + a device profile (there's no separate mobile-only engine).

// mobile browser projects using built-in device presets

projects: [ { name: 'Mobile Chrome', use: { ...devices['Pixel 7'] } }, { name: 'Mobile Safari', use: { ...devices['iPhone 14'] } }, ]

devices['Pixel 7'] runs on the Chromium engine; devices['iPhone 14'] runs on the WebKit engine — Playwright picks the matching engine automatically from the preset.

📌 NoteProject name is just a label — it's what you'll see in the HTML report and pass to --project. Give it a meaningful name!
⚠️ Don't assume "mobile testing" = real device behaviour. Playwright emulates viewport/touch/UA — it's not a real phone GPU/OS. For true device coverage, pair with a device-farm/cloud grid.
🌐
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you configure cross-browser testing in Playwright?

In Playwright, I use named projects to run the same test suite against different browser engines.

The main engines are Chromium, Firefox, and WebKit, which cover Chrome/Edge, Firefox, and Safari-like rendering respectively.

This matters because each engine can render layouts or execute browser features differently, so one browser alone may miss defects.

In the config, I define a project for each engine and give each project a clear name.

When needed, I can run one project with npx playwright test --project=webkit or run all configured projects together.

So, in short, projects let me reuse one test suite for broader browser coverage without maintaining duplicate tests.

📱 Device Emulation — Part 1

Phase 11 · Page 2 of 537. Device Emulation

Device emulation = telling the browser context to behave like a specific real device — viewport size, pixel density, touch support, and identity string — without needing the actual hardware.

📱 Mobile Devices (built-in presets)

Playwright bundles ~100+ presets in the devices object (from @playwright/test), each pre-filled with viewport, UA, deviceScaleFactor, isMobile and hasTouch.

// spread a full device preset into the browser context

import { test, devices } from '@playwright/test'; test.use({ ...devices['iPhone 14 Pro'] }); test('mobile nav opens', async ({ page }) => { await page.goto('https://example.com'); await page.click('.hamburger-menu'); });

📐 Screen Size / Viewport

Set manually with viewport: { width, height } when you need a custom size instead of a preset.

// custom viewport — e.g. testing a specific tablet breakpoint

test.use({ viewport: { width: 1024, height: 768 }, });

Or change it mid-test: await page.setViewportSize({ width: 375, height: 667 }) — useful for a single test that checks a resize/responsive breakpoint without a new project.

🕵️ User Agent

The userAgent string is what the site's JS reads to detect "what browser/device is this?" Overriding it lets you simulate a device's identity even on a desktop engine.

// override the User-Agent header manually

test.use({ userAgent: 'Mozilla/5.0 (Linux; Android 13; Pixel 7) ...', });
💡 Tip: Prefer a full devices[...] preset over hand-writing a UA string — presets keep UA, viewport, and touch flags consistent with each other.

🔍 Device Scale Factor (DSF)

DSF = pixel density ratio (CSS pixels → physical pixels). A standard monitor is 1; a Retina/high-DPI phone screen is typically 2 or 3.

// simulate a high-density Retina-style screen

test.use({ viewport: { width: 390, height: 844 }, deviceScaleFactor: 3, });

Matters for: screenshot comparison tests (sharper images at higher DSF) and any layout that uses image-set()/responsive images keyed to pixel density.

✅ Quick recallViewport = size in CSS px · DSF = sharpness/density multiplier · UA = "who am I" string the site reads.
⚠️ Setting viewport alone does not make a desktop engine behave like touch/mobile — you must also set isMobile: true and hasTouch: true (or just use a preset) or tap/touch events won't fire correctly.

🌍 Device Emulation — Part 2

Phase 11 · Page 3 of 537. Device Emulation (contd.)

📍 Geolocation

Fakes GPS coordinates so location-aware features (maps, "stores near me," delivery zones) can be tested deterministically — without moving your test runner around the planet.

// grant permission + set a fake location (Mumbai coords)

test.use({ geolocation: { latitude: 19.0760, longitude: 72.8777 }, permissions: ['geolocation'], });
⚠️ If you set geolocation but forget permissions: ['geolocation'], the browser silently blocks the location and the page sees nothing — a very common gotcha.

🔐 Permissions

Pre-grants browser permission prompts (camera, mic, notifications, geolocation, clipboard) so tests don't stall on a real popup dialog.

// grant multiple permissions at context level

const context = await browser.newContext({ permissions: ['camera', 'microphone', 'notifications'], }); await context.grantPermissions(['clipboard-read']); // revoke any time: await context.clearPermissions();

🕑 Timezone

Overrides the browser's reported timezone — vital for testing date/time-sensitive UI (booking slots, "posted 2 hours ago," scheduling) consistently regardless of the CI server's real timezone.

// force a specific IANA timezone

test.use({ timezoneId: 'Asia/Kolkata' });

🗣️ Locale

Sets the browser's Accept-Language header and navigator.language — drives which language/number/date format the site renders, for locale-specific UI tests.

// simulate a French (France) browser

test.use({ locale: 'fr-FR' });

🧩 Combining everything for one realistic profile

// full emulated profile: device + geo + permissions + locale + timezone

test.use({ ...devices['iPhone 14'], geolocation: { latitude: 48.8566, longitude: 2.3522 }, permissions: ['geolocation'], locale: 'fr-FR', timezoneId: 'Europe/Paris', });

🗣️ How I'd say it in an interview
❓ Interviewer asks:What is device emulation in Playwright, and which settings can you emulate?

Device emulation means configuring a browser context to mimic device characteristics without requiring the physical device.

A device preset can bundle viewport size, user agent, device scale factor, mobile behavior, and touch support.

For location-aware tests, I can set geolocation and grant permissions: ['geolocation'] so the page can access it.

For regional behavior, I can set locale and timezoneId to test language and date/time presentation consistently.

My preference is to start with a built-in devices preset and add only the extra settings the test needs.

So, in short, device emulation makes mobile and regional scenarios repeatable, but it does not replace testing on real hardware.

📏 Responsive Testing & Browser Quirks

Phase 11 · Page 4 of 538. Responsive Testing

📐 Desktop / Tablet / Mobile Breakpoints

Responsive testing = re-running the same functional checks at different viewport widths to confirm layout, navigation, and touch targets adapt correctly.

Common breakpoint ranges used in test projects
CategoryTypical widthWhat to check
🖥️ Desktop1280px – 1920pxFull nav bar, multi-column layout, hover states
📟 Tablet768px – 1024pxCollapsed/condensed nav, 2-column grids, touch + mouse both possible
📱 Mobile360px – 428pxHamburger menu, single column, tap targets ≥ 44px, no hover-only UI

// parametrised responsive test across 3 breakpoints

const breakpoints = [ { name: 'desktop', width: 1440, height: 900 }, { name: 'tablet', width: 834, height: 1112 }, { name: 'mobile', width: 390, height: 844 }, ]; for (const bp of breakpoints) { test(`nav is usable at ${bp.name}`, async ({ page }) => { await page.setViewportSize({ width: bp.width, height: bp.height }); await page.goto('https://example.com'); await expect(page.locator('nav')).toBeVisible(); }); }

🧬 Browser-Specific Behaviour

Even with identical HTML/CSS/JS, engines can render or execute things slightly differently — this is exactly what cross-browser + responsive testing is meant to surface.

Known engine-specific quirks to watch for
AreaTypical quirk
Form controlsNative <select>/date pickers render differently per engine — screenshot diffs can false-fail
ScrollbarsWebKit/Firefox reserve scrollbar width differently, shifting layout by a few px
Font renderingSub-pixel anti-aliasing differs — never pixel-diff text-heavy areas across engines
Flexbox/Grid edge casesRare gap/wrap differences in older Firefox/WebKit versions
TimingAnimation/transition callback timing can vary — avoid hard-coded waits
💡 Best practice: Assert on behaviour (element visible, text present, state changed) rather than pixel-perfect screenshots when running across all 3 engines — reserve visual-diff tests for a single baseline engine (usually Chromium).
⚠️ Don't run every test on every device × every browser — combinatorial explosion. Pick a critical-path subset (login, checkout, nav) for full cross-browser × responsive coverage; run the rest on one baseline engine.
📐
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you test responsive layouts and handle browser-specific differences?

Responsive testing checks whether the same page remains usable at different viewport widths, such as desktop, tablet, and mobile.

In practice, I test important navigation and page behavior at representative breakpoints instead of duplicating every test for every width.

For example, I verify that a desktop navigation bar changes to a working hamburger menu on a narrow screen.

Across browser engines, I focus assertions on behavior because fonts, scrollbars, and native controls can render differently.

To control test cost, I run critical paths across browsers and devices, while keeping the broader suite on a baseline engine.

So, in short, I combine representative viewport coverage with behavior-based assertions to catch real issues without creating noisy failures.

🔄 Also asked as: "How do you validate a mobile-first redesign?" / "What is the difference between responsive and cross-browser testing?"

⚠️ 4. Common Mistakes & Gotchas ALWAYS READ

  • ⚠️ Setting geolocation without granting the geolocation permission — location silently fails.
  • ⚠️ Manually setting viewport without isMobile/hasTouch — touch/tap gestures won't behave like mobile.
  • ⚠️ Pixel-diffing screenshots across all 3 engines — font/scrollbar rendering differs, causing false failures.
  • ⚠️ Running the full suite on every device × every browser — huge CI time for little extra signal; scope it to critical paths.
  • ⚠️ Forgetting a device preset already sets UA + touch + DSF together — don't fight it by re-setting only one field.
  • ⚠️ Assuming WebKit-on-Linux == real Safari-on-Mac in every detail — it's close, not identical.
