🔔 16. Alerts & Dialogs

Browsers pause JS execution when a native dialog (alert / confirm / prompt) pops up. Playwright can't click these with normal locators — they aren't part of the DOM. Instead you listen for the dialog event on the page.

Types of dialogs

  • alert — just a message + OK button.
  • confirm — message + OK/Cancel, returns true/false.
  • prompt — message + text input + OK/Cancel.
  • beforeunload — fired when leaving a page with unsaved changes.
⚠️ Gotcha: If you don't attach a dialog listener, Playwright auto-dismisses the dialog by default — your test won't hang, but you also won't get the message text.
Dialog object — key methods
MethodWhat it does
dialog.accept()Clicks OK (optionally pass text for prompts)
dialog.dismiss()Clicks Cancel / closes it
dialog.message()Returns the dialog's text
dialog.type()alert / confirm / prompt / beforeunload
// Accept an alert and read its text page.on('dialog', async (dialog) => { console.log(dialog.message()); await dialog.accept(); }); await page.click('#showAlertBtn'); // Handling a prompt with input text page.once('dialog', dialog => dialog.accept('John'));
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “How do you handle JavaScript alerts and confirmation dialogs in Playwright?”

A JavaScript dialog is a browser popup such as an alert, confirm, or prompt, not a normal page element.

The problem is a locator cannot click or type into a browser dialog like it does with HTML.

Playwright lets me listen for the dialog event before the dialog is handled.

To handle it, I register a handler with page.on('dialog', ...) and call accept or dismiss.

For example, I accept a confirmation when the test should continue with a delete action.

I also remember that an unhandled dialog is automatically dismissed when no dialog listener is present.

So, in short, I handle dialogs explicitly so the test follows the intended user flow and never relies on accidental browser behavior.

🔄 Also asked as: "How do you deal with popups Selenium's switchTo().alert() normally handles?" / "What happens if a confirm box pops up mid-test and you never handle it?"
💬 Follow-ups: What's the difference between on and once? How do you handle a beforeunload dialog?

🖼️ 17. Frames (iframes)

An iframe embeds another HTML document inside the current page. Elements inside it live in a separate document context, so page.locator() alone can't "see" them — you must first target the frame.

frameLocator() — the modern way

Playwright's frameLocator() returns a locator scoped to the iframe's content, and it auto-waits for the frame to load — no manual frame-switching like Selenium requires.

Nested frames

Chain frameLocator() calls to drill into a frame inside a frame. Each level narrows the search context further.

page (main document)
↓
frameLocator('#outerFrame')
↓
frameLocator('#innerFrame')
↓
locator('#submitBtn').click()
// Single iframe const frame = page.frameLocator('#paymentFrame'); await frame.locator('input[name="cardNumber"]').fill('4242424242424242'); // Nested iframe (frame inside a frame) await page .frameLocator('#outerFrame') .frameLocator('#innerFrame') .locator('#submitBtn') .click(); // Old-style: access via page.frames() list const target = page.frames().find(f => f.name() === 'billing');
💡 Tip: Prefer frameLocator() over page.frames() — it auto-waits and re-resolves if the frame reloads, matching Playwright's locator philosophy.
💬
🗣️ How I’d say it in an interview
❓ Interviewer asks: “How do you interact with elements inside an iframe in Playwright?”

An iframe is a separate document embedded inside the main page, so its elements are in their own frame.

The problem is a normal page locator does not automatically target elements inside that frame.

In Playwright, I use page.frameLocator() to locate the iframe and then find its child element.

For example, I chain a locator for the card number field after selecting the payment iframe.

For nested frames, I chain another frameLocator() for each frame level.

I prefer this because it keeps the frame targeting readable without manually switching back and forth.

So, in short, I target the correct frame first, which makes iframe tests clearer and less likely to interact with the wrong page.

🔄 Also asked as: "How is this different from Selenium's driver.switchTo().frame()?" / "How would you fill a card number that's inside a Stripe widget?"
💬 Follow-ups: Do you need to switch back to the main frame afterwards? Can frameLocator find a frame that loads late?

🗔 18. Windows & Tabs

Clicking a target="_blank" link or a "login with Google" button often opens a new tab or popup window. Each tab is its own Page object inside the same BrowserContext — Playwright doesn't "switch windows" like Selenium, it just gives you a new Page reference.

The core pattern

Because the new page opens asynchronously, you must start waiting for the event before triggering the click that opens it — otherwise you might miss it.

1. Start listening: context.waitForEvent('page')
↓
2. Click the link/button that opens popup
↓
3. await Promise.all([...]) resolves new Page
↓
4. Interact with newPage, or switch back
// Handling a popup / new tab const [popup] = await Promise.all([ context.waitForEvent('page'), // start waiting first page.click('#openNewTabBtn') // then trigger it ]); await popup.waitForLoadState(); console.log(await popup.title()); // All open pages in this context const allPages = context.pages(); await allPages[0].bringToFront(); // switch back to original tab
⚠️ Gotcha: If you click first and then call waitForEvent, you can miss the event entirely — the popup may already have opened. Always wrap both in Promise.all.
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “How do you handle a new tab or popup opened by a click in Playwright?”

A new tab is a separate Playwright Page object within the same browser context.

The problem is the new page can open before the test starts waiting for it.

To avoid that, I wait for the page event and perform the click together with Promise.all().

After the click, I use the returned page object to locate and interact with elements in the new tab.

For example, I use this pattern when a sign-in flow opens a separate OAuth window.

If needed, I bring the relevant page to the front or close the popup after assertions.

So, in short, I wait for the popup before triggering it, so the test reliably captures the correct page every time.

🔄 Also asked as: "How do you handle multiple browser windows in Playwright?" / "What happens if you click before you start waiting for the popup event?"
💬 Follow-ups: How do you close the popup after use? Can two pages run actions in parallel?

📊 19. Web Tables

Tables show up everywhere — order histories, admin panels, search results. The core skill is locating a specific row/column by its data, not by a hardcoded index.

Static vs Dynamic tables
Static TableDynamic Table
Fixed rows, hardcoded in HTMLRows generated from an API / DB at runtime
Row count never changesRow count and content vary per run
Can hardcode nth-child safelyMust locate rows by visible text / data attribute
Rare in real appsCommon — needs robust locator strategy

Finding a row by its data

The reliable pattern: filter tr by text it contains, then navigate to the sibling cell you need.

// Find the row containing "John Doe", then read its "Status" cell const row = page.locator('table tr', { hasText: 'John Doe' }); const status = await row.locator('td').nth(3).innerText(); // Extract ALL table data into a 2D array const rows = await page.locator('table tbody tr').all(); const data = []; for (const r of rows) { const cells = await r.locator('td').allInnerTexts(); data.push(cells); } // Pagination: click Next until it's disabled while (await page.locator('.next-btn').isEnabled()) { await page.click('.next-btn'); await page.waitForLoadState('networkidle'); }
💡 Tip: Use hasText or a data attribute like data-row-id to find rows — never a fixed row number, since dynamic tables re-sort or re-paginate.

🌑 20. Shadow DOM

Shadow DOM lets a component (like a custom <video-player> or a design-system button) encapsulate its own internal markup/CSS so it doesn't clash with the rest of the page. The hidden internal tree is the shadow tree, attached to a shadow host.

Open vs Closed mode

  • open — element.shadowRoot is accessible from JS/dev tools.
  • closed — shadowRoot returns null; much harder to automate (rare in practice).
📌 Key idea: Old Selenium needed special JS-executor tricks to pierce shadow DOM. Playwright's normal locator() automatically pierces open shadow roots — no special syntax needed for CSS selectors.
// Playwright locators pierce shadow DOM automatically await page.locator('my-app custom-button >> text=Submit').click(); // Or with plain CSS chaining — no special "shadow" keyword needed await page.locator('custom-datepicker') .locator('input.date-field') .fill('2026-09-12'); // Checking if an element has a shadow root (browser context) const hasShadow = await page.evaluate(() => document.querySelector('my-app').shadowRoot !== null );
🧠 Mnemonic: "Playwright doesn't fear the dark" — it walks straight into open shadow DOM like it's regular HTML. No special API needed!
🎤
🗣️ How I’d say it in an interview
❓ Interviewer asks: “How does Playwright handle elements inside the Shadow DOM?”

The Shadow DOM is a component feature that keeps its internal markup separate from the surrounding page.

The reason this matters is ordinary selectors can be harder to use when elements live inside web components.

By default, Playwright can locate elements inside open shadow roots with its normal locator engine.

For example, I use a role or CSS locator for a control inside an open shadow root.

I also check whether the component uses a closed shadow root, which normal automation cannot pierce.

When a locator fails, I inspect the component and confirm whether the issue is the shadow root or the locator itself.

So, in short, I use Playwright's built-in Shadow DOM support first and verify component boundaries before adding brittle workarounds.

🔄 Also asked as: "How does Playwright handle web components?" / "Have you tested a site built with Lit or Stencil components?"
💬 Follow-ups: What's the difference between open and closed shadow DOM? How would you automate a closed shadow root?

🖱️ 21. Mouse & Keyboard

For drag-and-drop, canvas drawing, hover menus, or custom sliders, element-level actions like .click() aren't enough — you need low-level mouse and keyboard APIs that simulate real hardware events.

Mouse API

  • page.mouse.move(x, y) — move cursor to absolute coordinates.
  • page.mouse.down() / up() — press/release the button (for drag).
  • page.mouse.click(x, y) — click at exact coordinates (e.g. on canvas).
  • page.mouse.wheel(dx, dy) — scroll programmatically.

Keyboard API

  • page.keyboard.press('Control+C') — chord/shortcut keys.
  • page.keyboard.type('text') — types like a real user, char by char.
  • Special keys: Enter, Tab, Escape, ArrowDown.
// Drag and drop using raw mouse events const src = page.locator('#drag-item'); const box = await src.boundingBox(); await page.mouse.move(box.x + 5, box.y + 5); await page.mouse.down(); await page.mouse.move(400, 300); await page.mouse.up(); // Copy-paste using keyboard shortcuts await page.locator('#src').selectText(); await page.keyboard.press('Control+C'); await page.locator('#dest').click(); await page.keyboard.press('Control+V');
💡 Tip: Playwright also has a built-in locator.dragTo(target) helper for simple drag-drop — reach for raw mouse.down/move/up only when you need fine control (e.g. sliders, canvas drawing).

4⚠️ Common Mistakes & Gotchas

  • ⚠️ Not attaching a dialog listener before the action — Playwright auto-dismisses silently.
  • ⚠️ Calling context.waitForEvent after the click instead of wrapping both in Promise.all.
  • ⚠️ Hardcoding row index (nth(2)) on a dynamic table that re-sorts.
  • ⚠️ Assuming Playwright can automate closed shadow roots the same way as open ones — it can't.
  • ⚠️ Using .click() for drag-and-drop instead of the mouse down/move/up sequence.
  • ⚠️ Forgetting waitForLoadState() on a new popup page before interacting with it.

6🧠 Memory Tricks & Last-Minute Tips

🧠 "LISTEN before you LEAP" — always attach the dialog/event listener before triggering the action that fires it (alerts, popups).
🧠 "Text over Index" — always find table rows/shadow elements by their content, never a hardcoded position.
  • ✅ Double-check every dialog handler is registered before the triggering click.
  • ✅ Use frameLocator, never manual frame switching.
  • ✅ Wrap popup waits in Promise.all — order matters.
  • ✅ Prefer locator.dragTo() unless you need pixel-level control.
  • ✅ Remember: open shadow DOM "just works," closed shadow DOM usually doesn't.
