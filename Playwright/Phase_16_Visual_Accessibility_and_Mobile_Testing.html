Playwright · Visual, A11y, Mobile & Localization Testing
📘 Topic 56 — Visual TestingPage 1

Visual testing catches bugs that functional tests miss — a button that still works but looks broken. It compares how a page looks against a trusted reference.

🖼️ Screenshot Comparison

The core idea: capture today's render, compare it pixel-by-pixel against a saved "baseline" image. Any meaningful difference fails the test.

📉 Visual Regression

A visual regression is an unintended UI change — spacing shifted, a color changed, an element overlapped — caught automatically instead of by a human eyeballing the app.

📸 toHaveScreenshot()

Playwright's built-in assertion. On first run it creates the baseline; on later runs it diffs against it and fails if pixels differ beyond a threshold.

// Full page screenshot assertion await expect(page).toHaveScreenshot('homepage.png'); // Element-level screenshot await expect(page.locator('.header')).toHaveScreenshot(); // Tolerate tiny anti-aliasing differences await expect(page).toHaveScreenshot('page.png', { maxDiffPixels: 100, threshold: 0.2, });

🗂️ Baseline Management

Baselines are stored image files checked into the repo, usually one set per OS/browser since fonts and rendering differ across platforms.

// Regenerate all baselines npx playwright test --update-snapshots
📌 Rule of thumb: generate baselines in CI, not on your laptop — different OS renders fonts differently!
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: What is visual regression testing in Playwright?

For me, visual regression testing means comparing the current UI against a trusted screenshot baseline.

The goal is to catch unintended visual changes, such as shifted spacing, changed colors, or overlapping elements.

In Playwright, I use toHaveScreenshot() to capture and compare a page or a specific element.

On the first run, Playwright creates the baseline, and later runs compare new screenshots against that saved image.

To reduce noise, I can configure maxDiffPixels or threshold for small rendering differences.

For reliable results, I keep baselines aligned with the same operating system and browser used in CI.

So, in short, screenshot comparison helps me detect visual regressions automatically, while consistent baselines prevent false failures.

🔄 Also asked as: "How would you catch a CSS regression before production?" / "How do you detect unexpected changes in a page's appearance?"
Follow-up Qs: How would you handle dynamic content in screenshots? When would you update a baseline?

📘 Topic 57 — Accessibility TestingPage 2

Accessibility (a11y) Testing ♿

💡 What is it?

Checking that everyone can use the app — blind, deaf, color-blind, or keyboard-only users.

🧱 4 Pillars — POUR

PillarAsk yourselfQuick test
Perceivable 👀Can they sense it?Images have alt text, text is readable
Operable ⌨️Can they use it without a mouse?Press Tab + Enter everywhere
Understandable 💬Is it clear?Errors say "Email is required"
Robust 🔧Does it work with screen readers?Real <button>, proper roles

🔧 Robust, made simple

Robust = clean, standard HTML so any tool (screen reader, voice control) can understand the page.

// Both look the same on screen <button>Submit</button> // ✅ "Submit, button" + keyboard works <div>Submit</div> // ❌ just "Submit" — no role, no keyboard
📌 Real tag first. ARIA (role="button") only if you can't. Check: does every button, link & input have a name and a role?

🏷️ ARIA, Roles & Labels

ARIA = extra HTML attributes that tell screen readers about custom widgets.

  • role → what the element IS (role="button")
  • aria-label → its name, what the screen reader says
  • aria-hidden → hide decorative stuff

👉 Best practice: use real tags (<button>) first, ARIA only if needed.

🧪 Testing in Playwright

@axe-core/playwright scans the page and lists violations automatically.

import AxeBuilder from '@axe-core/playwright'; test('a11y scan', async ({ page }) => { await page.goto('/'); const results = await new AxeBuilder({ page }).analyze(); expect(results.violations).toEqual([]); });
💡 Tip: Axe finds only some issues — also test manually with the keyboard. Scan error & loading states too.
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you test accessibility in Playwright?

Accessibility testing means checking that people with different abilities can use the application.

I use POUR, which stands for Perceivable, Operable, Understandable, and Robust.

For automation, I can scan a page with @axe-core/playwright and inspect the reported violations.

I also check keyboard navigation, accessible names, roles, labels, and clear validation messages.

For semantic HTML, I prefer native elements such as <button> instead of a clickable <div>.

I remember that automated scans find only some issues, so I include manual keyboard checks and different page states.

So, in short, I combine automated accessibility scans with practical keyboard and semantic checks rather than relying on one tool.

🔄 Also asked as: "How do you check that a UI works with a screen reader?" / "What is your approach to accessibility testing?"
Follow-up Qs: Can axe detect every accessibility issue? What is the difference between an ARIA role and an accessible label?

📘 Topic 58 — Mobile Web TestingPage 3

Mobile Web Testing 📱

🤖 Device Emulation

Playwright ships a devices dictionary that bundles a viewport size, user agent, pixel ratio, and touch support into one preset — like putting on a costume for a specific phone.

const { devices } = require('@playwright/test'); const iPhone = devices['iPhone 13']; test.use({ ...iPhone });

👆 Touch Events

Real mobile users tap and swipe, not click. locator.tap() dispatches touch events instead of mouse events — it needs hasTouch: true in the context (already on by default in mobile device presets).

test('tap the menu', async ({ page }) => { await page.goto('/'); await page.locator('.menu').tap(); });

📐 Mobile Viewport

You can also set just the viewport manually, without a full device preset, to test a specific breakpoint.

await page.setViewportSize({ width: 375, height: 667 });

🌐 Mobile Browser Testing

Playwright can launch Mobile Safari & Mobile Chrome engines directly (via webkit/chromium with mobile emulation), so you test real responsive breakpoints, not just a resized desktop browser.

📌 isMobile flag also toggles meta-viewport behaviour & touch — set it explicitly if you build a custom device.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you test mobile web behavior with Playwright?

For mobile testing, I use Playwright's device presets to configure viewport, user agent, and touch support together.

For example, devices['iPhone 13'] provides a ready-made configuration for that device profile.

When checking gestures, I use locator.tap() to simulate touch interaction instead of a mouse click.

For one breakpoint, I can use page.setViewportSize() without applying a full device preset.

I also verify responsive layouts at relevant mobile and tablet sizes.

When using custom settings, I make sure touch support is enabled before calling tap().

So, in short, I choose device emulation for realistic mobile settings and a custom viewport for focused breakpoint checks.

🔄 Also asked as: "How would you test responsive design in Playwright?" / "When would you use tap() instead of click()?"
Follow-up Qs: What does a Playwright device preset configure? How would you test a tablet landscape breakpoint?

📘 Topic 59 — Localization TestingPage 4

Localization Testing 🌍

💡 What is it?

Checking that the app shows the right date, time & money for users in different countries.

🎛️ 2 Settings to Know

SettingWhat it changesExample
locale 🌐Date, number & currency format'en-IN' → 10/10/2026, ₹1,00,000
timezoneId 🕒The time shown in the browser'Asia/Kolkata' (IST)

🪜 How to Test (3 steps)

  • 1. Set locale + timezoneId
  • 2. Open the page
  • 3. Check the text looks right for that country
// Step 1: pretend the user is in India test.use({ locale: 'en-IN', timezoneId: 'Asia/Kolkata' }); test('indian date', async ({ page }) => { await page.goto('/'); // Step 2 await expect(page.locator('.date')) // Step 3 .toContainText('10/10/2026'); });
📌 Same date, different look: US 10/25/2026 · India 25/10/2026 (day first). Money too: US $100,000 vs India ₹1,00,000 (lakh style commas).
⚠️ locale ≠ translation. It changes date/number/currency format only — your app's text stays in the same language.
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you test localization in Playwright?

Localization testing checks whether dates, times, numbers, and currencies appear in the expected regional format.

In Playwright, I configure locale for regional formatting and timezoneId for browser time behavior.

For example, I can set locale: 'en-IN' and timezoneId: 'Asia/Kolkata'.

Then I open the page and assert that displayed values follow the expected format.

One important distinction is locale settings do not translate application text into another language.

To avoid brittle tests, I use expected values that match the configured locale and timezone.

So, in short, I test localization by controlling regional settings and verifying formatting without confusing it with translation.

🔄 Also asked as: "How would you catch region-specific date or currency bugs?" / "What is the difference between locale and timezoneId?"
Follow-up Qs: Does locale translate the application's text? How would you test right-to-left language layouts?

⚠️ Common Mistakes & Gotchas ALWAYS READ

⚠️ Screenshots differ across OS/browser — generate baselines in CI, not locally.

⚠️ Skipping maxDiffPixels/threshold makes tests fail on tiny anti-aliasing noise.

⚠️ Adding aria-label on elements that already have visible text causes confusing duplicate announcements.

⚠️ Calling tap() without hasTouch enabled outside a device preset throws or misbehaves.

⚠️ Assuming locale translates UI text — it only changes native formatting, not your app's strings.

⚠️ Hardcoding a date string in an assertion — breaks the moment timezone or locale changes.

🧠 Memory Tricks & Last-Minute Tips

🧠 POUR = like pouring water — accessibility is the vessel that holds everyone.
🧠 Visual testing = screenshot-diff detective: baseline is the alibi photo, today's run is the suspect photo.
🧠 devices['iPhone 13'] = a whole costume in one line — viewport + UA + touch together.
🧠 locale vs timezoneId = "where you SAY you are" vs "WHEN you say it is."
  • ✅ Regenerate baselines in CI, matching CI's exact rendering environment.
  • ✅ Run axe scans on empty/loading/error states, not just the happy path.
  • ✅ Test at least two breakpoints: mobile portrait + tablet landscape.
  • ✅ Test at least one non-US locale to catch date/currency format bugs early.
