📘 Phase 7 — Auth & SessionsPlaywright

🔐 Authentication & Sessions

Every automated test that needs a logged-in user faces the same problem: logging in through the UI on every single test is slow and repetitive. Playwright solves this with session reuse — log in once, save the browser's "logged-in state," and reuse it everywhere.

🔑 Login AutomationPhase 7

🔑 Login Automation

The most basic form of authentication testing: fill the login form → submit → verify success. It's the foundation every other technique (cookies, storageState) builds on top of.

Typical login flow

// Basic login automation with Playwright import { test, expect } from '@playwright/test'; test('user can log in', async ({ page }) => { await page.goto('https://app.example.com/login'); await page.fill('#username', 'testuser'); await page.fill('#password', 'Secret123'); await page.click('button[type="submit"]'); await expect(page.locator('.dashboard')).toBeVisible(); });

The problem: this whole block re-runs before every single test — multiplied across hundreds of tests, login time alone can eat minutes of CI runtime.

🗣️ How I’d say it in an interview
❓ Interviewer asks: “How do you automate login and avoid logging in through the UI before every test?”

Login automation means using a test to sign in through the same steps a user would follow.

The problem is repeating the full login flow before every test makes a large suite slower and more fragile.

What I do is run a dedicated login step and save the authenticated browser state.

In Playwright, I reuse that saved state with storageState for tests that need the same user session.

I still keep separate login tests to verify that the sign-in flow itself works correctly.

I also make sure the saved state is refreshed when credentials or session tokens expire.

So, in short, I test login directly and reuse valid sessions elsewhere, improving speed without sacrificing coverage of authentication.

🍪 Cookies & Web StoragePhase 7

🍪 Cookies, Local & Session Storage

When a user logs in, the app usually stores proof of that login in one or more of these three browser storage mechanisms. Knowing which one is used decides how you capture/reuse the session.

Browser storage tree

  • Browser Storage
    • 🍪 Cookies — sent automatically with every request
      • Can be httpOnly (JS can't read them)
    • 🗄️ Local Storage — key/value, per origin
      • Survives browser restart, not sent to server automatically
    • 📦 Session Storage — key/value, per tab
      • Cleared the moment the tab closes
Comparison
FeatureCookiesLocal StorageSession Storage
Sent to server?Yes, automaticallyNoNo

Playwright APIcontext.addCookies()page.evaluate()page.evaluate()

Reading / writing storage in Playwright

// Cookies — set directly on the browser context await context.addCookies([{ name: 'session_id', value: 'abc123', domain: 'example.com', path: '/' }]); // Local storage — must go through page.evaluate await page.evaluate(() => { localStorage.setItem('authToken', 'xyz789'); });
📌 httpOnly cookies can't be read by JS at all — so page.evaluate() won't see them, only context.cookies() will.

🧾 storageStatePhase 7

🧾 Authentication State & storageState

Authentication state = the full snapshot of everything that proves a user is logged in — cookies plus local storage, bundled together. Playwright captures this in one call: storageState.

💾 Saving authenticated session

// auth.setup.ts — run once, log in, then save state import { test as setup } from '@playwright/test'; const authFile = 'playwright/.auth/user.json'; setup('authenticate', async ({ page }) => { await page.goto('/login'); await page.fill('#username', 'testuser'); await page.fill('#password', 'Secret123'); await page.click('text=Log in'); await page.waitForURL('/dashboard'); // snapshot cookies + storage into a JSON file await page.context().storageState({ path: authFile }); });

♻️ Reusing the saved session

// any test file — start already logged in import { test } from '@playwright/test'; test.use({ storageState: 'playwright/.auth/user.json' }); test('dashboard loads for logged-in user', async ({ page }) => { await page.goto('/dashboard'); // no login step needed — already authenticated! });

🔀 The save-once, reuse-many workflow

1️⃣ Run login once (setup project)
↓
2️⃣ context.storageState({ path }) saves JSON
↓
3️⃣ Every other test loads that JSON via storageState
↓
4️⃣ Tests start already authenticated 🎉
⚠️ If the session expires (short-lived token), the saved file goes stale — re-run the setup project to refresh it.

⚙️ Global Setup PatternPhase 7

⚙️ Avoid Logging In Before Every Test

Playwright's recommended enterprise pattern: a dedicated setup project that runs once, then every other project depends on it and reuses its saved state.

playwright.config.ts — projects wiring

export default defineConfig({ projects: [ { name: 'setup', testMatch: /.*\.setup\.ts/, }, { name: 'chromium', use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json', }, dependencies: ['setup'], }, ], });

Because dependencies: ['setup'] is set, Playwright runs the login exactly once before the chromium project starts — every test in it inherits the saved session automatically.

✅ Best practices

One setup project
Keep login logic in a single .setup.ts file.
Separate auth files per role
e.g. admin.json, user.json for different roles.
Gitignore the auth folder
Never commit real session tokens to source control.
Refresh on expiry
Re-run setup if tokens are short-lived (e.g. daily CI runs).

⚠️ Common mistakes

⚠️ Forgetting to add the .auth/ folder to .gitignore — leaks real credentials.
⚠️ Reusing one storageState file across roles that need different permissions.
⚠️ Not refreshing state when the backend rotates tokens — tests silently start failing.

🗣️ How I’d say it in an interview
❓ Interviewer asks: “What is storageState in Playwright, and why do you use it?”

The <code>storageState</code> option loads a saved snapshot of browser authentication state, including cookies and local storage.

The reason I use it is tests can start logged in instead of repeating the same UI login steps.

To create it, I sign in once and save the context state to a JSON file.

In my test setup, I provide that file as the storage state for tests using that account.

For multiple roles, I keep separate state files so each test uses the correct user's permissions.

I also protect these files because they can contain session information that grants access to an account.

So, in short, I reuse secure, role-specific session snapshots to make tests faster while keeping authentication setup controlled.

🗣️ How I’d say it in an interview
❓ Interviewer asks: “What is the difference between cookies and local storage?”

Cookies and local storage both store browser-side data, but they behave differently when an application makes requests.

Cookies are often sent automatically with matching HTTP requests, depending on their domain and security settings.

Local storage is kept in the browser and is not automatically attached to HTTP requests.

For example, I check whether an application uses cookies or a client-side token when investigating session behavior.

When I use <code>storageState</code>, I remember that Playwright can capture cookies and supported local-storage data.

I also consider security flags and token handling instead of assuming every app stores authentication the same way.

So, in short, I choose tests based on how the application really manages sessions, rather than treating cookies and local storage as interchangeable.

🔄 Also asked as: "Why would Playwright's storageState capture both cookies and local storage?"
