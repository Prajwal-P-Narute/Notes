🎭 Playwright Fundamentals — Phase 1 Introduction & Core Concepts

1. What is Playwright? 🎭

Definition: Playwright is an open-source browser automation framework by Microsoft that enables reliable end-to-end testing for modern web apps. Released in 2020.

🔑 Why Playwright Exists

  • Modern web apps are dynamic, async, and complex — classic tools struggle
  • Built to handle SPAs, shadow DOM, iframes, file uploads, network mocking natively
  • Single API to test Chromium, Firefox, WebKit — real cross-browser coverage
  • Auto-waiting: no manual sleep() or waitForElement() needed

2. Playwright Architecture 🏗️

🔧 How Playwright Communicates with Browsers

Your Test Code (JS/TS/Python/Java/C#)
↓
Playwright Library (Node.js server)
↓ WebSocket / CDP
Browser Process (Chromium / Firefox / WebKit)
↓
Web Page (DOM + Network)
⚠️ Key insight: Playwright uses Chrome DevTools Protocol (CDP) for Chromium and custom protocols for Firefox/WebKit. Communication is via WebSocket — much faster than Selenium's HTTP/WebDriver.

🧩 Core Architecture Concepts

Browser
A browser instance (Chromium/Firefox/WebKit). One per test run.
Browser Context
An isolated session — like an incognito window. Each test gets its own context.
Page
A single browser tab. Tests interact with pages via the page object.
Locator
A lazy reference to an element. Auto-waits, retries, more stable than selectors.
Frame
A <iframe> or frame inside a page. Access via page.frame().
Worker
A service/web worker attached to the page. Playwright can access these.
Route
Network interception — mock/modify/block HTTP requests with page.route().
Tracing
Records a zip of DOM snapshots, network calls, screenshots for debugging.

📦 Browser Isolation: Context vs Page

Think of it like this:
🌐 Browser = the Chrome app
📂 BrowserContext = a user profile / incognito window (isolated cookies, storage)
📄 Page = a single tab inside that window

Each test gets its own BrowserContext → no state leakage between tests!

⚡ Auto-Waiting — Playwright's Superpower

  • Before clicking: waits for element to be visible, enabled, stable
  • Before filling: waits for element to be editable
  • Before assertions: retries until condition met (default: 5 seconds)
  • No need for waitForElement(), Thread.sleep(), or time.sleep()
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is a BrowserContext in Playwright, and why does it matter?”

A BrowserContext is an isolated session inside a browser, like an incognito window.

It has its own cookies, local storage, and session state.

In Playwright, every test gets its own BrowserContext by default.

What that means is tests can't accidentally share login state or cached data.

So I never have to clear cookies manually between tests.

The way I remember it is Browser is the app, Context is the profile, and Page is a tab.

So, in short, built-in context isolation keeps every test independent, which makes the suite reliable and safe to run in parallel.

🎭 Playwright Fundamentals — Phase 1 playwright.config.ts

4. playwright.config.ts — Deep Dive ⚙️

What is it? The single config file that controls everything: which browsers to use, test timeouts, base URL, reporters, parallel execution, retries, and more.

📄 Annotated playwright.config.ts

import { defineConfig, devices } from '@playwright/test'; export default defineConfig({ testDir: './tests', // folder with test files timeout: 30000, // max time per test (ms) retries: 2, // auto-retry on failure workers: 4, // parallel test workers fullyParallel: true, // run all files in parallel reporter: 'html', // HTML report (others: 'list','json') use: { baseURL: 'http://localhost:3000', // prefix for page.goto('/') headless: true, // run without browser UI screenshot: 'only-on-failure', // capture on test fail video: 'retain-on-failure', // record video on fail trace: 'on-first-retry', // enable Playwright Trace }, projects: [ // run same tests in multiple browsers { name: 'chromium', use: { ...devices['Desktop Chrome'] } }, { name: 'firefox', use: { ...devices['Desktop Firefox'] } }, { name: 'webkit', use: { ...devices['Desktop Safari'] } }, ], });

🔑 Most Important Config Keys

testDir
Path to your tests folder
timeout
Max ms a single test can run before it fails
retries
How many times to re-run a failing test automatically
workers
Number of parallel test threads (default: 50% of CPU cores)
fullyParallel
Run tests in the same file in parallel (default: false)
baseURL
Base URL so tests can use relative paths like page.goto('/')
screenshot
When to capture: 'off' | 'on' | 'only-on-failure'
trace
Tracing: 'off' | 'on' | 'on-first-retry'
projects
Array of browser configs — run same tests in multiple browsers

🎭 Playwright Fundamentals — Phase 1 Basic Test Structure

5. Basic Test Structure 🧪

🔑 The Three Pillars: test() · expect() · describe()

// Full anatomy of a Playwright test file import { test, expect } from '@playwright/test'; // describe() — groups related tests (like a suite/module) test.describe('Login Page Tests', () => { // beforeAll() — runs ONCE before all tests in this group test.beforeAll(async ({ browser }) => { // e.g. seed DB, create test data }); // beforeEach() — runs before EVERY test in this group test.beforeEach(async ({ page }) => { await page.goto('/'); // navigate before each test }); // test() — a single test case test('should show error for wrong password', async ({ page }) => { await page.fill('#email', 'user@test.com'); await page.fill('#password', 'wrong'); await page.click('button[type="submit"]'); // expect() — assertion (auto-retries until timeout) await expect(page.locator('.error-msg')).toBeVisible(); }); // afterEach() — runs after EVERY test test.afterEach(async ({ page }) => { await page.screenshot({ path: 'screenshot.png' }); }); // afterAll() — runs ONCE after all tests in this group test.afterAll(async () => { // e.g. clean up DB, close connections }); });

📋 What Each Hook Does

test()
Defines a single test case. Must have a name and an async function.
expect()
Assertion helper. Auto-retries until condition passes or timeout hits.
describe()
Groups tests logically. Scopes hooks to the group. Nestable.
beforeEach()
Runs before every test. Use for navigation, login, page setup.
afterEach()
Runs after every test. Use for screenshots, cleanup per test.
beforeAll()
Runs ONCE before the group. Use for DB seed, server start.
afterAll()
Runs ONCE after the group. Use for DB cleanup, close connections.
⚠️ Gotcha: beforeAll/afterAll hooks receive { browser } fixture (not page) by default, because a page doesn't persist across all tests. Use page only in beforeEach/afterEach.

6. Test Naming, Organization & Best Practices 📂

✅ Test Naming Best Practices

  • Use plain English — "should show error when email is empty"
  • Follow pattern: "should [action] when [condition]"
  • Be specific — avoid generic names like "test1" or "checkLogin"
  • Name reveals intent, not implementation
  • Names appear in reports — make them self-documenting
// ❌ Bad naming test('test1', async ({ page }) => { ... }); test('login', async ({ page }) => { ... }); // ✅ Good naming test('should redirect to dashboard after successful login', async ({ page }) => { ... }); test('should show validation error when email is missing', async ({ page }) => { ... });

📁 Test Organization Strategies

  checkout/checkout.spec.ts
  dashboard/dashboard.spec.ts
By Type

  e2e/login.spec.ts

🏷️ Tagging & Filtering Tests

// Tag tests with @smoke, @regression, @critical etc. test('@smoke should load homepage', async ({ page }) => { ... }); // Run only tagged tests from CLI npx playwright test --grep "@smoke" // Skip a test test.skip('skipping broken test temporarily', async () => { ... }); // Run only this test (debug mode - don't commit!) test.only('should login as admin', async () => { ... });

🎤 Interview Q&A — Test Structure

Interview questions — know these!
QuestionAnswer
What is the difference between beforeEach and beforeAll? beforeEach runs before every test; beforeAll runs once before all tests in the describe block.
When would you use describe()? To group logically related tests so hooks and setup scope correctly to that group.
What does expect() do in Playwright? Makes assertions with auto-retry — it keeps checking until condition passes or the assertion timeout hits.
What is test.only() and why is it dangerous? Runs only that test, skipping all others — dangerous if accidentally committed to CI, whole suite won't run.
How do you skip a flaky test temporarily? Use test.skip() with a comment explaining why, then file a ticket to fix it.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What lifecycle hooks does Playwright provide, and when do you use each?”

Playwright has four lifecycle hooks: beforeEach, afterEach, beforeAll, and afterAll.

They handle setup and teardown, so tests stay clean and independent.

Before every test, I use beforeEach to navigate to the right page.

After every test, I use afterEach to capture a screenshot on failure.

For heavy setup, I use beforeAll, which runs once for the whole group.

For final cleanup, I use afterAll to release those resources.

So, in short, I keep repeated steps in hooks and heavy setup in beforeAll, so the suite stays fast, clean, and easy to maintain.

⚠️ Section 4 — Common Mistakes & Gotchas ALWAYS READ TIER 3
  • ⚠️ Using test.only() and committing to git: the entire CI suite runs just that one test.
  • ⚠️ Using the page fixture in beforeAll; pages are per-test, so use browser there.
  • ⚠️ Forgetting await before a Playwright call: silent failures with no useful error.
  • ⚠️ Hardcoding URLs instead of using baseURL in config; it breaks when you switch environments.
  • ⚠️ Committing headless: false: CI has no display, so tests will fail.
  • ⚠️ Setting workers high while tests share state: tests will interfere with each other.
  • ⚠️ Running npx playwright test before npx playwright install: "browser not found" error.
🧠 Section 6 — Memory Tricks & Last-Minute Tips TIER 3 · read last
🧠 B-C-P hierarchy:
Browser → Context → Page
= App → Incognito Window → Tab
Each test gets its own C & P.
🧠 Hook order: "Before-Before-After-After"
beforeAll → beforeEach → TEST → afterEach → afterAll
Outer runs before inner. Mirrors describe nesting.
🧠 Playwright vs Selenium = express vs slow train
CDP = direct fibre line. WebDriver = HTTP mail coach. Same destination, very different speed.
🧠 expect() is patient, test() is not
expect() retries until the assertion timeout. test() fails at the test timeout. Set both in config.
  • Always run npx playwright install after cloning a project; browsers don't come with node_modules.
  • Set retries: 2 in CI config but retries: 0 locally so failures surface immediately during dev.
  • Use --ui mode when debugging a failing test; it shows a step-by-step trace right in the browser.
  • Never leave test.only() in code that gets pushed; add an ESLint rule to catch it automatically.
  • Name your tests "should [verb] when [condition]"; it reads like a spec and maps directly to bug reports.
