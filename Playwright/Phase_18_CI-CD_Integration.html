🌐 What is CI/CD?

🔁 Continuous Integration (CI)

  • Automatically build & test code on every push
  • Catch bugs early before they reach prod
  • Run Playwright tests on each PR/commit

🚀 Continuous Delivery (CD)

  • Auto-deploy to staging/prod after tests pass
  • Full pipeline: code → test → deploy
  • Zero manual steps needed

🔧 64. Jenkins + Playwright

🛠️ Install Playwright on Jenkins Agent

💡 Jenkins agents need Node.js installed + browser dependencies. Use a Docker agent or install via NodeJS plugin.
Install Node
Use Jenkins NodeJS Plugin — configure Global Tool in Manage Jenkins → Tools
npm Commands
npm ci (clean install) → npx playwright install → npx playwright test
Browser Deps
Run npx playwright install-deps on Linux agents to get system libs
Env Variables
Set via Manage Jenkins → Configure System or inside environment {} block in pipeline
Reports
Use HTML Publisher Plugin to display Playwright HTML report in Jenkins UI
Artifacts
archiveArtifacts step saves reports, screenshots, videos for download
On Failure
Playwright auto-saves screenshots + trace.zip in test-results/ on failure → archive them
📌 Always use npm ci instead of npm install in CI — it's faster, deterministic & uses lockfile!

🔧 Jenkins Pipeline — Declarative

Jenkinsfile Syntax + Config

📝 Jenkinsfile (Declarative Pipeline)

// Jenkinsfile — place in project root
pipeline { agent { docker { image 'mcr.microsoft.com/playwright:v1.44.0-jammy' } } environment { BASE_URL = 'https://staging.myapp.com' CI = 'true' } stages { stage('Install') { steps { sh 'npm ci' } } stage('Test') { steps { sh 'npx playwright test --reporter=html,line' } } } post { always { archiveArtifacts( artifacts: 'playwright-report/**,test-results/**', allowEmptyArchive: true ) publishHTML([ allowMissing: false, reportDir: 'playwright-report', reportFiles: 'index.html', reportName: 'Playwright Report' ]) } failure { emailext(to: 'team@company.com', subject: 'Tests Failed!') } } }

🌿 Environment Variables in Jenkins

Pipeline-Level environment {}

  • Scope: entire pipeline
  • Use env.VAR_NAME to read
  • Set secrets via credentials('id')

Stage-Level env vars

  • Defined inside a stage {} block
  • Override pipeline-level vars
  • Useful for per-env test runs
// Access env vars in playwright.config.ts
const config = { use: { baseURL: process.env.BASE_URL ?? 'http://localhost:3000', } };

📸 Screenshots & Videos on Failure

🎥 In playwright.config.ts: set screenshot: 'only-on-failure' and video: 'retain-on-failure' — Jenkins then archives test-results/ automatically.
// playwright.config.ts — failure capture
use: { screenshot: 'only-on-failure', // capture on fail video: 'retain-on-failure', // keep video on fail trace: 'on-first-retry', // trace on retry }

🗣️ How I'd say it in an interview
❓ Interviewer asks:How would you configure a Playwright test pipeline in Jenkins?

I usually configure a declarative Jenkins pipeline with a Playwright Docker agent for consistent browser dependencies.

The pipeline starts with npm ci, installs or reuses the required browsers, and runs npx playwright test.

For configuration I pass values such as BASE_URL through environment variables instead of hardcoding environment-specific settings.

When tests finish I archive the HTML report, screenshots, videos, and traces so failures remain diagnosable.

To keep feedback useful I publish the report in Jenkins and notify the team when the pipeline fails.

For reliability I pin compatible Playwright and Docker versions and keep secrets in Jenkins credentials.

So, in short, I make the pipeline repeatable, secure, and easy to troubleshoot—not just capable of launching tests.

🐙 65. GitHub Actions — Playwright

Workflow YAML + Matrix + Parallel Jobs

📄 What is GitHub Actions?

GitHub's built-in CI/CD system. Workflows defined as YAML files in .github/workflows/. Triggered by push, PR, schedule, or manual dispatch. Runs on GitHub-hosted runners (ubuntu-latest, windows, macos).

🔑 Key YAML Components

KeyWhat it doesExample
on:Trigger eventspush, pull_request, schedule
jobs:Define job groupstest:, deploy:
runs-on:Choose runner OSubuntu-latest
steps:List of commands- run: npm ci
uses:Reference an actionactions/checkout@v4
with:Pass inputs to actionnode-version: 20
env:Inject env variablesBASE_URL: ${{ secrets.URL }}
if:Conditional executionif: ${{ !cancelled() }}

📝 Full Playwright Workflow YAML

// .github/workflows/playwright.yml
name: Playwright Tests on: push: { branches: [main, develop] } pull_request: { branches: [main] } jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20 } - name: Install deps run: npm ci - name: Install Playwright Browsers run: npx playwright install --with-deps - name: Run Tests run: npx playwright test env: BASE_URL: ${{ secrets.BASE_URL }} - name: Upload Report # always run if: always() uses: actions/upload-artifact@v4 with: name: playwright-report path: playwright-report/ retention-days: 30
📌 –with-deps flag installs Playwright browsers AND system libs in one command — perfect for GitHub Actions runners!
💡 Secrets are stored in GitHub → Settings → Secrets and Variables → Actions. Access via ${{ secrets.MY_SECRET }} — they're masked in logs automatically.

🧪 Matrix Testing + Parallel Jobs

GitHub Actions Advanced

🔢 Matrix Browser Testing

Run the same tests across multiple browsers (or OS/Node versions) simultaneously using a strategy.matrix. Each combination becomes its own job.
// Matrix strategy — test on chromium, firefox, webkit in parallel
jobs: test: runs-on: ubuntu-latest strategy: fail-fast: false # don't cancel other browsers on failure matrix: browser: [chromium, firefox, webkit] steps: - uses: actions/checkout@v4 - run: npm ci - run: npx playwright install ${{ matrix.browser }} --with-deps - run: npx playwright test --project=${{ matrix.browser }}

✅ fail-fast: false

Don't cancel remaining matrix jobs when one fails. All browsers run independently — you see ALL failures.

📊 Artifact per Browser

Name artifact ${{ matrix.browser }}-report to get separate report per browser in GitHub UI.

⚡ Parallel Jobs (Job-level)

// Two jobs running in parallel — smoke + regression
jobs: smoke-tests: runs-on: ubuntu-latest steps: - run: npx playwright test --grep @smoke regression-tests: runs-on: ubuntu-latest steps: - run: npx playwright test --grep @regression deploy: needs: [smoke-tests, regression-tests] # wait for BOTH runs-on: ubuntu-latest steps: - run: echo "Deploying..."

📤 Artifact Upload — Key Points

  • Use actions/upload-artifact@v4 — attach test-results, HTML report, videos
  • Use if: ${{ !cancelled() }} so artifacts upload even when tests fail
  • Set retention-days (default 90) to manage storage costs
  • Download from GitHub Actions run UI or use actions/download-artifact@v4
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you run Playwright tests across browsers in GitHub Actions?

I usually use a GitHub Actions matrix to run Playwright projects for Chromium, Firefox, and WebKit in parallel.

Each matrix entry creates a separate job, so browser results can be compared without running every browser sequentially.

I set fail-fast: false when I want remaining browser jobs to finish after one browser fails.

Before testing the workflow checks out the repository, sets up Node.js, installs dependencies, and installs the required browsers.

For credentials I store sensitive values in GitHub Actions secrets and expose only the variables the tests need.

After execution I upload reports and test results with if: ${{ !cancelled() }} so diagnostic artifacts survive test failures.

So, in short, I use matrix jobs for broad browser coverage and preserve each run's evidence for focused debugging.

🐳 66. Docker + Playwright

Official Image + Container Execution

🐳 Why Docker for Playwright?

✅ Problem it solves: Browser dependencies (libglib, libatk, libnss…) differ per OS. Docker packages everything — tests run identically in dev & CI.
⚠️ Without Docker: "Works on my machine" breaks in CI because system libraries are different on the runner.

📦 Official Playwright Docker Image

Image
mcr.microsoft.com/playwright:v1.44.0-jammy — includes Chromium, Firefox, WebKit + all deps
Tag format
v{playwright-version}-{ubuntu-codename} e.g. v1.44.0-jammy (Ubuntu 22)
Run locally
docker run --rm -v $(pwd):/app -w /app mcr.microsoft.com/playwright:v1.44.0-jammy npx playwright test
In Jenkins
Use agent { docker { image 'mcr.microsoft.com/playwright:v1.44.0-jammy' } } in Jenkinsfile
In GH Actions
Use container: mcr.microsoft.com/playwright:v1.44.0-jammy key in job spec

📝 Custom Dockerfile (project-specific)

// Dockerfile in project root
FROM mcr.microsoft.com/playwright:v1.44.0-jammy WORKDIR /app # Copy package files first (layer caching benefit) COPY package*.json ./ RUN npm ci # Copy rest of source COPY . . # Default command runs all tests CMD ["npx", "playwright", "test"]

🔧 Useful Docker Commands

CommandPurpose
docker build -t pw-tests .Build image from Dockerfile
docker run --rm pw-testsRun tests & remove container after
docker run -v $(pwd)/results:/app/test-results pw-testsMount results folder to host
docker run -e BASE_URL=https://... pw-testsPass env variable to container

🌐 Browser Dependencies (Linux)

  • Official image = zero extra setup, all deps included
  • Custom base image: run npx playwright install-deps chromium
  • Headed mode in Docker needs Xvfb — use --headed only with virtual display
  • Headless mode (default) = works perfectly in Docker with no display server
🐳 Always pin the Playwright Docker image version (e.g. v1.44.0-jammy) — don't use :latest. Version mismatch = browser launch failures!

⚡ 67. CI Parallelization

Workers + Sharding + Distributed Testing

🔀 Three Ways to Parallelize

MethodScopeConfigBest For
Workers Single machine workers: 4 in config Moderate test suites on one runner
Sharding Multiple machines --shard=1/3 CLI flag Large suites split across CI runners
Distributed Multiple CI jobs Matrix in GH Actions / parallel in Jenkins Cross-browser / cross-env at scale

👷 Workers (Intra-machine)

Playwright uses worker processes — each worker runs tests in its own browser context. Configured in playwright.config.ts via workers property.
// playwright.config.ts — worker config
export default defineConfig({ workers: process.env.CI ? 4 : 2, // 4 in CI, 2 locally fullyParallel: true, // tests within a file also run in parallel retries: process.env.CI ? 2 : 0, // retry flaky tests in CI });

🔪 Sharding (Multi-machine)

Split the test suite into N equal shards and run each on a separate machine/job. Playwright distributes tests automatically — no manual grouping needed!
🖥️ Machine 1
--shard=1/3
Tests 1–33
🖥️ Machine 2
--shard=2/3
Tests 34–66
🖥️ Machine 3
--shard=3/3
Tests 67–100
// GitHub Actions matrix sharding
strategy: matrix: shardIndex: [1, 2, 3] shardTotal: [3] steps: - run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}

🌐 Distributed Testing

  • Combine sharding + matrix: 3 shards × 3 browsers = 9 parallel jobs
  • Each shard uploads its blob report; the merge job downloads all shard artifacts before merging
  • Merge reports only after downloading all blob-report artifacts into ./all-blobs
  • Use blob reporter in each shard, then merge for combined report
// Blob reporter + merge for distributed shards 
# .github/workflows/playwright-sharded.yml
name: Playwright Sharded Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shardIndex: [1, 2, 3]
        shardTotal: [3]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }} --reporter=blob
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: blob-report-${{ matrix.shardIndex }}
          path: blob-report/
          if-no-files-found: ignore

  merge-reports:
    if: ${{ always() }}
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - uses: actions/download-artifact@v4
        with:
          pattern: blob-report-*
          path: all-blobs
          merge-multiple: true
      - run: npx playwright merge-reports --reporter html ./all-blobs
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: playwright-report/
          if-no-files-found: ignore
🧠 Memory Trick: Think of sharding like cutting a pizza 🍕 — each person (machine) gets equal slices. Workers = how fast one person chews!

⚠️ Common Mistakes & Gotchas TIER 3 ALWAYS READ
  • ⚠️ Using npm install instead of npm ci in CI — causes non-deterministic installs, can silently update deps
  • ⚠️ Forgetting if: ${{ !cancelled() }} on artifact upload — reports won't save when tests fail (the only time you need them most!)
  • ⚠️ Using :latest Docker tag — browser version mismatch with your package.json Playwright version causes launch failures
  • ⚠️ Setting fail-fast: true (default) in matrix — one browser failing cancels all others, you lose cross-browser insights
  • ⚠️ Forgetting --with-deps on GitHub Actions — browsers install but system libs are missing → tests crash on Linux
  • ⚠️ Not mounting test-results volume in Docker — screenshots/videos exist inside container but are lost when container exits
  • ⚠️ Sharding without blob reporter — each shard generates a separate HTML report; you get 3 disconnected reports instead of one merged view
  • ⚠️ Setting fullyParallel: true with shared state — tests that mutate the same data will conflict; ensure test isolation
🧠 Memory Tricks & Last-Minute Tips TIER 3
🍕 Sharding = Pizza Slices
Each machine gets equal slices (tests). Workers = how fast one machine chews through its slice.
🔒 Docker = Zip bag
Everything the test needs (browsers + libs) packed in one sealed bag. Same bag → same environment, always.
🎭 matrix = Clone Army
GitHub Actions sends the same job to multiple environments simultaneously — like cloning your test team.
📦 always() = safety net
if: ${{ !cancelled() }} is like a parachute — it opens even if everything above it fails. Put artifact upload here.
  • Set CI=true env var in pipeline — Playwright auto-adjusts (no animations, cleaner output)
  • Use retries: 2 only in CI — never locally, it hides flaky tests during development
  • For distributed runs: use blob reporter per shard + merge job; don't try to upload HTML per shard and combine manually
  • Keep Docker image version in sync with @playwright/test version in package.json — they must match!
  • Matrix strategy runs FASTER than sequential — 3 browsers in parallel = 3× speed
