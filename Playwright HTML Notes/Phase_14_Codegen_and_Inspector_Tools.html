Phase 14 — Playwright Codegen & ToolsCodegen · Part 1

🎬 Playwright Codegen

Codegen is a Playwright CLI tool that records your clicks/typing in a real browser and turns them into working test code — automatically.

// run codegen against any URL npx playwright codegen https://example.com

📌 Record a test

  • Opens two windows: a real browser + the Playwright Inspector panel.
  • Every click, type, check, select you do in the browser is captured live as code in the inspector panel.
  • You can pause recording, edit the browser state manually, then resume.

🎯 Generate locators

  • Codegen doesn't grab random CSS — it picks the most resilient locator available, in priority order: getByRole → getByText → getByLabel → getByTestId → CSS/XPath (last resort).
  • Hover an element in the app to preview the locator it would generate, before you even click.

⚙️ Generate actions

Common actions Codegen turns into code: click, fill, check/uncheck, select option, hover, press key, and assertions when you toggle "assert visibility" / "assert text" mode.

// example output from a login flow await page.getByLabel('Username').fill('admin'); await page.getByLabel('Password').fill('secret123'); await page.getByRole('button', { name: 'Log in' }).click();

🗣️ How I'd say it in an interview
❓ Interviewer asks:What is Playwright Codegen, and how do you use it?

In simple terms, Playwright Codegen records my browser interactions and converts them into test code automatically.

To start, I run npx playwright codegen with the target URL and interact with the application in its browser.

As I work, the Inspector displays generated actions and suggests locators based on the elements I select.

For locator quality, I prefer accessible role, text, and label locators before relying on CSS or XPath.

I also use it to discover unfamiliar page elements and quickly scaffold common actions like filling forms or clicking buttons.

Before reusing the output, I review the generated code, verify locator uniqueness, and add meaningful assertions.

For different projects, I can choose another supported target language, such as Python, Java, or C#.

So, in short, Codegen speeds up test creation, but my review turns its recording into reliable automation.

✏️ Refining Generated Code

🔧 Modify generated code

  • Replace brittle CSS/XPath locators with role/text based ones where codegen fell back to them.
  • Add real assertions — codegen mostly records actions, not checks.
  • Remove any waitForTimeout(...) — replace with proper auto-waiting locator actions.
  • Extract repeated steps into functions / a Page Object Model instead of one long flat script.
  • Parameterize hardcoded test data (usernames, URLs) instead of leaving literals inline.

⚠️ Why you should NOT blindly use generated code

  • ⚠️ Codegen can fall back to fragile CSS selectors (e.g. nth-child) when no good role/text/testid exists — these break on redesigns.
  • ⚠️ It records exactly what you clicked, not what you meant — no built-in business-logic checks.
  • ⚠️ Output is a flat script — no reuse, no structure, hard to maintain at scale.
  • ⚠️ Doesn't know about your test data strategy — you'll get literal values baked in.
  • ⚠️ Timing quirks in the recorded session (slow network, animations) can leak into the generated script.

💬
🗣️ How I'd say it in an interview
❓ Interviewer asks:Would you use Codegen output directly in a production automation framework?

My answer is no, because generated code is a useful draft rather than a finished, maintainable production test.

The main limitation is Codegen records interactions but does not understand the business outcome that the test must verify.

I first review the locators and replace fragile CSS or XPath selectors whenever stronger accessible locators are available.

Then I add explicit expect assertions so the test validates outcomes instead of merely performing browser actions.

For maintainability, I extract repeated workflows into helpers or page objects rather than keeping one long script.

I also parameterize URLs and test data instead of leaving environment-specific values hardcoded in the test.

Finally, I remove unnecessary fixed waits and rely on Playwright's locator auto-waiting and explicit conditions.

So, in short, I use Codegen to accelerate the first draft, then engineer the checks, structure, and data properly.

🔍 Playwright Inspector

Playwright Inspector is the GUI debugging companion — it lets you step through a test, inspect the page, and try out locators live.

// three ways to open the Inspector PWDEBUG=1 npx playwright test npx playwright test --debug // or inside a test: await page.pause();

🎯 Inspect locators

  • Click the "Pick locator" button, then click any element in the app.
  • Inspector highlights it and shows the suggested locator string instantly.

🐞 Debug actions

  • Step through the test one action at a time using the step-over control.
  • See the live DOM state in the browser at each step — great for catching timing/race issues.
  • Resume, pause, or stop the run at any point.

🧪 Test selectors

  • Type any locator (CSS, XPath, role-based) into the Inspector's locator box.
  • Matching elements get highlighted live in the browser — confirms the locator is correct/unique before you put it in code.

🗣️ How I'd say it in an interview
❓ Interviewer asks:How do you use Playwright Inspector to debug a failing test?

Playwright Inspector is a debugging interface that lets me pause tests, inspect browser state, and try locators interactively.

To open it, I can run tests with --debug, set PWDEBUG=1, or insert await page.pause().

When debugging, I step through actions individually and observe the page state at the exact point of failure.

For locator issues, I use the locator field to check which elements match and see them highlighted in the browser.

This helps me identify incorrect selectors, unexpected page states, and timing problems without guessing from logs alone.

After finding the cause, I update the test or locator and rerun the relevant scenario to confirm the fix.

I use it selectively, because interactive debugging is most useful during investigation rather than unattended CI execution.

So, in short, Inspector helps me reproduce a failure, observe the exact state, and fix the root cause systematically.

Phase 14 — Playwright Codegen & ToolsVS Code Extension

🧩 Playwright VS Code Extension

The official Playwright Test for VS Code extension brings codegen, inspector, and the test runner directly into the editor.

▶️ Run tests

  • A green ▶ icon appears in the gutter next to every test(...) block.
  • Click it to run just that test — or run a whole file/project from the sidebar.
  • Results (pass/fail, screenshots, traces) show inline without leaving the editor.

🐞 Debug tests

  • Set breakpoints directly in the .spec.ts/.spec.js file.
  • Click the debug icon to launch in headed mode, pausing at breakpoints.
  • Step through, inspect variables, and watch the real browser — same idea as Inspector, integrated into VS Code's debugger UI.

🎯 Pick locator

  • Extension button "Pick locator" opens the running browser for the current test.
  • Click an element → the best locator is inserted straight into your editor at the cursor.

📋 Test explorer

  • Sidebar tree view of every test, grouped by file/describe block.
  • Run, debug, or watch any node — a single test, a file, or the whole suite.
  • "Watch mode" reruns affected tests automatically as you edit.

❓ Interviewer asks:How does the Playwright VS Code extension help your automation workflow?

The extension brings Playwright test execution, debugging, and locator discovery directly into the Visual Studio Code editor.

For quick execution, I can use the gutter run icon beside a test or launch tests from Test Explorer.

To investigate failures, I set breakpoints, start debugging, and inspect variables while stepping through the test.

Overall, it reduces context switching between the editor, terminal, and browser during test development and troubleshooting.

So, in short, the VS Code extension keeps test authoring, execution, and debugging in one convenient workflow.

⚠️ Common Mistakes & Gotchas ALWAYS READ

  • ⚠️ Shipping raw codegen output straight to CI — no assertions, brittle selectors.
  • ⚠️ Forgetting codegen falls back to fragile CSS when no role/text/testid exists.
  • ⚠️ Leaving waitForTimeout() calls from a recorded session in the final test.
  • ⚠️ Not realizing .pause() works anywhere in a test, not just at the start.
  • ⚠️ Testing a locator only in the Inspector's box but never confirming it's unique (matches exactly one element).
