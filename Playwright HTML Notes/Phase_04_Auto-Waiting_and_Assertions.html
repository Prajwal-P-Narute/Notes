🎭 Playwright — Auto-Waiting

Phase 4 · Element ActionabilityPage 1

📌 Why Playwright Waits Automatically

Old tools (Selenium) fail if you click an element before it's ready — you had to write manual sleep() or wait code yourself.

Playwright is different: before every action (.click(), .fill()...), it automatically checks the element is actionable — and retries until it is, or times out.

💡 This is Playwright's single biggest reliability advantage — it removes almost all flaky "element not interactable" errors.

🌳 Element Actionability Checks

Before performing an action, Playwright runs through a checklist on the target element. All checks must pass before the action fires.

Attached
Element exists in the DOM (not removed/detached).
Visible
Has non-empty bounding box, no display:none / visibility:hidden.
Stable
Not mid-animation — its position hasn't changed across two frames.
Enabled
Not disabled (no disabled attribute).
Receives Events
Not blocked/covered by another element (e.g. a loading overlay).
🧠 Mnemonic: "A VSER" — Attached, Visible, Stable, Enabled, Receives events. Say it like "advisor" minus the D!

🔁 Auto-Retry Behavior

Playwright doesn't check once — it polls repeatedly until all checks pass or the timeout is hit (default 30s for actions).

Action requested — e.g. .click()
↓
Run actionability checks
↓
❌ Fail → wait a bit → retry
↓
✅ Pass → perform the action
↓
⏱️ Still failing at timeout → throw error
⚠️ Auto-waiting only applies to actions and assertions — it does NOT wait for things like a variable to change in your own JS code.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is auto-waiting in Playwright, and how does it help?”

Auto-waiting means Playwright checks that an element is ready before performing an action.

For a click, it checks that the element is visible, stable, enabled, and able to receive events.

If the element is not ready, Playwright keeps retrying until it is ready or the timeout is reached.

This helps because the test does not act too early while the page is updating.

I usually rely on auto-waiting instead of adding fixed waits.

If it still fails, I investigate why the element never became ready.

So, in short, I rely on auto-waiting and fix the real cause of delays to keep tests reliable.

✅ Assertions & Waiting

Phase 4 · expect(locator)Page 2

📌 Web-First Assertions

expect(locator) assertions are auto-retrying too — they poll until the condition is true or timeout hits. No manual wait needed before asserting.

Common expect(locator) assertions
AssertionChecks for
toBeVisible()Element is visible on the page
toBeHidden()Element is not visible / not attached
toBeEnabled()Element is not disabled
toBeDisabled()Element has the disabled attribute
toHaveText()Exact visible text match
toContainText()Partial text match (substring)
toHaveValue()Input/textarea current value
toHaveAttribute()Specific attribute name+value
toHaveURL()Page URL matches
toHaveTitle()Document title matches
// visibility + text + value checks togetherawait expect(page.locator('#status')).toBeVisible(); await expect(page.locator('h1')).toHaveText('Dashboard'); await expect(page.locator('#msg')).toContainText('Saved'); await expect(page.locator('input#qty')).toHaveValue('3'); await expect(page).toHaveURL(/dashboard/);
💡 Prefer toContainText() over toHaveText() when the surrounding text might change (dates, counters) — it's less brittle.

⚖️ toHaveText vs toContainText

toHaveText()
Must match the entire visible text exactly.
toContainText()
Passes if the text is found anywhere inside.
📌 Note All these assertions already have built-in retry + timeout — that's why they're called "web-first" assertions. You almost never need an explicit wait before one.
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What are web-first assertions in Playwright?”

Web-first assertions are checks that automatically retry until the expected result appears or times out.

For example, I use toBeVisible() to check visibility and toHaveText() to check text.

They are useful because page content may take time to update.

Instead of checking once, Playwright keeps checking the condition for the assertion timeout.

In my tests, I use expect() assertions to verify the page state.

I avoid fixed waits because the assertion can continue as soon as the expected condition is met.

So, in short, I use web-first assertions to verify the result reliably without adding unnecessary manual waits.

⏱️ Explicit Waiting

Phase 4 · Manual wait APIsPage 3

📌 When Auto-Wait Isn't Enough

Sometimes you need to wait for something that isn't tied to an action — a network call, a URL change, a custom condition. That's when explicit waits come in.

Explicit wait APIs
MethodWaits for
waitFor()A locator's state — visible / hidden / attached / detached
waitForLoadState()Page lifecycle — 'load', 'domcontentloaded', 'networkidle'
waitForURL()Page URL to match a pattern (after navigation/redirect)
waitForResponse()A specific network response to arrive
waitForSelector()Legacy — element to appear/disappear (older API, prefer locators now)
// wait for element state, URL change, and a network responseawait page.locator('#spinner').waitFor({ state: 'hidden' }); await page.waitForURL('**/dashboard'); await page.waitForResponse(resp => resp.url().includes('/api/cart') && resp.status() === 200);

🚫 When NOT to Use Explicit Waits

⚠️ Don't add a waitForTimeout(5000) "just to be safe" before a click — that's exactly the flaky-sleep pattern Playwright was built to eliminate.
⚠️ Don't waitForSelector() before an action on the same locator — the action already auto-waits for it.
⚠️ Don't chase "networkidle" everywhere — many modern apps (polling, websockets) never go fully idle, causing your test to hang.
💡 Rule of thumb: reach for an explicit wait only when you're waiting for something not directly tied to a locator action — like a specific API response or a URL change after a redirect.
🧠 Mnemonic: "Don't wait, just act." If you're about to click/fill/assert something, trust auto-wait. Only add explicit waits for network/URL/custom conditions.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “When do you use explicit waits in Playwright?”

I use explicit waits when I need to wait for something beyond a normal element action.

For example, I may wait for a URL change after login or a specific API response.

For URL changes, I use waitForURL() when the navigation is part of the flow.

For API calls, I use waitForResponse() when the test depends on that response.

I avoid fixed waits like waitForTimeout() because they can slow tests down.

Before adding a wait, I check whether Playwright already handles the timing automatically.

So, in short, I use explicit waits only for specific events that auto-waiting cannot cover.

⚠️ Common Mistakes & Gotchas TIER 3 ALWAYS READ

⚠️ Adding waitForTimeout() before clicks "just in case" — defeats the purpose of auto-waiting and slows tests.

⚠️ Using toHaveText() when the text has dynamic parts (timestamps) — causes constant failures; use toContainText() instead.

⚠️ Assuming networkidle always fires — apps with polling/analytics/websockets may never go idle.

⚠️ Calling waitForSelector() right before an action on the same element — redundant, the action already waits.
