🧩 Page Object Model & Framework Design

This phase covers how real automation frameworks are structured: the Page Object Model (POM), folder architecture, reusable components, and data-driven testing.

🗺️ What This Phase Covers

28. What is POM?

Page Object Model (POM) is a design pattern where each web page (or component) of the app under test is represented as a class. That class stores the page's locators and exposes methods to interact with it — tests never touch locators directly.

💡 Think of a Page Object as a "remote control" for a page — the test just presses buttons (login(), searchProduct()) without knowing how the page is wired internally.

Why use POM?

  • Separation of concerns — test logic ≠ UI locators.
  • One place to fix a locator when UI changes.
  • Tests read like plain English (business flow).
  • Encourages reusability across many test files.

Page Classes

A page class models one screen/page. It typically contains: a constructor taking the page object, locator definitions, and action methods.

Locators Inside Page Classes

Locators are declared as class fields/getters so they're defined once and reused by every method in the class — never hard-coded inside test files.

// LoginPage.js — locators declared inside the class class LoginPage { constructor(page) { this.page = page; this.usernameInput = page.locator('#username'); this.passwordInput = page.locator('#password'); this.loginBtn = page.locator('button[type="submit"]'); } }

Reusable Methods

Each page class exposes low-level action methods that wrap Playwright/Selenium calls — e.g. fillUsername(), clickLogin(). These are reused across many tests.

Business Methods

Business methods combine several low-level actions into one meaningful step that mirrors a real user action, e.g. login(user, pass) internally calls fill + fill + click.

// LoginPage.js — reusable + business methods class LoginPage { // ...constructor with locators above... async fillUsername(value) { await this.usernameInput.fill(value); } async fillPassword(value) { await this.passwordInput.fill(value); } // business method — one real user action async login(username, password) { await this.fillUsername(username); await this.fillPassword(password); await this.loginBtn.click(); } } module.exports = { LoginPage };

Using it in a test

const loginPage = new LoginPage(page); await loginPage.login('admin', 'secret123'); await expect(page).toHaveURL('/dashboard');

Avoiding Duplicate Code

  • Never repeat the same locator string in multiple test files — define it once in the page class.
  • Extract common steps (e.g. login, navigation) into business methods, not copy-pasted in every test.
  • Use a Base Page (see Page 4) for actions common to every page — click, type, wait.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is the Page Object Model, and how does it make an automation framework easier to maintain?”

POM is a design pattern where I keep each page's locators and actions inside a dedicated class.

The problem is UI changes can break many tests when locators are copied across test files.

With POM, I define locators once and expose reusable methods such as login().

For example, my test calls loginPage.login(user, pass) without knowing the underlying locator details.

When the UI changes, I update the relevant page class instead of editing every test.

I also keep business methods focused on user actions and avoid oversized page classes.

So, in short, I use POM to separate test intent from UI details, making changes safer and the suite easier to maintain.

🔄 Also asked as: “How do you keep your test suite maintainable?” · “How do you manage UI changes that break tests?”
Follow-up Qs: Low-level method → business method? · When should a page class be split?

29. Better Framework Architecture

A scalable automation framework separates concerns into dedicated folders — this makes the codebase navigable even as it grows to hundreds of tests.

project-root/ ├── tests/ // actual test spec files (*.spec.js) ├── pages/ // Page Object classes (LoginPage, HomePage...) ├── fixtures/ // custom test fixtures / setup-teardown hooks ├── utils/ // helper functions (date utils, string utils) ├── test-data/ // JSON / CSV / Excel data files ├── api/ // API client wrappers for hybrid UI+API tests ├── config/ // env configs, playwright.config.js ├── reports/ // generated HTML/Allure test reports └── package.json
Folder purposes at a glance
FolderPurpose
tests/Actual test specs — call page methods, hold assertions.
pages/One class per page/component — POM lives here.
fixtures/Reusable setup/teardown — e.g. logged-in browser context.
utils/Generic helpers not tied to any page (dates, random data).
test-data/External data files used by data-driven tests.
api/Direct API calls — for seeding data or hybrid checks.
config/Environment URLs, timeouts, credentials per environment.
reports/Auto-generated output — screenshots, traces, HTML reports.
⚠️ Common mistake: dumping locators and test logic into one flat folder — this becomes unmaintainable past ~20 tests.

Flow: how a test uses the structure

test file→imports Page Object→Page Object uses config/↓
reads test-data/→runs assertions→writes to reports/
📌 Rule of thumb: if a new teammate can't find where "login logic" lives within 10 seconds, your architecture needs folders.

30. Reusable Components

Base Page

A Base Page class holds actions common to every page (click, type, wait, screenshot). All other page classes extend it.

// BasePage.js class BasePage { constructor(page) { this.page = page; } async click(locator) { await locator.click(); } async type(locator, text) { await locator.fill(text); } async waitVisible(locator) { await locator.waitFor({ state: 'visible' }); } } class LoginPage extends BasePage { /* ... */ }

Utility Classes & Common Actions/Assertions

ComponentWhat it holds
Utility classesDate formatting, random string/email generators, file readers.
Common actionsGeneric UI actions in BasePage: click(), type(), scrollTo().
Common assertionsWrapped checks e.g. expectVisible(), expectText() for consistent error messages.
ConstantsFixed values — timeouts, roles, status codes — never magic numbers in tests.
Environment configBase URLs & credentials per env (dev/staging/prod), loaded at runtime.
// config/env.js — environment configuration const config = { dev: { baseURL: 'https://dev.app.com' }, staging: { baseURL: 'https://staging.app.com' }, prod: { baseURL: 'https://app.com' } }; module.exports = config[process.env.ENV || 'dev'];
💡 Constants + env config together mean you never hard-code a URL or timeout value inside a test.

31. Data-Driven Testing

Data-driven testing runs the same test logic multiple times with different input data sets — instead of writing one test per data combination.

Data Sources: JSON / CSV / Excel

// test-data/users.json [ { "username": "admin", "password": "secret123", "expected": "dashboard" }, { "username": "guest", "password": "wrongpass", "expected": "error" } ]
  • JSON — best for structured, nested data; native JS parsing.
  • CSV — simple flat tabular data, easy for non-technical testers to edit.
  • Excel — used when QA/business teams maintain test data manually.

Parameterized Tests

Loop over the data set and generate one test per row — this is Playwright/JS's equivalent of TestNG's Data Provider.

// login.spec.js — parameterized test const users = require('../test-data/users.json'); for (const user of users) { test(`login with ${user.username}`, async ({ page }) => { const loginPage = new LoginPage(page); await loginPage.login(user.username, user.password); await expect(page).toHaveURL(new RegExp(user.expected)); }); }

Environment-Specific Data

Keep a separate data file/section per environment (e.g. users.dev.json, users.staging.json) so the same test logic runs safely across environments.

🧠 Mnemonic: "J-C-E, Data's Free" — JSON, CSV, Excel are the 3 common data sources; picking the right one keeps your data layer "free" of hard-coded values in test code.
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is data-driven testing, and how would you implement it in Playwright?”

Data-driven testing is running the same test logic with multiple input sets instead of duplicating test scripts.

The reason this matters is one flow may need valid, invalid, boundary, and other input combinations.

Common data sources are JSON, CSV, and Excel, chosen according to the team's needs.

For data, I keep inputs outside the test logic so cases are easier to review and update.

In Playwright, I can loop through the data and define a separate test for each case.

I also check expected outcomes for each row and keep environment-specific data separate when needed.

So, in short, I separate test data from test logic to reduce duplication and make coverage easier to extend reliably.

🔄 Also asked as: “How do you test one flow with many inputs?” · “How do you reduce duplicate test cases?”
Follow-up Qs: Environment-specific data → how is it selected? · Negative test row → how is failure asserted?

⚠️ Common Mistakes & Gotchas
  • ⚠️ Hard-coding locators inside test files instead of the page class.
  • ⚠️ Skipping a Base Page — leads to duplicated click/type logic everywhere.
  • ⚠️ Mixing business methods and low-level methods with no clear naming split.
  • ⚠️ Hard-coding URLs or credentials instead of using env config.
  • ⚠️ Flat folder structure with no pages/ vs tests/ separation.
  • ⚠️ Not separating test data by environment — causes flaky cross-env runs.
