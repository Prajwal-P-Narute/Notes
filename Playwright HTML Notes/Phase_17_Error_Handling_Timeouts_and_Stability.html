60. Handling Flaky Tests Critical

A flaky test = passes sometimes, fails sometimes — same code, no code changes.

🔍 Root Causes of Flakiness

🎯 Locator Issues

  • Unstable XPath / CSS selectors
  • Dynamic IDs that change per render
  • Class names tied to build hashes
  • Prefer: data-testid, role, text

⏱️ Timing Issues

  • Element not in DOM yet → click fails
  • Animation not complete → assert fails
  • API response delayed → state stale
  • Fix: use waitFor / auto-wait

📡 Network Instability

  • 3rd-party API timeouts
  • CI slow network / DNS lag
  • Fix: mock network calls
  • Use page.route() to stub

🗄️ Shared Data / State

  • Tests sharing same DB records
  • Left-over cookies/localStorage
  • Order-dependent test execution
  • Fix: isolated test data per test
⚠️ Hard waits like page.waitForTimeout(3000) are the #1 anti-pattern — they don't wait for a condition, they just pause. Tests still fail on slow machines and waste time on fast ones.

✅ Proper Fix Strategies

Flakiness Cause → Correct Fix
CauseWrong Approach✅ Right Fix
Element not readywaitForTimeout(2000)locator.waitFor() or auto-wait
Bad selectorXPath with indexgetByRole() / data-testid
Shared test dataSame user for all testsUnique user per test via factory
Network slowIncrease global timeoutMock with page.route()
Animation mid-flightStatic sleepexpect(el).toBeVisible() (retries)
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you identify and fix flaky tests in Playwright?

A flaky test is one that passes sometimes and fails sometimes without any code changes.

The main causes are unstable locators, timing issues, network delays, and shared test data or state.

For timing issues, I rely on Playwright's auto-waiting and condition-based waits instead of fixed sleeps.

For stable locators, I prefer role-based locators or reliable test IDs over dynamic selectors.

When the network is unstable, I can mock requests with page.route() where appropriate.

For shared state, I create isolated test data and avoid tests depending on execution order.

So, in short, I investigate the root cause instead of hiding flakiness, making test results trustworthy for the team.

🎭 Phase 17 — Error Handling & Stability Topic 61: Retry Mechanisms

61. Retry Mechanism Essential

Retrying is NOT the same as fixing flakiness — it's a safety net, not a solution. Fix the root cause first; retry catches unavoidable noise.

📌 Three Layers of Retry in Playwright

Test Retries
(Full test re-runs)
Configured in playwright.config.ts. Re-runs the entire test from scratch when it fails.
  • Use sparingly — masks real problems
  • Always set retries to 0 locally (only in CI)
Assertion Retries
(Built-in auto-retry)
expect(locator).toBeVisible() polls internally until the condition is met or expect.timeout is hit. This is Playwright's superpower — use it always.
Conditional Retry
(Custom logic)
Retry a specific action (e.g., flaky API call) with a custom loop — not the whole test. Use waitFor with a condition or a helper retry wrapper.

⚙️ Config: Test-Level Retries

// playwright.config.tsexport default defineConfig({ retries: process.env.CI ? 2 : 0, // 2 retries in CI, 0 locally reporter: [ ['html'], ['junit', { outputFile: 'results.xml' }] ], });

🔄 Custom Retry Helper

// helpers/retry.ts — retry a flaky async action up to N timesasync function withRetry<T>( fn: () => Promise<T>, retries = 3, delay = 500 ): Promise<T> { for (let i = 0; i < retries; i++) { try { return await fn(); } catch (e) { if (i === retries - 1) throw e; await new Promise(r => setTimeout(r, delay)); } } }

🏭 CI Retry Strategy

  • Set retries = 2 in CI — absorb genuine environment noise
  • Track "passed on retry" rate — if >5%, investigate root cause
  • Use quarantine tags to isolate known-flaky tests from blocking the pipeline
  • Playwright HTML report shows retry attempt count per test
  • Never rely on retries to cover up assertion logic bugs
💡 Golden Rule: If a test needs retries to pass reliably, it's telling you something — listen. Retries buy time, not reliability.
🔄
🗣️ How I'd say it in an interview
❓ Interviewer asks: What retry mechanisms does Playwright provide?

Playwright supports assertion retries, whole-test retries, and custom retry logic for specific operations.

At the assertion level, auto-retrying assertions such as expect(locator).toBeVisible() keep checking until they pass or time out.

At the test level, Playwright can rerun the entire test after a failure.

In my configuration, I can enable retries in CI while keeping local retries at zero.

For a specific operation, a custom helper can retry an action or API call when that behavior is appropriate.

I treat retries as a safety net and investigate tests that frequently pass only on a retry.

So, in short, retries can absorb occasional noise, but fixing the underlying cause is what makes a suite reliable.

62. Timeout Management Must Know

Playwright has 4 separate timeout types — each controls a different part of the test lifecycle. Confusing them is one of the most common mistakes.

📊 Timeout Types at a Glance

Timeout hierarchy — outer wraps inner
Timeout TypeDefaultScopeOverride Location
Test Timeout30,000 msEntire test + hooksconfig.timeout / test.setTimeout()
Expect Timeout5,000 msSingle assertion pollconfig.expect.timeout / option in call
Action Timeout30,000 msSingle action (click/fill)actionTimeout in config/per call
Navigation Timeout30,000 msPage load / navigationnavigationTimeout in config/per call

⚙️ Config Examples

// playwright.config.ts — all timeout settingsexport default defineConfig({ timeout: 60_000, // test timeout (ms) expect: { timeout: 8_000 }, // assertion polling timeout use: { actionTimeout: 10_000, // click / fill / etc. navigationTimeout: 30_000, // page.goto / reload }, });
// Per-test and per-call overridestest('slow e2e flow', async ({ page }) => { test.setTimeout(120_000); // override for this test only await page.goto('/checkout', { timeout: 20_000 }); await expect(page.locator('#confirm')) .toBeVisible({ timeout: 15_000 }); // per-assertion override });

💡 Tip: A test timeout should be your last line of defence. If tests regularly approach the timeout limit, your test is doing too much — split it or fix the slow dependency.
⏱️
🗣️ How I'd say it in an interview
❓ Interviewer asks: What are the different timeout types in Playwright?

Playwright has four timeout types: test, expect, action, and navigation timeouts.

The test timeout limits the overall test and its hooks.

The expect timeout controls how long an assertion polls for its expected condition.

The action timeout limits an individual action such as clicking or filling a field.

The navigation timeout limits how long a navigation operation can take.

I configure them globally when useful and override a specific timeout for slower steps when needed.

So, in short, I adjust the timeout that matches the failure instead of increasing every timeout blindly.

🎭 Phase 17 — Error Handling & Stability Topic 63: Test Isolation

63. Test Isolation Must Know

Each test should be completely independent — able to run alone, in any order, in parallel, and still pass. Isolation = reliability.

🧱 Four Pillars of Isolation

1️⃣ Independent Tests

  • No test A creates data that test B reads
  • No shared global state between tests
  • Each test sets up its own preconditions (use beforeEach)
  • Test failure doesn't cascade to next test
// ✅ Good — test creates its own usertest('user can update profile', async ({ page, request }) => { const user = await createTestUser(request); // unique per test await loginAs(page, user); // ... test logic await deleteUser(request, user.id); // cleanup });

2️⃣ Context Isolation

Every test gets a fresh browser context — no shared cookies, sessions, or local storage between tests.

  • Playwright creates a new context per test by default ✅
  • Sharing contexts across tests = authentication leak risk
  • Use browser.newContext() explicitly for custom setups
  • Storage state can be pre-set per context (e.g. logged-in state JSON)
// Reuse authenticated state per test, not per sessionconst context = await browser.newContext({ storageState: 'auth/admin.json', // pre-saved login state }); const page = await context.newPage(); // ... test, then close context await context.close();

3️⃣ Data Cleanup

  • Clean up in afterEach / afterAll — never in beforeEach only
  • Use API calls (not UI) for setup & teardown — it's 10× faster
  • Consider DB transaction rollback for integration tests
  • Use random/UUID-based test data names to avoid collision

4️⃣ Parallel-Safe Tests

Tests run in parallel workers — they must not share resources.

❌ Parallel-Unsafe

  • Shared test user (same email)
  • Single DB record modified by all
  • Fixed port numbers in test code
  • Global counters / file writes

✅ Parallel-Safe

  • Unique user per test (UUID email)
  • Isolated DB rows / namespaces
  • Dynamic ports or mocked network
  • Worker-scoped fixtures for shared setup
💡 Worker-scoped fixtures in Playwright run once per worker process (not per test) — perfect for expensive setup like server spin-up that's safe to share within one worker.
🧱
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you ensure test isolation in Playwright?

Test isolation means each test can run independently, in any order, or in parallel without affecting another test.

For browser state, Playwright provides a fresh browser context per test by default.

For test data, I create unique records for each test and clean them up afterward.

For setup and teardown, I prefer API calls where appropriate because they are faster than UI workflows.

For parallel execution, I avoid shared users, mutable database records, fixed ports, and shared files.

When setup is expensive, I consider worker-scoped fixtures only for resources that are safe to share within that worker.

So, in short, I isolate browser state, test data, and shared resources so tests remain independent and parallel-safe.

🏗️ Recommended Project Structure for Isolation

  • Fixtures folder: base fixture extending Playwright's test with context + cleanup wired in
  • Helpers: createUser(), deleteUser(), loginAs() — API-based, not UI
  • Test data factory: generates unique data with UUID per invocation
  • Auth state files: pre-login JSON for each role (admin, user, guest) — generated once in global setup
  • global-setup.ts: create shared resources (auth tokens), save to file
  • global-teardown.ts: delete shared resources created by global setup
💡 Trace on First Retry: Set trace: 'on-first-retry' in config so you don't collect traces every run (slow) but always capture when something goes wrong.
⚠️ Never use test.only() in CI — it silently skips all other tests. Add a lint rule to fail CI if test.only is committed.

⚠️ Section 4 — Common Mistakes & Gotchas TIER 3 ⚡ ALWAYS READ
  • Using waitForTimeout() — it makes tests slow AND still flaky. Never use it.
  • Setting retries in local development — hides bugs you need to see immediately.
  • Confusing test timeout vs expect timeout — they are completely separate; tuning the wrong one has zero effect.
  • Using the same test user for all parallel tests — causes race conditions and mysterious failures.
  • Cleaning up data in beforeEach only — if cleanup fails before the test, you get stale data from a previous run.
  • Forgetting await context.close() after manual context creation — browser context leak.
  • Dynamic IDs / class hash selectors like #app-abc123 — break every build. Use data-testid.
  • Treating a high retry-pass rate as acceptable — if retries > 5% of runs, you have a real flakiness problem.
  • Using UI for test data setup — UI is 10–20× slower than API calls and introduces its own flakiness.
  • Committing test.only() — silently skips every other test in CI.
🧠 Section 6 — Memory Tricks & Last-Minute Tips TIER 3 — last stop
🧠 Mnemonic — Flaky causes
L.T.S.N. = Locators · Timing · Shared data · Network
"Let Tests Stay Neat" — if a test is flaky, check these four in order.
🧠 Analogy — Retry vs Fix
Retry = putting a bandage on a leaky pipe. It stops the dripping for now, but the pipe still needs a plumber. Fix the root cause (the pipe); retry is your emergency bandage only.
🧠 Timeout Hierarchy
Think outer → inner: Test timeout wraps everything. Inside it: Action/Nav/Expect timeouts. If the inner timeout fires first, the test fails before Test timeout is hit.
🧠 Isolation = Hotel Room Rule
Each test gets a fresh room — clean sheets, empty minibar. They don't share towels with the previous guest. That's browser context isolation.
