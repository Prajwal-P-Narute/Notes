📌 Phase 9 — Playwright Fixtures

Built-in Fixtures & Core Concepts
🔩 What is a Fixture?
💡 A fixture is a piece of setup/teardown code that Playwright injects into your test automatically. Think of it like a smart plug — the test doesn't create it; it's just plugged in when needed.
Why fixtures?
  • Removes boilerplate from test bodies
  • Reusable setup across many tests
  • Automatic cleanup — yield marks the teardown point
  • Composable — fixtures can depend on other fixtures
  • Scoped — control when they're created & destroyed
How it works
Playwright uses test.extend() to add fixtures. The test runner injects the fixture based on the parameter name in the test function signature.
🎁 Built-in Fixtures

Playwright ships with these built-in fixtures — always available without any config:

✅ Key rule: each built-in fixture is automatically torn down after the test finishes — no manual cleanup needed.

🔧 Custom Fixtures

test.extend() · Test vs Worker Scope
✏️ Creating Custom Fixtures
Use test.extend({}) to define your own fixtures. Export the result as your custom test object — then import it everywhere instead of Playwright's default test.
// fixtures/base.ts — define custom fixtureimport { test as base } from '@playwright/test'; type MyFixtures = { todoPage: TodoPage; }; export const test = base.extend<MyFixtures>({ todoPage: async ({ page }, use) => { // ↑ "page" is a built-in fixture — Playwright injects it const todo = new TodoPage(page); await todo.goto(); // setup BEFORE yield await use(todo); // ← yield point — test runs here await todo.cleanup(); // teardown AFTER yield }, }); export { expect } from '@playwright/test';
⚠️ Pattern: Code before await use() = setup. Code after = teardown. The use() call is where the test body executes.
// my-test.spec.ts — using the custom test objectimport { test, expect } from './fixtures/base'; test('adds a todo item', async ({ todoPage }) => { // todoPage is already set up! await todoPage.addItem('Buy milk'); await expect(todoPage.items).toContainText('Buy milk'); });
⚖️ Test Fixtures vs Worker Fixtures

🧪 Test Fixtures

  • Created once per test
  • Each test gets a fresh instance
  • Default scope — most fixtures are this
  • Examples: page, context, custom page objects
  • Defined with async ({...}, use) => {}

👷 Worker Fixtures

  • Created once per worker process
  • Shared across all tests in the same worker
  • Great for expensive setup (DB connection, browser launch)
  • Examples: browser, DB pool, auth token
  • Must declare scope: 'worker'
// Worker-scoped fixture — shared across tests in the same workerexport const test = base.extend<{}, { dbPool: Pool }>({ // Worker fixtures go in the SECOND type argument dbPool: [async ({}, use) => { const pool = await Pool.create({ size: 5 }); await use(pool); // all tests in worker share this pool await pool.close(); }, { scope: 'worker' }], // ← explicit worker scope });
💡 Rule of thumb: if the fixture is stateless or cheap to recreate → test scope. If it's expensive (network, DB, binary launch) → worker scope.

🔗 Fixture Scope & Dependencies

Scope · Dependency · Auth Fixtures
🎯 Fixture Scope Deep Dive
ScopeCreatedDestroyedUse When
'test' (default)Before each testAfter each testPage objects, test-specific data
'worker'Before first test in workerAfter last test in workerBrowser, DB pool, heavy singletons
📌 Workers in Playwright = separate Node.js processes. By default, Playwright runs tests in parallel across multiple workers. Worker fixtures are per-process, NOT global.
🔗 Fixture Dependencies

Fixtures can depend on other fixtures — Playwright resolves them automatically like a DI container. Just name the dependency in the destructure parameter.

// Fixture depending on another fixtureexport const test = base.extend<{ loginPage: LoginPage; authPage: AuthPage }>({ loginPage: async ({ page }, use) => { // depends on built-in "page" await use(new LoginPage(page)); }, authPage: async ({ loginPage }, use) => { // depends on loginPage! await loginPage.login('admin', 'pass'); // uses loginPage fixture await use(new AuthPage(loginPage)); }, });
🔵 page (built-in) created
↓
🟢 loginPage fixture — receives page
↓
🟡 authPage fixture — receives loginPage
↓
🟣 Test body runs with authPage
↓
🔁 Teardown in reverse order (authPage → loginPage → page)
🔐 Authentication Fixtures

The most common real-world fixture pattern — save auth state once, reuse across all tests:

// auth fixture — storageState pattern (recommended)import { test as base, chromium } from '@playwright/test'; export const test = base.extend<{}, { workerStorageState: string }>({ // Worker scope = login ONCE per worker (not per test!) workerStorageState: [async ({ browser }, use) => { const id = test.info().parallelIndex; const fileName = `playwright/.auth/user-${id}.json`; const page = await browser.newPage(); await page.goto('https://app.example.com/login'); await page.fill('#email', 'user@test.com'); await page.fill('#pass', 'secret'); await page.click('button[type=submit]'); await page.context().storageState({ path: fileName }); await page.close(); await use(fileName); }, { scope: 'worker' }], // Override context to use saved auth state storageState: async ({ workerStorageState }, use) => await use(workerStorageState), });
⚠️ Never hard-code credentials in tests. Use .env files or environment variables. The auth fixture is the right place to load them.

📄 Page Fixtures & Custom Test Setup

Page Fixtures · test.extend() Patterns
📄 Page Fixtures

A page fixture wraps the built-in page to add pre-navigation, viewport config, mock routes, or any custom base state before every test.

// Override the built-in "page" fixtureexport const test = base.extend<{ page: Page }>({ page: async ({ page }, use) => { // Set viewport for all tests using this custom test await page.setViewportSize({ width: 1280, height: 720 }); // Mock all analytics calls await page.route('**/analytics/**', r => r.abort()); // Navigate to base URL await page.goto('/'); await use(page); // test runs here with preconfigured page }, });
🏗️ Custom Test Object — test.extend()
What is it?
Your project's own custom test function — it wraps Playwright's base test and adds all your fixtures. Every spec file imports from this instead of @playwright/test.
Pattern
  • Create fixtures/base.ts — single source of truth
  • Export custom test and expect
  • Chain .extend() calls to combine fixture sets
// fixtures/base.ts — THE custom test objectimport { test as base, expect } from '@playwright/test'; import { LoginPage } from '../pages/LoginPage'; import { DashboardPage } from '../pages/DashboardPage'; import { ApiClient } from '../utils/ApiClient'; type Fixtures = { loginPage: LoginPage; dashboardPage: DashboardPage; apiClient: ApiClient; }; export const test = base.extend<Fixtures>({ loginPage: async ({ page }, use) => { await use(new LoginPage(page)); }, dashboardPage: async ({ page }, use) => { await use(new DashboardPage(page)); }, apiClient: async ({ request }, use) => { const client = new ApiClient(request, process.env.BASE_URL!); await use(client); // no explicit teardown — request context handles it }, }); export { expect };
💡 Best practice: always export { expect } from your base fixture file so test files have a single import for both test and expect.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks:“How do you create and use custom fixtures in Playwright?”

I create custom fixtures with test.extend() when built-in fixtures do not cover project-specific needs.

The reason I use them is to centralize reusable setup for page objects, API clients, and authentication.

In my framework, I define these fixtures in a shared base.ts file.

Then each test imports the extended test object and requests fixtures through its parameters.

For example, a loginPage fixture can create a LoginPage using the supplied page.

I also use the fixture's use() function to provide the resource and control teardown timing.

So, in short, I use custom fixtures to remove duplication and keep setup consistent as the framework grows.

💉 Inject Page Objects & API Clients

Injection · Reusable Setup · Best Practices
📦 Injecting Page Objects via Fixtures
Why inject?
Tests describe what to test — fixtures handle how to set up. This is the Dependency Injection principle applied to tests. Tests become shorter, more readable, and maintenance-proof.
Pattern
1. Page Object class takes Page in constructor
2. Fixture creates the class instance
3. Fixture calls use(instance)
4. Test receives it in parameters
// Full DI pattern: Page Object + Fixture + Test // 1. Page Object class LoginPage { constructor(private page: Page) {} async login(user: string, pass: string) { await this.page.fill('#email', user); await this.page.fill('#password', pass); await this.page.click('button[type=submit]'); } } // 2. Fixture injects it export const test = base.extend<{ loginPage: LoginPage }>({ loginPage: async ({ page }, use) => use(new LoginPage(page)), }); // 3. Test is clean — no setup noise test('user can log in', async ({ loginPage }) => { await loginPage.login('user@test.com', 'secret'); });
🌐 Injecting API Clients

Use the built-in request fixture as the base for an API client fixture. This keeps HTTP calls reusable and consistent across tests.

// ApiClient class + fixtureclass ApiClient { constructor( private req: APIRequestContext, private base: string ) {} async createUser(data: UserPayload) { return this.req.post(`${this.base}/users`, { data }); } async getUser(id: number) { return this.req.get(`${this.base}/users/${id}`); } } // Fixture apiClient: async ({ request }, use) => { await use(new ApiClient(request, process.env.API_URL!)); }
♻️ Reusable Setup Patterns
Pattern 1 — Extend chain
  • Create authFixtures, pageFixtures, apiFixtures separately
  • Merge: base.extend(authFix).extend(pageFix)
  • Keeps fixture files small & focused
Pattern 2 — mergeTests()
  • Playwright v1.39+ mergeTests() utility
  • mergeTests(authTest, pageTest)
  • Cleanly combines fixture sets
// mergeTests — Playwright v1.39+import { mergeTests } from '@playwright/test'; import { test as authTest } from './fixtures/auth'; import { test as pageTest } from './fixtures/pages'; export const test = mergeTests(authTest, pageTest); // clean!
✅ Golden rule: your spec files should only import from ./fixtures/base (or merged fixture). Never import from @playwright/test directly in spec files — this ensures all fixtures are available everywhere.
⚠️ Auto fixture: set { auto: true } in a fixture definition to run it for EVERY test without the test needing to declare it. Use sparingly — only for things that truly must apply everywhere (e.g. console error listener).

TIER 3 ⚠️ Common Mistakes & Gotchas ALWAYS READ
  • ⚠️ Forgetting await use() — fixture never yields, test never runs, setup hangs forever
  • ⚠️ Putting worker-scoped fixtures in the first type arg — they silently become test-scoped! Use 2nd type arg and declare scope: 'worker'
  • ⚠️ Importing from @playwright/test directly in spec files — your custom fixtures won't be available
  • ⚠️ Using auto: true for fixtures that are expensive — they run for EVERY test including ones that don't need them
  • ⚠️ Not awaiting async operations in teardown (after use()) — cleanup silently fails
  • ⚠️ Storing auth state at a fixed path — parallel workers overwrite each other; use parallelIndex in the filename
  • ⚠️ Fixture teardown order is the reverse of setup — don't assume a specific order for independent fixtures
TIER 3 🧠 Memory Tricks & Last-Minute Tips
🧠 use() = async yield: "Everything before use() is BEFORE the test, everything after is AFTER the test." It's like a sandwich — setup is the top slice, teardown is the bottom, the test is the filling.
🧠 Scope memory trick: "Test scope = fresh towel, Worker scope = shared gym shower." Test scope gives everyone their own. Worker scope everyone on the shift shares one.
🧠 auth.json tip: Name it user-${parallelIndex}.json — think of parallel workers as parallel queues at a coffee shop. Each queue needs its own authenticated session.
