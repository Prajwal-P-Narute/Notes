🎭 Playwright — Phase 2: LocatorsUnderstanding Locators

🔍 What is a Locator?

Definition: A Locator is a Playwright object that represents a way to find element(s) on a page. It does not immediately find the element — it's a lazy recipe for finding elements, not a fixed DOM snapshot.
// Create a locator — nothing is queried yet const btn = page.getByRole('button', { name: 'Submit' }); // Action triggers actual DOM query + auto-wait await btn.click();

⚖️ Locator vs Selenium WebElement

Key Differences
FeaturePlaywright LocatorSelenium WebElement
Queried when?At action time (lazy)At findElement() call (eager)
Stale element?❌ Never stale — re-queried each time⚠️ Throws StaleElementReferenceException
Auto-waiting?✅ Built-in (visibility, enabled, stable)❌ Manual waits required
Re-evaluation?✅ Re-evaluates on each action❌ Fixed DOM reference
Multiple elements?Returns all matching → use .nth()Use findElements() → List
Strict mode?✅ Fails if multiple match (strict)❌ Returns first silently

⏳ Auto-Waiting — The Magic

Before every action, Playwright automatically waits for the element to be:

✅ Attached to DOM
✅ Visible
✅ Stable (not animating)
✅ Enabled (not disabled)
✅ Receives events
✅ Not covered by overlay
💡 No more Thread.sleep() or explicit waits! — Playwright handles it all internally.

🔁 Re-evaluation & Stability

Re-evaluation
Every time you call an action (.click(), .fill()), the locator queries the DOM again fresh. If DOM changed, it finds the new element — no stale reference ever.
Locator Stability
A locator is "stable" when it consistently points to the same logical element across page reloads and dynamic updates. Prefer semantic attributes (role, label, test-id) over DOM-structure-based selectors.
Strict Mode
If your locator matches more than one element, Playwright throws an error. This prevents silent bugs where the wrong element is acted upon.
📌 Key Insight: Think of a Locator as a "saved search query," not a "saved result." It runs the query fresh every time you use it!
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is a Locator in Playwright, and how is it different from a Selenium WebElement?”

A Playwright locator is a lazy recipe for finding elements on a page.

The problem it solves is stale elements and manual waits that older tools forced on us.

What that means is it does not touch the DOM when I create it, only when I act.

Before every action, it auto-waits until the element is visible, stable, and enabled.

Because it re-queries each time, it never goes stale like a Selenium WebElement.

In strict mode, if my locator matches more than one element, it throws an error.

So, in short, a locator finds elements when needed and handles waiting automatically, making tests more reliable without manual sleeps.

🏷️ Built-in Locators — Part 1

💡 Philosophy: Always prefer user-facing attributes (what the user sees / interacts with) over internal DOM structure. Makes tests resilient to CSS/HTML refactors.

① getByRole() — Most Powerful 🌟

Finds elements by their ARIA role — the way assistive technology sees the page.

// Buttons page.getByRole('button', { name: 'Submit' }) // Links page.getByRole('link', { name: 'Home' }) // Headings page.getByRole('heading', { name: 'Welcome', level: 1 }) // Checkboxes page.getByRole('checkbox', { name: 'Accept Terms' }) // name can be a regex too! page.getByRole('button', { name: /submit/i })
✅ Best for: buttons, links, checkboxes, radios, menus, dialogs, headings — anything with semantic HTML

② getByText()

Finds elements by their visible text content.

// Exact match (default: exact=true for string) page.getByText('Welcome back') // Partial match — pass a regex page.getByText(/welcome/i) // Explicit partial match page.getByText('Welcome', { exact: false })
⚠️ Gotcha: Matches any element containing that text — can be too broad. Prefer getByRole when possible.

③ getByLabel()

Finds form inputs by their associated <label> text.

// Finds <input> associated with label "Email" page.getByLabel('Email') page.getByLabel('Password').fill('secret')
🔗 Works with: for/id pairing, aria-label, aria-labelledby, and wrapping labels

④ getByPlaceholder()

Finds inputs by their placeholder attribute text.

page.getByPlaceholder('Enter your email').fill('user@test.com') page.getByPlaceholder(/search/i)
⚠️ Note: Use when no visible label exists. If a visible label exists, prefer getByLabel() — more accessible & semantic.

🏷️ Built-in Locators — Part 2

⑤ getByAltText()

Finds elements (usually <img>) by their alt attribute.

// Find an image by alt text page.getByAltText('Company logo') // Also works for role="img" with aria-label await expect(page.getByAltText('Profile picture')).toBeVisible()

⑥ getByTitle()

Finds elements by their title attribute (tooltip text).

page.getByTitle('Close dialog') // Useful for icon buttons that have no visible text await page.getByTitle('Delete item').click()

⑦ getByTestId() — Testing's Safety Net

Finds by data-testid attribute (configurable). Best for elements with no good semantic selector.

// HTML: <button data-testid="login-btn">...</button> page.getByTestId('login-btn') // Custom attribute in playwright.config.ts // testIdAttribute: 'data-cy' or 'data-qa' page.getByTestId('submit-form').click()
⚙️ Configure in playwright.config.ts: use: { testIdAttribute: 'data-cy' }

🎭 Playwright — Phase 2: LocatorsCSS & XPath

🎨 CSS & XPath Selectors

⚠️ Use these when built-in locators can't uniquely identify the element. User-facing locators are still preferred!

🎨 CSS Selectors in Playwright

Use page.locator('css=selector') or just page.locator('selector') (CSS is default).

// Class selector page.locator('.submit-btn') // ID selector page.locator('#username') // Attribute selector — exact match page.locator('input[type="email"]') // Attribute contains value page.locator('[class*="btn-primary"]') // Starts-with attribute page.locator('[data-id^="item-"]') // Ends-with attribute page.locator('[href$=".pdf"]') // Child combinator: li directly inside ul.menu page.locator('ul.menu > li') // Descendant: any p inside .card page.locator('.card p') // nth-child pseudo-class page.locator('tr:nth-child(2)') // :has — Playwright CSS extension! page.locator('article:has(h2)')

🌳 XPath Selectors

Use page.locator('xpath=...') or just supply the XPath string starting with //.

// Basic element by attribute page.locator('//button[@id="login"]') // Element containing text page.locator('//h2[contains(text(), "Welcome")]') // Ancestor-descendant page.locator('//div[@class="form"]//input') // Sibling navigation (XPath axes) page.locator('//label[text()="Email"]/following-sibling::input') // Index-based (1-indexed in XPath) page.locator('(//button[text()="Edit"])[2]')
⚠️ XPath is fragile — changing HTML structure breaks it. Use only when CSS & semantic locators fail, e.g., parent traversal (.. / ancestor::).

• Must navigate to a parent
• Complex text-based conditions

🗣️ How I'd say it in an interview
❓ Interviewer asks: “CSS vs XPath in Playwright: when do you use which?”

CSS selectors are my fallback when built-in locators can't pick out an element.

The reason is they are short, readable, and slightly faster than XPath.

I use XPath only when I must move up to a parent, which CSS can't do cleanly.

The problem with both is they depend on HTML structure, so refactors break them.

To avoid that, I stick with getByRole and getByLabel wherever I can.

I do this because user-facing locators describe intent, not the DOM layout.

So, in short,I prefer user-facing locators because they are more reliable and easier to maintain.

🎭 Playwright — Phase 2: LocatorsAdvanced Locator Operations

🔧 Advanced Locator Operations

① locator() — Base Method

The foundation for all CSS/XPath/text locating. Can also be called on a locator to scope it.

// Scoped locator: find button inside .modal only const modal = page.locator('.modal'); const btn = modal.locator('button'); // scoped search

② filter() — Refine a Locator

Narrows down a set of matched elements by an extra condition — hasText or has.

hasText

// All rows that contain "Admin" page.locator('tr') .filter({ hasText: 'Admin' }) // Regex version .filter({ hasText: /admin/i })

has

// All .card that contain a button page.locator('.card') .filter({ has: page.locator('button') })
💡 filter() returns a new locator — it does NOT resolve the list yet. Still lazy!

③ Picking from Multiple Matches

const rows = page.locator('tr'); rows.first() // → first match (0-indexed) rows.last() // → last match rows.nth(2) // → 3rd row (0-indexed!) // Count all matches const count = await rows.count();
⚠️ nth() is 0-indexed! nth(0) = first, nth(1) = second, etc.

④ Chaining Locators

Chain locators to progressively narrow scope — each step scopes the next.

// Chain: find 3rd product card, then its "Add to Cart" button page .locator('.product-card') .nth(2) .getByRole('button', { name: 'Add to Cart' }) .click()

⑤ Combining Locators — and() & or()

// AND: element must match BOTH locators page.locator('button').and(page.locator('.primary')) // OR: element matches either locator page.getByRole('button').or(page.getByRole('link'))

🎭 Playwright — Phase 2: LocatorsStrict Mode & Multiple Elements

🔒 Strict Mode & Multiple Elements

Strict Mode

Rule: Actions (.click(), .fill(), etc.) require exactly ONE matching element. If multiple match → throws an error!
// ❌ Throws if multiple buttons exist await page.locator('button').click(); // Error if >1 match // ✅ Explicitly target the right one await page.getByRole('button', { name: 'Submit' }).click(); // ✅ Or use nth() to disambiguate await page.locator('button').nth(0).click();

Handling Multiple Elements — Assertions & Iteration

const items = page.locator('.todo-item'); // Count assertion await expect(items).toHaveCount(5); // Assert all texts await expect(items).toHaveText(['Buy milk', 'Walk dog']); // Iterate over each element const count = await items.count(); for (let i = 0; i < count; i++) { await items.nth(i).click(); } // Get all text contents at once const texts = await items.allTextContents();

🔗 Advanced Chaining + Filter Combo

// Find the row containing "John", then click Edit in that row const row = page .locator('tr') .filter({ hasText: 'John' }); await row.getByRole('button', { name: 'Edit' }).click();
💡 This pattern — locator → filter → scoped locator — is the most powerful and readable approach for table rows, list items, and cards.
✅ Methods that work on all matches (no strict mode restriction):
count() · all() · allTextContents() · allInnerTexts() · toHaveCount()
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is strict mode, and how do you handle multiple matching elements?”

Strict mode means Playwright throws an error if an action's locator matches more than one element.

The problem it prevents is silently clicking the wrong element.

To fix a strict mode error, I make the locator more specific, instead of adding .first() blindly.

For tables and lists, I use locator('tr').filter({hasText:'John'}) and scope another locator inside it.

When I really need one of many, I use nth(), which is zero-indexed.

To check many elements, I use toHaveCount() and allTextContents().

So, in short,strict mode helps me avoid interacting with the wrong element.

⚡ Dynamic Locators

🔥 Challenge: IDs, classes, and URLs change dynamically at runtime. Your locator must survive these changes!

① Dynamic IDs — The Fragility Trap

// ❌ FRAGILE — ID generated at runtime changes each render page.locator('#comp-7x9kq4') // breaks next render! // ✅ STABLE — use stable attribute or role instead page.getByRole('button', { name: 'Login' }) page.locator('[data-testid="login-btn"]')

② Dynamic Classes

// ❌ Class has random suffix: "btn-xT45qr" page.locator('.btn-xT45qr') // ❌ breaks // ✅ Use contains: partial stable class name page.locator('[class*="btn-submit"]') // ✅ Or use semantic approach page.getByRole('button', { name: 'Submit' })

③ Partial Text Matching

// ✅ Regex — stable even if text has dynamic suffix page.getByText(/Order #\d+/) // "Order #12345" ✅ // ✅ filter with partial text page.locator('.notification') .filter({ hasText: 'uploaded successfully' })

④ Data Attributes — The Gold Standard 🥇

Ask devs to add data-testid / data-cy / data-qa — these are:

  • ✅ Never changed by CSS refactors
  • ✅ Never changed by functional changes
  • ✅ Explicit contract between dev & tester
// HTML: <button data-testid="checkout-btn">Pay Now</button> page.getByTestId('checkout-btn') // Attribute selector alternative page.locator('[data-testid="checkout-btn"]')

data-testid🟢 Very HighPurpose-built, never auto-changed
Form label🟢 HighUser-visible text
Placeholder text🟡 MediumMay be internationalised
CSS class (semantic)🟡 MediumMay be refactored
Dynamic ID🔴 Very LowGenerated, changes per render
Structural XPath🔴 Very LowBreaks on any DOM restructure

🗣️ How I'd say it in an interview
❓ Interviewer asks: “How do you handle dynamic IDs, classes, and text in your locators?”

A dynamic locator problem is when IDs, classes, or text change dynamically and break my locators.

For example, generated IDs like #comp-7x9kq4 may change between renders.

First, I avoid hardcoding dynamic IDs or class names.

Instead, I use getByRole(), getByLabel(), or stable data-testid attributes.

For partial matches, I use filter({ hasText: 'Order' }) or regular expressions like /Order #\d+/.

I also ask developers to add stable test IDs when needed.

So, in short, I use stable locators to make my tests reliable and easy to maintain.

🏢 Enterprise Locator Strategy

⚙️ Handling Changing DOM

Problem
In enterprise apps, components re-render on state change, virtual lists recycle DOM nodes, and SPA routing unmounts/remounts sections constantly.
Solution
1. Locators re-evaluate automatically — no stale refs
2. Use .waitFor() for elements that appear after async ops
3. Use assertions with auto-retry: expect(loc).toBeVisible()
// Wait for element to appear (after API call, animation) await page.locator('.success-banner').waitFor({ state: 'visible' }); // Wait for element to disappear (loader) await page.locator('.loading-spinner').waitFor({ state: 'hidden' }); // Auto-retrying assertion (preferred over waitFor in most cases) await expect(page.locator('.data-table')).toBeVisible();

🏗️ Locator Strategy for Enterprise Apps

START: Need to interact with element
↓
Does element have ARIA role + visible name?
↓ YES
✅ Use getByRole() — done!
↓ NO
Is it a form input with a visible label?
↓ YES
✅ Use getByLabel()
↓ NO
Does it have a stable data-testid?
↓ YES
✅ Use getByTestId()
↓ NO
Use CSS attribute or scoped locator + filter
↓ LAST RESORT
⚠️ XPath — document & request data-testid from dev

📋 Best Practices Summary

  • 🔑 Add data-testid in code review checklist for all interactive elements
  • 🔑 Never hardcode dynamic IDs — detect them early in PR review
  • 🔑 Create Page Object Models (POMs) — centralise all locators, update once
  • 🔑 Use filter() + scoped locators for list/table patterns
  • 🔑 Prefer assertions (expect().toBeVisible()) over manual waitFor()
  • 🔑 Test locators in Playwright Inspector (--debug) before committing
🏆 Enterprise Rule: Locators live in Page Objects. Tests never contain raw selectors — only method calls. This way, one DOM change = one POM update, not 50 test fixes.
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: “What is your locator strategy for a large enterprise application?”

My locator strategy is to prefer role, label, and test ID, followed by CSS and XPath.

The problem is locators may break when the UI changes.

To avoid this, I use stable data-testid attributes whenever needed.

In my framework, I keep locators inside Page Object classes.

This helps because I can update a locator in one place instead of many tests.

For timing, I use Playwright's auto-waiting and retrying assertions like toBeVisible() instead of fixed waits.

So, in short, I use stable locators and proper waits to make tests reliable and easy to maintain.

⚠️ 4 · Common Mistakes & GotchasALWAYS READTIER 3 · 90 sec
  • ⚠️ Using dynamic IDs as locators — they change every render and break tests
  • ⚠️ Forgetting nth() is 0-indexed — nth(0) is first (XPath [1] is first)
  • ⚠️ Using getByText() too broadly — it matches any element containing the text
  • ⚠️ Adding Thread.sleep() — Playwright auto-waits; sleeps cause flakiness and slowness
  • ⚠️ Silencing a strict mode error with .first() — fix the locator instead
  • ⚠️ Structural XPath with no fallback — breaks on even a minor HTML refactor
  • ⚠️ Not scoping locators — scope to a parent container to avoid wrong matches
  • ⚠️ Scattering raw selectors through tests instead of keeping them in Page Objects
