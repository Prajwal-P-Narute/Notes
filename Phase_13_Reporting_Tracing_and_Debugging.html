🗂️ 41. Playwright Reports

After a test run, Playwright can generate different kinds of report formats — pick the one that fits your workflow (local viewing, CI logs, or integration with other tools).

1️⃣ HTML Report

A rich, interactive report you open in the browser — shows pass/fail status, step-by-step timeline, screenshots, traces and errors per test.

// generate + auto-open the HTML report npx playwright test --reporter=html // open it manually later npx playwright show-report

2️⃣ Console (list/line/dot) Reporter

Prints results straight into the terminal as the run happens — good for quick local feedback. Default reporter is list.

3️⃣ JUnit Report

Outputs an XML file in JUnit format — the standard most CI/CD tools (Jenkins, Azure DevOps, GitLab) understand for showing test trends.

4️⃣ JSON Report

Outputs raw results as .json — machine-readable, used for building custom dashboards or feeding data into other reporting tools.

Reporter formats compared
ReporterOutputBest for
htmlInteractive siteLocal debugging, visual review
listTerminal textQuick local run feedback
junitXML fileCI dashboards (Jenkins etc.)
jsonJSON fileCustom tooling / analytics

💡 Tip: configure multiple reporters at once in playwright.config.ts:

// playwright.config.ts export default { reporter: [ ['html'], ['junit', { outputFile: 'results.xml' }] ] };
🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: Which Playwright reporters do you use, and when would you choose each one?

Playwright supports, several reporter formats so results can be reviewed by people or consumed by other tools.

For local review, I prefer the HTML reporter because it provides an interactive view of test results and evidence.

For CI dashboards, I use JUnit XML when the pipeline needs to publish and track test outcomes.

For custom tooling, the JSON reporter provides machine-readable results that can feed a dashboard or analysis script.

When useful, I configure multiple reporters together in playwright.config.ts.

After a run, I can open the HTML report with npx playwright show-report.

So, in short, I choose a reporter based on who consumes the results and how they need to use them.

🔄 Also asked as: “How do you share Playwright results with developers and CI?” · “When would you use JUnit instead of HTML?”

📸 42. Screenshots & Videos

Visual evidence makes debugging failures far faster — Playwright can capture images/video automatically or on demand.

Failure Screenshots

Playwright can auto-capture a screenshot the moment a test fails — configured once, applies to every test.

// playwright.config.ts use: { screenshot: 'only-on-failure' }

Full-Page Screenshot

Captures the entire scrollable page, not just the visible viewport.

await page.screenshot({ path: 'full.png', fullPage: true });

Element Screenshot

Captures just one locator — handy for visual checks on a specific component.

await page.locator('.card').screenshot({ path: 'card.png' });

Video Recording

Records the whole test run as a .webm video — great for spotting timing/animation issues a screenshot would miss.

// playwright.config.ts use: { video: 'retain-on-failure' }
Screenshot options — video values
video settingBehaviour
offNever record
onAlways record, every test
retain-on-failureRecord, keep only if test fails
on-first-retryRecord only during the first retry
⚠️ Note Full-page vs element screenshot vs default viewport screenshot are three different calls — don't mix up fullPage:true with a locator screenshot in interviews!
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: How do you capture screenshots and videos when a Playwright test fails?

I configure, screenshots and videos to preserve useful evidence when a test fails.

For screenshots, I set screenshot: 'only-on-failure' in the test configuration.

For video, I commonly choose retain-on-failure to keep recordings of failed tests.

For a full page, I use page.screenshot({ fullPage: true }) to capture the scrollable content.

For one component, I call screenshot() on a locator to capture that element.

When debugging, video can reveal timing or animation issues that a single screenshot cannot show.

So, in short, I collect enough visual evidence to diagnose failures without generating unnecessary artifacts for every passing test.

🔄 Also asked as: “How do you investigate a UI failure after the run?” · “What is the difference between a full-page and locator screenshot?”
Follow-up Qs: What does retain-on-failure do? · When would you capture an element screenshot?

🧵 43. Trace Viewer

🔥 EXTREMELY IMPORTANT TOPIC Trace Viewer is one of Playwright's signature features — expect this in almost every interview.

A trace is a recorded "movie" of the whole test: every action, every DOM snapshot, every network call — all replayable after the run.

Trace Recording (config)

// playwright.config.ts use: { trace: 'on-first-retry' } // other values: 'off' | 'on' | 'retain-on-failure'

Opening the Trace Viewer

npx playwright show-trace trace.zip

Inside the viewer you get: an Action Timeline (hover any step to rewind), DOM Snapshots (the real rendered page at that moment, inspectable), Network logs (every request/response), plus screenshots and console output — all synced together.

🎤
🗣️ How I'd say it in an interview
❓ Interviewer asks: What is Playwright Trace Viewer, and how do you use it to debug CI failures?

Trace Viewer, lets me inspect a recorded test run after execution, including actions and supporting evidence.

In the trace, I can review the action timeline, DOM snapshots, network activity, screenshots, and console logs.

When a test fails in CI, this evidence helps me investigate without needing to reproduce the failure immediately.

To open a trace, I run npx playwright show-trace trace.zip with the trace file.

For routine CI runs, I commonly configure trace: 'on-first-retry' to capture diagnostic data on a retry.

While investigating, I move through the timeline and inspect the page state around the failing action.

So, in short, Trace Viewer turns a test run into evidence I can replay and inspect systematically.

🔄 Also asked as: “How do you diagnose a failure that happens only in CI?” · “What information does a Playwright trace contain?”
Follow-up Qs: How does on-first-retry differ from on? · Which command opens a trace file?

🐞 44. Debugging

When a test misbehaves, Playwright gives several ways to step through it live instead of guessing from logs.

Test fails or behaves oddly
↓
Run with --debug → opens Inspector
↓
Step through actions one at a time
↓
Hit a page.pause() or breakpoint → inspect live browser
↓
Fix locator/assertion → resume run

--debug flag

npx playwright test --debug

Launches the test in headed mode plus opens the Playwright Inspector — a step-by-step control panel.

Inspector

Lets you step forward action-by-action, view the current locator being used, and try selectors live in its picker.

VS Code Debugging

The official Playwright Test for VS Code extension adds a Test Explorer sidebar — run/debug individual tests with real breakpoints directly in the editor.

Breakpoints

Standard JS breakpoints (in VS Code or via debugger;) pause execution — combine with --debug for full control.

Slow Motion

Slows every action down so you can watch it happen instead of it flashing by.

chromium.launch({ slowMo: 1000 }); // ms delay per action

page.pause()

Drops a manual breakpoint inside your test code — opens the Inspector at that exact line, browser stays open and interactive.

await page.pause();
🧠 Mnemonic: D-I-V-B-S-P → "Debug, Inspect, VS-Code, Breakpoint, Slow-mo, Pause" — the debugging toolkit in order of how deep you go.
💬
🗣️ How I'd say it in an interview
❓ Interviewer asks: What is your usual workflow for debugging a failing Playwright test?

I start, by running the failing test with npx playwright test --debug when interactive inspection is useful.

That opens, a headed browser and Playwright Inspector so I can step through actions.

For a specific point, I can add await page.pause() to inspect the page mid-test.

In VS Code, I use the Playwright Test extension and normal breakpoints when that fits the investigation.

For timing issues, slowMo can slow actions down so I can observe the sequence.

After finding the cause, I fix the locator, assertion, timing assumption, or test data rather than simply hiding the failure.

So, in short, I use reports and debugging tools to identify the cause, then make a targeted, reliable fix.

🔄 Also asked as: “How do you troubleshoot a flaky UI test?” · “How can you pause a test and inspect the browser?”
Follow-up Qs: How is page.pause() different from --debug? · When is slowMo useful?

⚠️ Common Mistakes & Gotchas ALWAYS READ

⚠️ Forgetting trace/video only capture on retry by default — a single run with no retries produces nothing.

⚠️ Mixing up fullPage:true with an element screenshot — they are different API calls.

⚠️ Leaving page.pause() in committed code — it will hang any CI run.

⚠️ Assuming --debug works headless — it always forces a headed browser.

⚠️ Setting video:'on' for every test in CI — huge storage cost; prefer retain-on-failure.

🧠 Trace = "black box flight recorder" — replay everything after the crash (failure).
